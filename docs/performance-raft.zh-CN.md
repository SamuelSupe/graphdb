# Raft 空事务优化与性能验证

日期：2026-10-01（Asia/Singapore）。分支：`codex/raft-ha`，独立 worktree：`GraphDB-raft-ha`。本次优化基于已实现分片扩容的 `984cb692`，保留默认单机、单组 Raft 和目录组加数据组的分片部署。

## 改动及一致性边界

原实现对每个 Raft `Ready` 都执行 bbolt 写事务。只包含心跳、消息或 `ReadIndex` 结果的通知也会提交事务并同步磁盘，虽然没有日志、HardState 或快照需要保存。

现在仅在这三个持久化字段都为空时跳过事务。包含 commit 位置的 HardState 即使 `MustSync=false` 也仍然保存；日志、投票和快照的落盘顺序保持不变。强读取继续使用 `ReadOnlySafe` 多数派确认并等待本地应用，没有增加读取租约、缓存读取屏障或降低写入持久化要求。

这项改动位于 Raft 专用存储，单机数据路径没有变化。目录组和数据组复用同一实现，均可减少只读与心跳的额外同步。

## 测量方法

- OrbStack Linux aarch64，Go 1.26.7；容器限制 8 CPU / 8 GiB，每个数据库进程 `GOMAXPROCS=2`。
- 单组使用三个独立进程和数据目录，通过真实 HTTP 通信；分片使用三副本目录组、三副本数据组和独立入口。所有进程位于同一宿主机和容器网络空间，不能代表跨机网络延迟或故障域。
- 数据和结果使用独立 Linux 持久卷，源码及二进制只读挂载；每个变体、场景和轮次重新创建数据目录，不清理用户数据或全局缓存。
- 复用现有 `tools/loadtest`，固定 1,002 个实体，写批次 20 项。预先播种后运行只读预热，测量期间只更新固定实体，避免图规模随轮次增长。
- 读者轮流执行匹配、遍历、`min_version` 查询和扫描。混合负载为 4 个写者加 16 个读者，纯写入为 4 个写者。
- 每轮核对请求错误、发布批次数与图版本增长一致，并验证 `min_version`；CPU 与磁盘写入取所有服务进程的 `/proc` 增量，包含服务日志，排除负载客户端。
- 先用同一二进制进行两轮 A/A 校准，再按相反顺序交错运行旧版和优化版。A/A 采集 CPU profile；性能比较关闭 profile，两个变体采用相同参数。
- 本机还运行其他工作负载。A/A 在不同场景出现最高约 26% 的相邻吞吐差异，因此保留逐轮结果，不把微小差异当作可靠收益。

旧版二进制 SHA256：`849e13cd1b165e6ab9f2ae83bcb5659db916a6b51c860b5c95d9cb073206bbdd`。

优化版二进制 SHA256：`c4214fdb27e1ee073906b65160bccb0d715e587cd3a0e242de983b0d2b86c69f`。

## 单组 Raft 结果

每个窗口测量 30 秒、预热 5 秒，两轮反转运行顺序。吞吐为四种读操作的合计完成数/秒；p95 按具体操作统计，不合并不同操作的百分位。

| 并发读者 / 轮次 | 旧版读次数/秒 | 优化版读次数/秒 | 同轮提升 | 匹配查询 p95，旧→新 ms | 所有副本写入字节/读，旧→新 | CPU 毫秒/读，旧→新 |
| --- | ---: | ---: | ---: | --- | --- | --- |
| 8 / 1 | 432.1 | 1,298.4 | +200.5% | 30.05 → 11.39 | 133,259 → 357 | 1.963 → 1.288 |
| 8 / 2 | 470.6 | 1,217.3 | +158.7% | 28.24 → 12.05 | 126,653 → 357 | 1.857 → 1.384 |
| 32 / 1 | 835.8 | 1,402.8 | +67.8% | 60.17 → 32.54 | 51,347 → 358 | 1.567 → 1.277 |
| 32 / 2 | 533.2 | 866.5 | +62.5% | 96.73 → 55.21 | 58,384 → 359 | 2.492 → 1.816 |

只读窗口每次操作的磁盘写入减少 99.3%–99.7%，剩余写入包含请求和查询日志。单位操作 CPU 下降约 18%–34%；优化版因为完成了更多请求，总 CPU 时间增加，不能据此声称总 CPU 用量降低。

旧版只读 profile 中 `diskStorage.save` 所在的 bbolt 更新路径占 Leader CPU 样本约 8%，`fdatasync` 约 7%；CPU profile 不包含全部磁盘等待时间。观察到的吞吐收益来自避免每次多数派读取中的额外事务和同步，不能将 CPU 样本比例直接当作总延迟比例。

| 场景 / 轮次 | 合计操作/秒，旧→新 | 写批次/秒，旧→新 | 匹配查询 p95，旧→新 ms | 写入 p95，旧→新 ms |
| --- | --- | --- | --- | --- |
| 4 写 + 16 读 / 1 | 27.99 → 27.46 | 3.22 → 3.09 | 1,040.30 → 1,154.03 | 1,772.07 → 1,941.34 |
| 4 写 + 16 读 / 2 | 19.92 → 18.45 | 2.46 → 2.46 | 1,739.96 → 1,806.24 | 2,251.52 → 2,230.89 |
| 4 写 / 1 | 3.06 → 3.48 | 3.06 → 3.48 | — | 1,835.40 → 1,896.11 |
| 4 写 / 2 | 2.99 → 2.63 | 2.99 → 2.63 | — | 2,146.76 → 2,330.49 |

混合操作吞吐分别下降 1.9% 和 7.4%，纯写吞吐一升一降；写入 p95 多数窗口略高。A/A 混合吞吐差异为 −5.6% / +23.8%，混合写入 p95 差异为 −36.7% / −15.0%，纯写 p95 差异为 −12.5% / +1.5%。目前不能区分这些小幅变化与环境波动，写入性能结论为 **UNKNOWN**，不宣称混合或纯写收益，也不将“未确认回归”表述成“已保证不回归”。图应用及其文件事务仍是写入性能的后续优化边界。

## 分片入口结果

每轮连续运行两次旧版及一次优化版，第二轮反转顺序。三个窗口均为 8 个读者、30 秒测量、5 秒预热，旧版两个窗口也用于该拓扑的 A/A 校准。此场景包含目录强读取、Leader 发现、入口转发及数据组强读取。

| 轮次 | 旧版 A/A 读次数/秒 | 优化版读次数/秒 | 相对两个基线的提升 | 匹配查询 p95，旧 A/A→新 ms | 服务写入字节/读，旧 A/A→新 |
| --- | --- | ---: | --- | --- | --- |
| 1 | 284.09 / 286.90 | 948.92 | +230.8%–234.0% | 61.94 / 41.69 → 15.34 | 242,511 / 192,875 → 358 |
| 2 | 239.23 / 229.67 | 599.18 | +150.5%–160.9% | 49.87 / 56.07 → 46.57 | 186,181 / 257,149 → 359 |

同轮 A/A 吞吐差异约 1.0% 和 4.0%。分片读吞吐和单位读取的磁盘写入有明显收益，第二轮 p95 仅小幅降低，不能将第一轮的延迟收益外推到所有运行条件。未测量分片混合写入、多个热点数据组或迁移中的性能。

逐窗口的 SHA256、CPU、磁盘写入、主机负载、版本核对及全部操作的 p50/p95/p99 见 [原始测量记录](performance-raft-results.json)。完整服务日志、数据目录与基线 profile 保留在专用卷 `graphdb-raft-perf-data` 的 `aa-raft-v2`、`ab-raft`、`ab-sharded` 目录；本机副本和后续恢复验收位于 `/tmp/graphdb-raft-perf/`。

## 复现

使用同一 Go 工具链分别构建基线和优化版，并构建 `./tools/loadtest`。以下示例中 `/bench` 挂载两个服务二进制和 loadtest；所有输出放在新建测试卷中。

```sh
docker --context orbstack run --rm --cpus 8 --memory 8g \
  -v "$PWD:/workspace:ro" -v /absolute/binaries:/bench:ro \
  -v graphdb-raft-perf-data:/runs -w /workspace golang:1.26-bookworm \
  python3 scripts/raft_benchmark.py \
  --variant before=/bench/graphdb-before --variant after=/bench/graphdb-after \
  --loadtest /bench/loadtest --output /runs/new-comparison \
  --cases read-8 read-32 mixed-direct write-direct \
  --rounds 2 --seconds 30 --warmup 5
```

A/A 校准将两个 `--variant` 指向同一文件；分片场景增加 `--topology sharded`。需要 CPU profile 时增加 `--profile`，播种后会重启到独立管理监听器以访问 pprof，然后重新预热。测量进程退出后会停止专用服务，结果和目录留在测试卷中。
