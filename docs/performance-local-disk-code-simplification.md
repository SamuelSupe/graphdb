# 本地磁盘版代码简化与验证（2026-09-19）

基线：`codex/local-disk-v2` 的 `aa2c9f4c841f7cf00f1b57fbf33dcbf67f11ab36`。
对比对象：本轮代码简化实现；索引基准采集于维护修复前的候选代码，后续修复不改变该索引路径。原 `main` 和已有发行版本未修改。

## 完成的改造

- 死信内部遍历使用一次新鲜目录扫描，保留游标、提前停止和错误传播；避免每翻一页重新枚举整个目录。
- 深度索引检查按实体页、边分片一次分组；当前和历史分片规则共用一次哈希计算，保留内容校验。
- 删除不可达的 PostgreSQL 协调实现及其专用测试。保留本地租户锁、写入围栏、WAL 恢复、持久化格式，以及拒绝 PostgreSQL 标记和不支持配置的边界。
- 本地 GC 默认按最多 64 次删除分批，在批次间释放读视图锁和租户锁。每批重新读取 manifest/catalog，重新判断文件是否仍被引用；显式 `MaxDeletes` 保留总预算，内部同样按 64 个文件分批并返回检查点。索引孤儿清理也支持预算、游标和 dry-run。

最初简化候选的生产 Go 代码从 93,606 行降至 86,456 行，净减少 **7,150 行**。测试代码从 65,963 行降至 61,391 行；移除的是已退役协调路径测试，同时补充目录扫描、历史分片和 GC 并发边界回归。统计包含新增文件，不含忽略目录中的临时工具。

## 定向性能结果

环境：OrbStack，Linux arm64，`golang:1.25-bookworm`（Go 1.25.14），容器限制 4 CPU / 6 GiB，`GOMAXPROCS=4`。源码放在 Linux 卷，基准使用 FileStore 和 Go 测试临时目录。

复用 `BenchmarkIndexHealth10K`：10,000 实体、5,000 边，先写入、compact、重建索引并检查一次，然后计时。每个版本执行一次 `-benchtime=3x -count=1`；最终基准没有与本任务的其他测试并行运行。

| 指标 | 基线 | 最终实现 | 本次变化 |
| --- | ---: | ---: | ---: |
| ns/op | 1,650,654,591 | 1,486,446,947 | -9.95% |
| B/op | 3,395,348,826 | 3,370,343,616 | -0.74% |
| allocs/op | 18,425,038 | 17,488,888 | -5.08% |

这是预热后的深度检查小样本，未清空操作系统页缓存，不代表冷启动、冷盘、请求 p95 或整体吞吐。`B/op` 是累计分配字节，不是峰值 RSS；单次检查的累计分配仍较高。本次定向基准没有覆盖三方案多轮对比或十万实体负载；后续发布持续负载见文末，不能据此宣称原计划的整体性能验收目标已达成。

## 仍然存在的边界

GC 限制的是每批删除数量，不是持锁时间上限。单个大文件的校验、首次大目录枚举仍可能耗时；本轮未引入新的索引服务或后台目录缓存。上述测试覆盖本轮改动的行为和关键并发边界，不构成所有负载下无缺陷的保证。

## 2026-09-20 发布门禁发现与修复

候选 `v1.3.4-local.2`（`a5cc9d49`）通过静态、HTTP 和对象备份检查，但 30 分钟持续负载失败：compact 等待超时、存活 GC 被判心跳过期，随后 WAL 写入等待超时。该候选没有上传发行包，失败记录保留在 GitHub Actions 运行 `35483883169`。

- GC 最后一页可能在删除预算耗尽前丢弃缓存，下一批重新枚举并纳入持续新增的文件。修复后，一个前缀的候选列表保留到游标离开该前缀，后续新增文件留给下一次 GC。
- 索引清理释放租户维护执行名额，允许 compact 继续推进；全局工作线程上限保持有效。
- 本地已注册的存活 GC 工作线程优先于心跳时间判断，覆盖排队和繁忙期间的心跳延迟。

三个聚焦回归在旧候选上均失败，修复后在 OrbStack 通过；相关 task/GC/index 的 race 检查也通过。候选 `v1.3.4-local.3`（`a7e60a43`）重新执行完整门禁：静态、HTTP、对象备份检查通过；30 分钟负载中业务操作错误数为 0，完成 5 次 compact、2 次 GC 和 2 次索引重建。但报告工具遗漏用量采样的正常结束取消分类，导致流水线 `35485649579` 失败，因此没有发行包。

唯一未分类事件出现在 `03:36:30.488Z`，恰好对应 `03:06:30.488Z` 开始的 30 分钟全局上下文截止时间。补齐与其他采样一致的分类后，同一份未修改原始日志通过报告校验；关闭窗口外超时和非超时错误仍由回归测试保护。候选 `v1.3.4-local.4` 只修改报告工具和版本元数据，数据库实现与候选 `.3` 相同。


候选 `.4` 的发行流水线 `35487236749` 再次暴露真实维护阻塞：9 次查询达到 120 秒请求期限，一次 GC 状态轮询超时。它没有上传发行包；并非前述正常结束报告分类问题。相同提交的分支 CI 全部通过，发行 CI 的两个恢复测试另有 2 秒轮询超时，本地分别重复 10 次通过，未放宽其超时。

在 OrbStack 的 2 CPU / 7 GiB Linux 本地卷上，使用相同 4 写入 / 16 查询负载和 pprof 复现维护争用，定位到：

- 自动维护的 GC 设置了 `MaxDeletes=256`，旧分支直接调用一次 GC，绕过每批 64 文件的让锁机制；持锁期间逐个文件同步删除。
- 多个维护写锁同时等待时，原先的写者优先会在批次间继续挡住查询。修复后排队的读视图可在两个维护批次间执行；WAL 写入受理的背压优先级不变。

新增或扩展的两个回归在旧实现上失败，修复后通过 race；覆盖显式总预算跨批次、dry-run、固定候选集及维护写锁之间的读请求。完整正式源码包的单元测试、vet、race 在 OrbStack 通过（storage race 170.316 秒）。忽略目录中的历史压测临时 Go 文件不属于正式包，验证时列出 cmd、internal、docs、sdk、tools 全部源码目录。

诊断证据位于 `.workflow/release-profile-20260920/`，包括修改前后堆栈、负载日志和回归结果。该诊断与其他验证有过并发，不作为性能提升比例的测量。新候选使用 `v1.3.4-local.5`；只有完整发行门禁通过后才上传发行包。


读视图公平性修复后的 8 分钟加压诊断使用 500 ms 写入间隔（发行门禁为 5 s），查询及写入错误数为 0，但 GC 等待仍超过诊断工具的 5 分钟期限。该 GC 最终成功删除 11,434 个文件，用时 7 分 37 秒；此轮不能记为门禁通过。后续合并同一删除批次的目录同步，复用已有持久化队列，在错误和取消路径仍先同步再释放锁，并用目录失效回归保护同步失败传播。此修复不省略 Parquet 内容检查。


合并目录同步后，OrbStack 正式源码包再次通过完整单元测试、vet 和 race（storage race 166.341 秒）。使用发行门禁相同的 5 秒写入间隔、4 写入 / 16 查询进行 4 分钟检查，业务操作错误数为 0，完成 3 次 compact、1 次 GC 和 1 次索引重建。它与前述 500 ms 加压诊断负载不同，不能据此计算性能提升；30 分钟发行门禁由新标签流水线执行。


随后在相同 500 ms 写入间隔下复测 8 分钟，进程正常退出，业务操作错误数为 0，完成 5 次 compact、2 次 GC 和 2 次索引重建；两个已完成 GC 的等待分别约 118 秒、9 秒。诊断日志为 `soak-after-batch-heavy.ndjson`。不过报告仍拒绝了恰好在 8 分钟截止时产生的维护取消事件：维护循环与查询/写入循环的结束处理不一致。

候选 `.5`（`29bfa1e2`）因此取消发行流水线 `35490064098`，未发布发行包。将 compact、GC、索引重建共用的维护循环在全局上下文取消时退出，同时保留独立请求期限和实际业务错误；不扩大报告器忽略窗口。聚焦回归覆盖这三类结果。数据库生产实现与 `.5` 一致，使用 `v1.3.4-local.6` 重新执行完整发行门禁。


`.5` 的分支 CI `35490064480` 另有同一文件恢复测试触发 2 秒等待上限（该 race 测试总耗时 3.11 秒），而本地此前各重复 10 次通过。将用于验证异步任务终态的测试辅助函数改为有上下文取消的 10 秒等待，并在失败时输出最后状态和阶段；这不是产品延迟指标，未调整 HTTP、WAL、维护任务或持续负载的超时阈值。


候选 `.6`（`f6ad0035`）通过完整分支 CI、发行静态检查、HTTP/WAL 和对象备份检查，但发行流水线 `35490715250` 的 30 分钟负载仍失败：2 次 GC 等待超过 5 分钟，1 次 compact 超时，4 次写入等待超过 120 秒；查询错误数为 0。没有发布发行包。

根因是本地 GC 虽释放文件维护锁，却仍在整个任务期间持有租户任务执行名额，阻止 compact 和排队的索引重建启动，继而造成 WAL 背压。修复后，GC 放开外层任务名额，每批重新申请全局执行容量，用已有租户和读视图锁保护批次；同步 HTTP、自动维护、统一任务和旧索引任务均传递相同的 admission 上下文。后台维护并发上限保持有效。

单执行名额回归在旧 `.6` 上失败：其他维护只能在全部垃圾删完后运行；修复后，其他维护可在批次之间运行，并且 GC 必须等待其释放名额。聚焦 storage race 与 HTTP 维护测试通过，证据见 `admission-before.log` 和 `admission-final.log`。新候选使用 `v1.3.4-local.7`，重新执行完整发行门禁。

修复后正式源码包的完整单元测试、vet、race 在 OrbStack 通过（storage race 170.735 秒），Go/Python SDK 版本检查通过。
