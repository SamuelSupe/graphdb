# Raft 高可用运行说明

本页介绍 [高可用设计](high-availability-design.zh-CN.md) 的单组部署：三个完整副本、单主写入、强一致读取、自动接管。节点各自持有独立目录和磁盘，属于 Share-Nothing 部署；单组写入由一个 Leader 承担。需要扩容时，可选 [分片部署](sharding.zh-CN.md)，通过独立 Raft 数据组和租户迁移增加容量。

单机和 Raft 使用同一二进制，均支持 direct / WAL。未设置 `GRAPHDB_RAFT_*` 时，默认单机运行，保留原有本机 WAL、定时维护、自动 S3 备份和离线 CLI；`GRAPHDB_MODE=all` 在两种部署中均表示一个进程提供完整图服务。设置节点 ID 和完整 Raft 配置后才启用集群；不完整的 Raft 配置会导致启动报错。两种部署使用独立端口和数据目录即可同时运行。

## 启动集群

使用三个新的、独立的数据目录。不要把已有单机目录直接作为任意一个副本加入集群；通过集群 API 导入数据或恢复已有备份。首次启动的三个节点使用完全相同的集群 ID、成员地址和随机通信令牌。

```sh
export GRAPHDB_RAFT_TOKEN="$(openssl rand -hex 32)"
docker --context orbstack compose -f docker-compose.raft.yml up --build -d
```

本机验证入口为 `http://127.0.0.1:8080`。示例的 HAProxy 通过 `/v1/readiness` 选择可服务节点；Follower 将数据请求和就绪确认转发到 Leader。就绪检查不等待维护应用结束，正常图操作仍使用完整读取屏障。生产访问入口也需要多个实例或外部高可用负载均衡，三个数据库节点应位于独立故障域。示例本机容器共用同一宿主机，不能证明宿主机故障可用性。

Raft 监听器只开放在可信私有网络；示例不发布 8081。通信校验集群 ID 和至少 32 字节的共享令牌，HTTP 传输本身不加密。跨不可信网络需使用受保护的网络或 TLS 隧道。节点的数据目录和 Raft 日志属于同一副本，不要单独复制其中一部分。

| 环境变量 | 含义 |
| --- | --- |
| `GRAPHDB_RAFT_NODE_ID` | 非零节点 ID；设置后启用 HA |
| `GRAPHDB_RAFT_CLUSTER_ID` | 稳定集群身份 |
| `GRAPHDB_RAFT_ADDR` | 独立的 Raft `host:port` 监听器 |
| `GRAPHDB_RAFT_PEERS` | 节点 ID 到私有 HTTP origin 的 JSON 对象 |
| `GRAPHDB_RAFT_TOKEN` | 所有节点相同的通信令牌 |
| `GRAPHDB_RAFT_DIR` | 默认数据目录下 `.graphdb-raft` |
| `GRAPHDB_RAFT_BOOTSTRAP` | 初始三个投票节点为 `true`；新替换节点为 `false` |
| `GRAPHDB_RAFT_TICK` | 默认 `100ms`，选举使用 10 个 tick |
| `GRAPHDB_RAFT_SNAPSHOT_ENTRIES` | 默认每 1000 条应用日志创建快照；成员变更强制更新快照 |
| `GRAPHDB_RAFT_MAX_SNAPSHOT_BYTES` | 默认 `512MiB`，限制复制快照（含传输封装）和安装后的展开数据量 |
| `GRAPHDB_RAFT_ALLOW_LEGACY_PROTOCOL` | 默认 `false`；仅已验证来源的首次桥接暂设 `true`，全组升级后逐个重启关闭 |

HA 下离线修改命令拒绝启动；数据目录也拒绝绕过 Raft 的普通写入。副本首次加入时即持久化复制模式标记，因此即使 Raft 日志存放在其他目录、尚未应用日志，删除 Raft 环境变量也不能以单机模式打开副本目录。已有单机目录不需要新增配置或模式标记。跨模式迁移通过 API 导入或备份恢复到新目录完成。所有副本需使用影响编码、限额及业务语义一致的配置。跨版本混部仅限 [滚动升级兼容窗口](raft-rolling-upgrade.zh-CN.md#兼容窗口)。

## 成功、重试和读取

- direct 请求在多数派持久化日志、Leader 发布本地图版本后返回成功。
- WAL `202` 返回 `durability=raft_majority`：内容、身份和租户代次已多数派持久化。独立本机 ingest WAL 不再启用。Leader 将明确的请求列表写入 `flush` 日志后合批发布；新主继续处理受理队列。
- 受理队列使用 `GRAPHDB_INGEST_QUEUE_MEMORY_MAX_BYTES` 作为未完成请求的字节预算；Raft 还限制等待提案及未应用日志积压。超出预算返回可重试错误。
- 请求断开或超时仍可能提交。使用相同幂等键重试，并通过状态接口核对；同一身份的不同内容会产生冲突。
- 普通查询在 `ReadIndex` 多数派确认后等待本地应用，随后固定读取范围。Follower 转发到当前 Leader 执行，不能联系多数派的隔离节点返回 `503`；响应的 `X-GraphDB-Leader-ID` 是发现提示，客户端应重试高可用入口。
- `/v1/health` 返回 Raft 节点 ID、Leader ID、term、提交与应用位置、应用积压条数、当前应用缓冲字节、待响应提案字节和错误。`application_entries` 和 `application_commits` 分别统计本进程成功应用的日志条数与本地应用事务数，可用增量观察合并程度；重启后计数重置。`/v1/readiness` 是节点流量准入依据；判断 Leader 使用本地健康响应的节点 ID 和 Leader ID。
- 携带 `min_version` 时，保存响应的 `X-GraphDB-Tenant-Generation`，下一次读取传 `X-GraphDB-Read-Generation`。恢复或清除租户后，旧代次请求返回 `409 tenant_generation_changed`，避免相同版本数字被误用。
- 分页游标保留逻辑版本、排序位置和租户代次。接管节点无法提供游标绑定的本地 catalog 时，现有游标校验明确报错，客户端重新开始扫描。

## 快照、任务和 S3

Raft 日志和投票状态使用 bbolt 原子事务持久化。正常复制携带逻辑请求及 Leader 决定的 ID、时间、合批列表；每个节点自行生成图存储文件。Raft 的心跳/传输与图应用使用不同执行循环，慢应用不会占用心跳执行队列。应用仍按日志顺序执行。待应用工作只保留日志位置，负载从 bbolt 按最多 4MiB 的窗口读取（单条较大的日志仍完整读取）；启动不再把全部日志载入内存。普通图查询、扫描和导出固定本地读取视图后释放应用锁，普通提交及 WAL 合批可以同时推进。租户替换、归属切换和其他结构变更仍等待已有读取结束。运行中查询的列举与取消属于本进程，不经过 Raft 读取屏障或应用锁。

复制快照包含图文件、租户代次、已受理请求、幂等记录、任务、已应用位置和成员地址。创建快照时逐文件流式读取；安装时先解压到临时磁盘，完整校验摘要、压缩归档、文件路径和大小后，再逐对象通过应用事务发布。安装期间不提供正常图服务，查询取消仍可进入本进程。压缩快照及传输封装仍在内存中，完整快照仍受字节预算限制；这不是无限容量的快照协议。应用日志在修改文件前持久化旧内容；崩溃后回滚不完整应用，再重放，已完成提交不重复增加版本。

应用事务的回滚日志允许不同对象并行准备旧内容，并合并最多 8 个并发记录，配置的合并延迟为 100 微秒。串行记录直接提交，同一对象的后续修改复用已持久化的第一份旧内容。每个对象仍在回滚记录持久化成功后才修改文件；文件和目录同步、最终提交标记保持原有顺序。该优化不改变磁盘格式或多数派语义，单机写入路径保持不变。三、五副本性能和并行崩溃恢复结果见 [补充验收](raft-ha-validation.zh-CN.md#回滚日志合并补充验收)。

已经多数派提交、操作类型相同的连续发布日志，每次最多 8 条共用一个本地应用事务，直接消费已有日志窗口，不等待凑批。命令仍逐条执行，各自保留 ID、时间、版本、WAL 受理位置和响应；整个事务及最后一个应用位置持久化成功后才确认请求。WAL 受理与图发布分别合并，受理确认不等待同一窗口中的后续 flush。批次中途失败或进程退出时，恢复完整旧状态，再按持久日志重放。成员配置、空日志、任务、租户替换和归属变更分别构成合并边界。日志、快照和 checkpoint 的磁盘编码保持兼容；升级按已验证的版本窗口执行。

连续应用合并的三、五副本混合吞吐、崩溃恢复和单机/分片共存结果见 [吞吐补充验收](raft-ha-validation.zh-CN.md#连续日志应用吞吐补充验收)。

命令执行过程中若节点关闭或应用上下文被取消，即使处理层将取消转换成 HTTP 超时响应，应用事务也会回滚、保持原来的 checkpoint，重开后从已提交日志重放。取消响应不会被保存为命令的已执行结果。

同一应用事务内，每个对象的重复改写合并为一次最终文件同步，并复用已有执行器、最多以 2 个工作者并发完成。改写之前仍先持久化回滚记录，新对象也记录原先不存在；所有最终文件内容、目录和提交标记依次持久化成功后才确认请求。单机写入继续立即同步。删除对象会移除其待同步记录，租户目录替换会先完成已有文件与目录的同步，避免重命名或硬链接遗漏尚未持久化的数据。最终同步失败时 checkpoint 不前进，重开后恢复旧状态。测量范围及验证结果见 [重复对象同步验收](raft-ha-validation.zh-CN.md#重复对象同步合并补充验收)。

WAL 终态受理记录保留请求 SHA256、接入身份、状态和结果，去掉原始写入 items，原幂等身份仍永久保留。已有完整请求记录可以由新版读取和校验；历史记录不会被无期限删除。引入该格式之前的旧版不能可靠解释终态摘要；这些旧版仍需要维护升级。第四轮修复候选已包含该格式，可按本轮滚动窗口桥接。

超过快照预算时保留日志和在线读取，拒绝后续变更，并在健康状态中暴露 `snapshot_error`。应提高预算后逐节点重启恢复写入；不要删除数据或日志。

集群任务的排队和执行均有日志记录，切主后继续处理排队任务。维护任务通过集群接口执行，首版不启用单机定时维护循环。任务执行和快照占用本地应用阶段，新查询和新写入可能等待；生产维护长尾需要单独测量。

S3 继续使用现有 `GRAPHDB_BACKUP_S3_*` 配置。手动对象备份先复制并固定捕获结果，只有 Leader 上传和校验，再复制任务完成结果；稳定任务 ID 允许切主重试同一上传。租户恢复由 Leader 下载、校验完整内容，以每块最多 1MiB 的日志复制到各副本的暂存目录，最后复制恢复发布命令。每个副本先检查所有块的大小和完整 SHA256，再执行原有恢复事务并发布新代次；成功、准备失败或取消时清理暂存。持久化块损坏时拒绝应用、保留 checkpoint 和错误证据，需要按副本故障处理。换主可以按任务身份和固定摘要续传，已经持久化的相同块不用重传；输入完整复制后不再依赖原备份源。租户清空或替换后旧恢复失效，不能把旧数据写回新代次。Follower 不在应用时下载 S3。旧的单条恢复日志仍能被新版读取。

后台命令准备完成后，任务可能被清除或 GC 移除。应用时发现任务已不存在，会以业务冲突消费该日志并清理对应恢复暂存，继续推进 checkpoint。分片 WAL 发布也核对当前归属状态和代次，迁移或取消后过期的发布命令不能读取已清理的源数据。任务内容损坏、当前归属下的受理记录缺失和实际存储错误仍按副本故障处理。回归证据见 [第三轮审核](raft-p0-p1-review3-2026-10-02.zh-CN.md)。

任务执行中的本地对象读取、读取准入、缓存和流式 I/O 错误纳入复制事务，不能被转换为任务失败后继续推进 checkpoint。Raft 受理导入时保存原始源摘要，Leader 核对后将 SHA256 写入执行日志；副本上的源缺失或变化使该副本回滚并停止应用。Leader 准备阶段发现源无效或变化时保存一致失败，不发布图数据。旧任务或执行日志没有源摘要时保留相应旧语义，不回溯补写证明。可选对象不存在与正常 EOF 不影响提交，单机任务保留原有错误语义。回归证据见 [第四轮审核](raft-p0-p1-review4-2026-10-02.zh-CN.md)。

分块恢复解除整份备份必须装入单条 32MiB 提案的限制，但不是无限容量恢复。准备和解码仍在内存中构建完整备份/图；暂存块也计入整个组的快照预算。开始传输前检查现有文件、输入和归档开销是否能装入 `GRAPHDB_RAFT_MAX_SNAPSHOT_BYTES`，预算不足则让任务明确失败。执行期间仍需为其他写入、快照、旧图和恢复临时目录预留内存与磁盘空间。各副本必须使用相同预算，不能仅调大 Leader 的配置。

HA 首版暂不支持自动备份策略；启用请求明确报错。可由外部调度调用集群手动备份接口。手动恢复演练需提供明确的 `backup_key`。维护清理可以令此前保留的分页游标过期，客户端需要重新开始扫描。

## 安全替换节点与滚动升级

Raft 管理接口位于私有 Raft 监听器，请求必须携带 `Authorization: Bearer <令牌>` 和 `X-Raft-Cluster: <集群 ID>`。

1. 用新的 ID、空目录、完整当前成员地址启动替换节点，`GRAPHDB_RAFT_BOOTSTRAP=false`。
2. 向当前 Leader `POST /raft/members`，请求 `{"action":"add_learner","id":4,"url":"http://node4:8081"}`。
3. 等待新节点追赶，再请求 `{"action":"promote","id":4}`。尚未追赶完成返回 `409`。
4. 请求 `{"action":"remove","id":旧节点ID}`。移除后 ID 永久保留，不能复用；保持至少三个投票副本。
5. 停止旧节点。新节点会从包含其成员配置的快照及后续日志恢复。

成员变更在多数派提交后，按日志顺序核对受理时的成员配置；在生效检查中发现配置已变化时返回 `409`，不会覆盖已有节点地址或突破至少三个投票副本的限制。`204` 表示该请求对应的配置和通信地址已经在当前节点持久化。遇到超时或切主返回错误时，先查询当前 Leader 的状态，再按最新配置决定是否重试；不能从旧 Leader 的空进度列表判断移除成功。成员变更应逐项执行。

使用 `GET /raft/upgrade` 检查全组，`POST /raft/drain` 等待已有提案完成并交接 Leader；一次只替换一个副本，追赶后再继续。跨版本仅支持已做双版本验收的兼容窗口；第四轮修复候选可首次桥接到本轮协议 1，完成后关闭 legacy 通信。更早程序的维护升级限制仍保留。分片入口提供双 router 和摘流接口。步骤、协调脚本及回退边界见 [滚动升级手册](raft-rolling-upgrade.zh-CN.md)。丢失多数副本时停止写入，不通过重新 bootstrap 残存目录强行组成新集群。

## 验证

候选镜像的固定容器门禁使用 `GRAPHDB_GATE_IMAGE=<镜像> scripts/raft_gate.sh`。发布工作流额外运行三十分钟 Raft WAL 混合负载，记录二进制 SHA256、镜像 ID、逐项结果和日志。该门禁在一台宿主机上运行，跨宿主机故障域验收仍独立进行，详见 [发布准备状态](raft-release-readiness.zh-CN.md)。

针对新的一致性与恢复边界运行 `internal/ha` 和 `internal/storage` 的集成测试，另外使用实际 Linux 二进制启动三个独立进程进行入口与故障切换验证。结果与未验证边界见 [验收记录](raft-ha-validation.zh-CN.md)。协议实现参考 [etcd/raft](https://github.com/etcd-io/raft)，入口健康检查配置参考 [HAProxy 文档](https://docs.haproxy.org/3.0/configuration.html)。

目录同步合并的三、五副本对比与持久化验收见 [性能复测](performance-raft-directory-sync.zh-CN.md)，其中三副本仍有明显回退，不能据此宣称整体性能提升。
