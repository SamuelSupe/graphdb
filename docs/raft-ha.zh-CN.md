# Raft 高可用运行说明

适用于 **GGraphDB 2.5.1**；发行资格见[版本验证](validation-v2.5.1.md)，升级约束见[版本边界](naming-and-compatibility.zh-CN.md)。

本页介绍 [高可用设计](high-availability-design.zh-CN.md) 的单组部署：三个完整副本、单主写入、强一致读取、自动接管。节点各自持有独立目录和磁盘，属于 Share-Nothing 部署；单组写入由一个 Leader 承担。需要扩容时，可选 [分片部署](sharding.zh-CN.md)，通过独立 Raft 数据组和租户迁移增加容量。

单机和 Raft 使用同一二进制，均支持 direct / WAL。未设置 `GRAPHDB_RAFT_*` 时，默认单机运行，保留原有本机 WAL、定时维护、自动 S3 备份和离线 CLI；`GRAPHDB_MODE=all` 在两种部署中均表示一个进程提供完整图服务。设置节点 ID 和完整 Raft 配置后才启用集群；不完整的 Raft 配置会导致启动报错。两种部署使用独立端口和数据目录即可同时运行。

## 启动集群

使用三个新的、独立的数据目录。不要把已有单机目录直接作为任意一个副本加入集群；通过集群 API 导入数据或恢复已有备份。首次启动的三个节点使用完全相同的集群 ID、成员地址和随机通信令牌。

```sh
export GRAPHDB_RAFT_TOKEN="$(openssl rand -hex 32)"
docker --context orbstack compose -f docker-compose.raft.yml up --build -d
```

本机验证入口为 `http://127.0.0.1:8080`。示例的 HAProxy 通过 `/v1/readiness` 选择可服务节点；Follower 将数据请求和就绪确认转发到 Leader。就绪检查不等待维护应用结束；本地磁盘探测使用独立临时文件，不等待数据发布屏障，但仍检查真实写入/同步失败、恢复错误和目录关闭。正常图操作仍使用完整读取屏障。生产访问入口也需要多个实例或外部高可用负载均衡，三个数据库节点应位于独立故障域。示例本机容器共用同一宿主机，不能证明宿主机故障可用性。

示例每秒检查入口，连续三次失败才摘流，一次成功恢复准入，避免一次磁盘长尾同时移除所有副本。数据请求始终执行多数派和应用屏障；健康检查容错不会许可隔离节点服务过时数据。摘流传播需要时间，升级控制器在 drain 成功后默认等待 7 秒再停止进程，生产环境应按实际负载均衡策略调整。

Raft 监听器只开放在可信私有网络；示例不发布 8081。通信校验集群 ID 和至少 32 字节的共享令牌，HTTP 传输本身不加密。跨不可信网络需使用受保护的网络或 TLS 隧道。节点的数据目录和 Raft 日志属于同一副本，不要单独复制其中一部分。

| 环境变量 | 含义 |
| --- | --- |
| `GRAPHDB_RAFT_NODE_ID` | 非零节点 ID；设置后启用 HA |
| `GRAPHDB_RAFT_CLUSTER_ID` | 稳定集群身份 |
| `GRAPHDB_RAFT_ADDR` | 独立的 Raft `host:port` 监听器 |
| `GRAPHDB_RAFT_PEERS` | 节点 ID 到私有 HTTP origin 的 JSON 对象 |
| `GRAPHDB_RAFT_TOKEN` | 所有节点相同的通信令牌 |
| `GRAPHDB_RAFT_DIR` | 默认数据目录下 `.graphdb-raft` |
| `GRAPHDB_RAFT_BOOTSTRAP` | 初始三个投票节点为 `true`；新替换节点为 `false` |
| `GRAPHDB_RAFT_TICK` | 默认 `100ms`，同时为心跳间隔 |
| `GRAPHDB_RAFT_ELECTION_TICKS` | 默认 `30`，范围 `2–1000`；Follower 在 30–59 个 tick 后发起选举，即默认约 3–6 秒 |
| `GRAPHDB_RAFT_SNAPSHOT_ENTRIES` | 默认每 1000 条应用日志创建快照；成员变更强制更新快照 |
| `GRAPHDB_RAFT_MAX_SNAPSHOT_BYTES` | 默认 `512MiB`，限制复制快照（含传输封装）和安装后的展开数据量 |
| `GRAPHDB_RAFT_ALLOW_LEGACY_PROTOCOL` | 默认 `false`；仅已验证来源的首次桥接暂设 `true`，全组升级后逐个重启关闭 |

HA 下离线修改命令拒绝启动；数据目录也拒绝绕过 Raft 的普通写入。副本首次加入时即持久化复制模式标记，因此即使 Raft 日志存放在其他目录、尚未应用日志，删除 Raft 环境变量也不能以单机模式打开副本目录。已有单机目录不需要新增配置或模式标记。跨模式迁移通过 API 导入或备份恢复到新目录完成。所有副本需使用影响编码、限额及业务语义一致的配置。跨版本混部仅限 [滚动升级兼容窗口](raft-rolling-upgrade.zh-CN.md#兼容窗口)。

## 成功、重试和读取

- direct 请求在多数派持久化日志、Leader 发布本地图版本后返回成功。
- WAL `202` 返回 `durability=raft_majority`：内容、身份和租户代次已多数派持久化。独立本机 ingest WAL 不再启用。Leader 将明确的请求列表写入 `flush` 日志后合批发布；新主继续处理受理队列。
- 受理队列使用 `GRAPHDB_INGEST_QUEUE_MEMORY_MAX_BYTES` 作为未完成请求的字节预算；Raft 还限制等待提案及未应用日志积压。超出预算返回可重试错误。
- 协议 7 home group 可通过 `GRAPHDB_PARTITION_INGEST_RECEIPT_RETENTION` 为新分片批次启用[终态回执保留期](partition-wal-ingestion.zh-CN.md#终态回执保留期)，默认 `0s`。
- 请求断开或超时仍可能提交。使用相同幂等键重试，并通过状态接口核对；同一身份的不同内容会产生冲突。
- 普通查询在 `ReadIndex` 多数派确认后等待本地应用，随后固定读取范围。Follower 转发到当前 Leader 执行，不能联系多数派的隔离节点返回 `503`；响应的 `X-GraphDB-Leader-ID` 是发现提示，客户端应重试高可用入口。
- `/v1/health` 返回 Raft 节点 ID、Leader ID、term、提交与应用位置、应用积压条数、当前应用缓冲字节、待响应提案字节和错误。`application_entries` 和 `application_commits` 分别统计本进程成功应用的日志条数与本地应用事务数，可用增量观察合并程度；重启后计数重置。`/v1/readiness` 是节点流量准入依据；判断 Leader 使用本地健康响应的节点 ID 和 Leader ID。
- 携带 `min_version` 时，保存响应的 `X-GraphDB-Tenant-Generation`，下一次读取传 `X-GraphDB-Read-Generation`。恢复或清除租户后，旧代次请求返回 `409 tenant_generation_changed`，避免相同版本数字被误用。
- 分页游标保留逻辑版本、排序位置和租户代次。接管节点无法提供游标绑定的本地 catalog 时，现有游标校验明确报错，客户端重新开始扫描。

## 快照、任务和 S3

Raft 日志和投票状态使用 bbolt 原子事务持久化。选举等待与心跳频率可独立调整；默认等待从 10 个 tick 调整为 30 个 tick，以容忍维护期间秒级磁盘同步长尾。较长等待也会延长异常失主后的检测时间，不保证 3 秒内接管；全组建议保持相同配置，并按实际磁盘、网络长尾和恢复目标验收。正常复制携带逻辑请求及 Leader 决定的 ID、时间、合批列表；每个节点自行生成图存储文件。Raft 的心跳/传输与图应用使用不同执行循环，慢应用不会占用心跳执行队列。每个远端副本的日志追加/快照与心跳/选主/响应分别使用独立的有界发送队列，避免慢数据传输阻塞多数派探测；消息跨队列可乱序，仍由 Raft 核验 term、index 及提交位置。应用仍按日志顺序执行。待应用工作只保留日志位置，负载从 bbolt 按最多 4MiB 的窗口读取（单条较大的日志仍完整读取）；启动不再把全部日志载入内存。普通图查询、扫描和导出固定本地读取视图后释放应用锁，普通提交及 WAL 合批可以同时推进。租户替换、归属切换和其他结构变更仍等待已有读取结束。运行中查询的列举与取消属于本进程，不经过 Raft 读取屏障或应用锁。

复制快照包含图文件、租户代次、已受理请求、幂等记录、任务、已应用位置和成员地址。创建快照时逐文件流式读取。安装时先解压到临时磁盘，完整校验摘要、压缩归档、文件路径和大小后，再通过应用事务发布。安装期间不提供正常图服务，查询取消仍可进入本进程。默认使用格式 2 在磁盘生成并传输归档，按远端能力回退。回退时，当前版本从磁盘归档分段编码为格式 1 的 JSON/Base64，接收大内联消息时分段解码到暂存文件。旧程序接收格式 1 仍可能需要完整内存缓冲。两种格式都受字节预算限制，图解码和单对象事务回滚仍可能需要内存，配置和运维边界见[产品运维](product-operations.zh-CN.md)。应用日志在修改文件前持久化旧内容。崩溃后回滚不完整应用再重放，已完成提交不重复增加版本。

应用事务的回滚日志允许不同对象并行准备旧内容，并合并最多 8 个并发记录，配置的合并延迟为 100 微秒。串行记录直接提交，同一对象的后续修改复用已持久化的第一份旧内容。每个对象仍在回滚记录持久化成功后才修改文件；文件和目录同步、最终提交标记保持原有顺序。该优化不改变磁盘格式或多数派语义，单机写入路径保持不变。三、五副本性能和并行崩溃恢复结果见 [补充验收](raft-ha-validation.zh-CN.md#回滚日志合并补充验收)。

准备维护的最终发布会先分批记录全部改写和删除对象的旧内容，每批最多 4096 个对象或约 16MiB（单个更大对象仍需完整旧内容），每批持久化成功后才开始修改任何文件。较小文件可以共用一次回滚日志事务，减少 GC 发布期间的同步次数；后续改写复用这些记录。最终文件、目录和提交标记的持久化顺序保持不变，回滚记录格式不变。进程中断时完整恢复已改写、删除及新建对象，checkpoint 不前进。该批次与最多 64 个编码任务的文件写入队列独立，只作用于 Raft 准备维护，不改变单机路径。

压缩和索引重建捕获文件时，若写缓存与权威 manifest 的读取集合及 ETag 完全一致，独立维护构建复用这份不可变图，避免每次准备重新装载快照和重放提交尾。缓存缺失或身份不匹配时仍从捕获文件装载。后续写入不修改已捕获的图；最终发布仍核验维护 token，过期输入不会覆盖新提交。

准备维护模式下，索引重建完成后由独立 GC 任务清理孤立文件。索引重建发布包仅传输改写对象，因此在临时构建目录里执行删除并不能清理正式副本；独立 GC 的删除列表才会复制到各节点。单机及旧协议的索引重建保留既有清理流程。

已经多数派提交、操作类型相同的连续发布日志，每次最多 8 条共用一个本地应用事务，直接消费已有日志窗口，不等待凑批。命令仍逐条执行，各自保留 ID、时间、版本、WAL 受理位置和响应；整个事务及最后一个应用位置持久化成功后才确认请求。WAL 受理与图发布分别合并，受理确认不等待同一窗口中的后续 flush。批次中途失败或进程退出时，恢复完整旧状态，再按持久日志重放。成员配置、空日志、任务、租户替换和归属变更分别构成合并边界。日志、快照和 checkpoint 的磁盘编码保持兼容；升级按已验证的版本窗口执行。

连续应用合并的三、五副本混合吞吐、崩溃恢复和单机/分片共存结果见 [吞吐补充验收](raft-ha-validation.zh-CN.md#连续日志应用吞吐补充验收)。

命令执行过程中若节点关闭或应用上下文被取消，即使处理层将取消转换成 HTTP 超时响应，应用事务也会回滚、保持原来的 checkpoint，重开后从已提交日志重放。取消响应不会被保存为命令的已执行结果。

同一应用事务内，每个对象的重复改写合并为一次最终文件同步，并复用已有执行器、最多以 2 个工作者并发完成。改写之前仍先持久化回滚记录，新对象也记录原先不存在；所有最终文件内容、目录和提交标记依次持久化成功后才确认请求。单机写入继续立即同步。删除对象会移除其待同步记录，租户目录替换会先完成已有文件与目录的同步，避免重命名或硬链接遗漏尚未持久化的数据。最终同步失败时 checkpoint 不前进，重开后恢复旧状态。测量范围及验证结果见 [重复对象同步验收](raft-ha-validation.zh-CN.md#重复对象同步合并补充验收)。

WAL 终态受理记录保留请求 SHA256、接入身份、状态和结果，去掉原始写入 items。普通 WAL 的原幂等身份在对应租户代次有效期间保留。新版可以读取和校验已有完整请求记录。引入该格式之前的旧版不能可靠解释终态摘要，仍需要维护升级。第四轮修复候选已包含该格式，可按本轮滚动窗口桥接。

超过快照预算时保留日志和在线读取，暂停普通写入，并在健康状态中暴露 `snapshot_error`。已发布 2.3.1 需要提高预算后逐节点重启恢复写入；不要删除数据或日志。2.3.4 使非流式和流式路径都每 5 秒独立重试失败的快照，不依赖新提案；在原预算内成功构建并持久化快照后自动恢复写入。2.3.10 候选对快照捕获／构建中的普通 I/O 错误也保留此行为，临时文件写失败不会关闭副本；日志、已发布快照的持久化和恢复错误仍停止节点。若数据持续超过配置预算，拒写仍会保留，调大静态配置仍需逐节点重启。

后续未发布源码增加持续快照故障的受控让位：保留每 5 秒重试；连续失败至少 30 秒后，在独立维护 worker 中尝试转移领导权，同一故障的尝试间隔至少 30 秒。目标必须是近期活跃的投票副本，已复制并应用本次固定提交屏障，没有快照或节点错误，也未 Drain；其已持久化快照位置必须覆盖本地首次失败的捕获位置。配置联合变更期间不转移，发送转移前重新检查任期、成员和故障是否仍存在。

候选快照尚未覆盖该位置时，Leader 通过经 Raft token 与集群身份认证的 `POST /raft/snapshot/probe` 请求候选立即生成覆盖固定提交屏障的快照，不再等待默认 1000 条日志阈值。候选校验当前 Leader、任期、稳定投票成员、应用进度与 Drain 状态，再交给现有应用／快照构建路径；每节点仅允许一个 probe 请求在途。每个候选使用独立的有界探测期限，慢候选不会耗尽其他健康副本的探测机会。取消退出 HTTP 等待，已捕获的构建仍按原有单构建与资源释放规则完成。Leader 收到成功后再次读取候选状态，确认快照确已持久化且副本仍健康才让位。旧副本不支持此接口、构建超时或失败时保留拒写与重试，不放宽快照证明。

没有合格副本时继续拒写并保留强读及日志，不关闭节点、不强制选举。共同磁盘不足、预算不足、追赶未完成或缺失快照状态的副本不会成为自动让位目标；这些情况仍须恢复容量或修复副本。成功本地快照或安装新快照后清除故障计时。后台构建在发送完成结果前关闭捕获源，执行 checkpoint 清理并释放其读视图；取消后的探测不能在旧源仍未释放时启动下一次捕获。Raft 持久化／恢复错误仍按原策略停止节点。此机制不改变快照网络格式和写入协议。

已持久化快照的旧文件清理独立在后台执行，不占用 Raft 控制循环或存储读锁。清理失败通过 `snapshot_cleanup_error` 和诊断指标告警，每 5 秒重试；节点仍可复制、读取、写入和重启。清理队列只保留最新任务，并保留尚未应用完成的旧快照文件。日志、快照元数据和确认消息的持久化顺序保持原有要求。 读写入口从持久化提交位置检查应用积压，处理提交/应用位置交错采样，避免同步状态查询阻塞请求取消。强读仍执行 ReadIndex、多数派确认和本地应用屏障。周期诊断使用带年龄的后台状态采样；实时健康和控制接口的语义保持不变。

2.3.4 起：发送时发现旧快照文件已被清理，会向 Raft 报告 SnapshotFailure 并等待重试；其他快照读取/完整性错误仍保留原有故障语义。成员移除或安装含移除记录的快照时，取消其发送循环并回收排队的文件句柄。

集群任务的排队和执行均有日志记录，切主后继续处理排队任务。2.3.4 使准备阶段的对象存储不可用、网络错误、超时、HTTP 429/5xx 保持排队，交由下一轮公平调度重试；确定的无效输入仍记录为任务失败。这不改变已提交命令应用失败时的回滚和停止语义。维护任务通过集群接口执行，首版不启用单机定时维护循环。任务执行和快照占用本地应用阶段，新查询和新写入可能等待；生产维护长尾需要单独测量。

快照捕获以共享应用锁固定不可变文件，允许读取并排除日志应用。每个目录只验证、创建一次，文件仍逐个硬链接并检查大小。校验、压缩在捕获后执行。2.3.10 候选起，默认路径也复用捕获后的后台文件构建，Raft 持久化循环只保存小型文件描述符。接收端在 HTTP worker 中持久化内联负载，再交给 Raft。该候选当时仍默认使用格式 1。默认快照间隔为 1000 条日志。

Raft 持久化的最低协议升至 13 后，本地生成的归档描述符复用压缩时写入前缀的 SHA-256。封装时校验前缀并同步文件和目录。接收、重启和恢复时按描述符校验归档。协议 12 及更早版本的描述符记录整份文件的 SHA-256，两种描述符均可读取。

快照安装通过校验后，同文件系统内将暂存文件原子重命名到目标位置，跨文件系统的目标继续流式复制。两种路径均由复制事务记录旧文件，并在提交检查点之前同步数据及其目录。

准备式维护仍校验完整的租户基础状态，不会将过期索引或旧图发布到新版本。捕获阶段按目录复用路径检查；传输阶段先确认首块清单，随后最多并发复制 4 个 1MiB 块，让连续的分块日志使用已有应用事务合并。全部分块确认后才提交发布命令，每个副本继续检查完整大小和 SHA256。错误或取消时等待已启动的传输调用退出，不发布未完成输入；切主后仍按固定摘要和块内容恢复传输。该变化作用于传输阶段，不改变整个图变化时的准备冲突与重试规则；本轮尚未单独量化端到端维护收益。捕获测量和可用性、吞吐资格的待验收边界见[本轮优化验收](performance-raft-batching-2026-10-04.zh-CN.md)。

S3 继续使用现有 `GRAPHDB_BACKUP_S3_*` 配置。手动对象备份先复制并固定捕获结果，只有 Leader 上传和校验，再复制任务完成结果；稳定任务 ID 允许切主重试同一上传。租户恢复由 Leader 下载、校验完整内容，以每块最多 1MiB 的日志复制到各副本的暂存目录，最后复制恢复发布命令。每个副本先检查所有块的大小和完整 SHA256，再执行原有恢复事务并发布新代次；成功、准备失败或取消时清理暂存。持久化块损坏时拒绝应用、保留 checkpoint 和错误证据，需要按副本故障处理。换主可以按任务身份和固定摘要续传，已经持久化的相同块不用重传；输入完整复制后不再依赖原备份源。租户清空或替换后旧恢复失效，不能把旧数据写回新代次。Follower 不在应用时下载 S3。旧的单条恢复日志仍能被新版读取。

后台命令准备完成后，任务可能被清除或 GC 移除。应用时发现任务已不存在，会以业务冲突消费该日志并清理对应恢复暂存，继续推进 checkpoint。分片 WAL 发布也核对当前归属状态和代次，迁移或取消后过期的发布命令不能读取已清理的源数据。任务内容损坏、当前归属下的受理记录缺失和实际存储错误仍按副本故障处理。回归证据见 [第三轮审核](raft-p0-p1-review3-2026-10-02.zh-CN.md)。

任务执行中的本地对象读取、读取准入、缓存和流式 I/O 错误纳入复制事务，不能被转换为任务失败后继续推进 checkpoint。Raft 受理导入时保存原始源摘要，Leader 核对后将 SHA256 写入执行日志；副本上的源缺失或变化使该副本回滚并停止应用。Leader 准备阶段发现源无效或变化时保存一致失败，不发布图数据。旧任务或执行日志没有源摘要时保留相应旧语义，不回溯补写证明。可选对象不存在与正常 EOF 不影响提交，单机任务保留原有错误语义。回归证据见 [第四轮审核](raft-p0-p1-review4-2026-10-02.zh-CN.md)。

已发布 manifest 引用的 commit、提交段和快照对象属于必需数据；其缺失、解码或身份校验失败同样使复制事务回滚，不能作为普通维护任务失败消费日志。manifest 自身解码失败也纳入事务。修复故障或按运维流程重建副本后，再从保留的日志位置重放。S3 恢复重新准备输入时，校验报告时间固定为任务受理时间，使切主后的传输摘要保持相同；单机校验仍记录实际检查时间。新回归及已有异常任务的处理见 [产品 P0/P1 审核](product-p0-p1-review-2026-10-03.zh-CN.md)。

分块恢复解除整份备份必须装入单条 32MiB 提案的限制，但不是无限容量恢复。准备和解码仍在内存中构建完整备份/图；暂存块也计入整个组的快照预算。开始传输前检查现有文件、输入和归档开销是否能装入 `GRAPHDB_RAFT_MAX_SNAPSHOT_BYTES`，预算不足则让任务明确失败。执行期间仍需为其他写入、快照、旧图和恢复临时目录预留内存与磁盘空间。各副本必须使用相同预算，不能仅调大 Leader 的配置。

HA 首版暂不支持自动备份策略；启用请求明确报错。可由外部调度调用集群手动备份接口。手动恢复演练需提供明确的 `backup_key`。维护清理可以令此前保留的分页游标过期，客户端需要重新开始扫描。

## 安全替换节点与滚动升级

协议 13 使用原始 JSON 承载应用命令，并为普通 HA 的 WAL 受理和发布持久化待决索引。可先以集群当前协议替换二进制，再在同一 Raft 组的全部副本上显式设置 `GRAPHDB_RAFT_PROTOCOL_VERSION=13`。旧检查点缺少队列索引时仍从受理记录重建。

非分片 HA 在租户侧批次回执中保存原受理 LSN、租户代次和请求摘要，并在同一条 Raft 应用事务中回收对应的终态控制文件。查询和原批次重试读取同一份终态结果。集群升级后由 Leader 分批迁移可核实的历史回执。无法证明结果一致的历史记录，以及由其他批次的幂等结果生成的回执，继续使用原有控制记录。快照超出预算时仍可提交这一回收操作。分片回执保留时间继续由 `GRAPHDB_PARTITION_INGEST_RECEIPT_RETENTION` 控制。

协议 13 的非分片 HA 将新绑定的 WAL 回执保存为稀疏 Parquet。整列为默认值的字段在磁盘上省略，读取时补齐原类型和默认值，再检查原有内容摘要。新版本同时读取完整列和稀疏回执。恢复含稀疏回执的备份需要支持该布局的版本。租户分片继续沿用原有 Parquet 列布局。

非分片 HA 和按租户分片的普通 WAL 可在数据组的所有副本设置 `GRAPHDB_HA_INGEST_RECEIPT_RETENTION`，为协议 13 新受理的批次启用[终态回执保留期](user/write-ingest.zh-CN.md)。启用后，后台按终态期限分批回收接入回执及属于同一受理位置的租户侧批次记录和幂等别名。回收使用同一 Raft 应用事务，快照超限时仍可进行。配置默认 `0s`。更改配置只影响随后新受理的批次。

复制应用仅在未写入对象、未创建待同步目录且上一条提交标记仍完整时，才会在业务拒绝后保留已打开的 journal。成功应用及有写入的失败沿用原有持久化或回滚步骤。

兼容的内联 Raft 通道每个节点同时接收一条超过 2 MiB 或长度未知的消息。正常的小消息和心跳可并行处理。流式快照入口沿用独立的接收额度。

强读会合并同一等待窗口内已到达的请求，提交一次 ReadIndex，并各自等待该索引应用。已提交的轮次不再接纳新的读请求，因此稍后到达的读会等待新的多数派确认。单个请求取消时，其他请求可继续等待。`graphdb_raft_events_total{event="read_index_round"}` 统计本节点提交的确认轮次。

普通 HA 写入由 Leader 直接提交提案。物化分片写入与原生分片 WAL 受理在 Leader 的本地路由和图模式允许时直接提案，应用时按日志顺序复核归属、图模式和代次。本地路由无法确认时，先用 ReadIndex 确认多数派并等待读取位置应用。原生分片提交在开始事务时复用同一请求已确认的图描述符。与当前状态冲突时重新获取描述符。事务动作通过本地范围校验后提交 Raft，应用时复核事务序号、分片 epoch、根及当前决策。幂等查询及从持久化记录恢复事务仍使用强读。

Raft 管理接口位于私有 Raft 监听器，请求必须携带 `Authorization: Bearer <令牌>` 和 `X-Raft-Cluster: <集群 ID>`。

1. 用新的 ID、空目录、完整当前成员地址启动替换节点，`GRAPHDB_RAFT_BOOTSTRAP=false`。
2. 向当前 Leader `POST /raft/members`，请求 `{"action":"add_learner","id":4,"url":"http://node4:8081"}`。
3. 等待新节点追赶，再请求 `{"action":"promote","id":4}`。尚未追赶完成返回 `409`。
4. 请求 `{"action":"remove","id":旧节点ID}`。移除后 ID 永久保留，不能复用；保持至少三个投票副本。
5. 停止旧节点。新节点会从包含其成员配置的快照及后续日志恢复。

成员变更在多数派提交后，按日志顺序核对受理时的成员配置；在生效检查中发现配置已变化时返回 `409`，不会覆盖已有节点地址或突破至少三个投票副本的限制。`204` 表示该请求对应的配置和通信地址已经在当前节点持久化。遇到超时或切主返回错误时，先查询当前 Leader 的状态，再按最新配置决定是否重试；不能从旧 Leader 的空进度列表判断移除成功。成员变更应逐项执行。

使用 `GET /raft/upgrade` 检查全组，`POST /raft/drain` 等待已有提案完成并交接 Leader；一次只替换一个副本，追赶后再继续。跨版本仅支持已做双版本验收的兼容窗口；第四轮修复候选可首次桥接到本轮协议 1，完成后关闭 legacy 通信。更早程序的维护升级限制仍保留。分片入口提供双 router 和摘流接口。步骤、协调脚本及回退边界见 [滚动升级手册](raft-rolling-upgrade.zh-CN.md)。丢失多数副本时停止写入，不通过重新 bootstrap 残存目录强行组成新集群。

## 未发布的审查修正

普通读取不再持有 Application 状态锁直到 HTTP 返回。图发布、查询模板保存、分区事务的暂存与决策、发放读租约以及回收未认领的事务输入可以与不可变读视图并行。分区提交发布新根，先前固定的视图继续使用自己的根。目录替换、图页回收和结构控制操作先等待读取释放屏障，超过排空期限会取消尚未结束的读取并打断阻塞的响应写入。被取消的读取需要重新发起。扫描和快照流会在分段写入时刷新写期限。触发维护读排空后，Raft 的响应中断期限优先。已提交复制命令不使用单机写入的本地90秒超时，父上下文取消仍使应用回滚。未分类5xx/408/499以及非配额429不记为已拒绝 checkpoint。由复制配置与状态决定的 quota_exceeded429仍是确定性业务拒绝。

WAL 发布每轮公平处理不同租户，一个租户背压不会阻止其他租户。达到批量上限会唤醒发布，部分批次保留原定时周期。请求体上限与单机统一为 32 MiB，非超限读取错误不会伪装成 413。MaxSnapshotBytes 按原始状态计算，Base64 及有界元数据另算传输预算。默认启用流式快照，旧副本仍受自身接收实现限制。目录恢复复用 4096 对象、约 16 MiB 的旧内容日志批次，在修改前持久化并保留崩溃回滚。

协议 13 下，普通 HA 和按租户分片的 data group 在启动及租户代次变化后分批检查普通 WAL 控制回执。应用每批 Raft 清理时重新核对当前代次，回收已失效的旧代回执，并同步更新待处理队列。大图分片回执按各自的图代次和保留策略管理。快照超过预算期间，有权限的调用方仍可按原有租户生命周期条件提交硬清除。清除与旧代回执回收生效后，集群在同一预算内生成并持久化快照即可恢复写入。

大图分片在快照超出字节预算期间允许结束已有事务和运行有界图 GC。数据组经过强读屏障后可按原请求返回已经持久化的准备结果。home 继续校验事务身份、序号、基线及参与分区，准备结果齐全时才发布。数据组按原有校验完成单分区或批量收尾。GC 沿用读取保留边界，只回收过期视图、未认领输入和不可达的图页。新事务及需要生成页的准备须等合规快照持久化后恢复。其他快照错误由常规保护处理。

home 和该图的全部数据组启用协议 13 时，准备阶段因快照超限无法继续的事务可自动启动恢复 GC。事务、暂存输入和已受理 WAL 继续保留。GC 保护已发布根、仍有效的固定读取视图及已准备分区的根，运行期间暂停原事务发布，结束后以原事务序号恢复。每个事务自动完成一轮。若活跃数据或仍在保留期的视图继续超出预算，事务保持待决，可在有可回收空间时通过原图 GC 接口再运行一轮。

Raft 提案允许最多64MiB的编码负载，保留64MiB的在途提案总预算，以容纳32MiB HTTP请求经过两层 JSON/base64封装后的大小；单条最大请求会占用大部分在途预算。消息接收预算同时覆盖该提案上限，与快照原始状态预算分开。提交后超时或失去可用性的响应为 write_outcome_unknown、retryable=false；已转发写请求的响应丢失同样不能盲目重放。通过批次状态或原幂等身份核对。旧入口仍受自身旧版限制。

保存 Raft 日志前先从完整条目解析最低协议，再获取存储锁。最低协议仍与对应日志或快照元数据一起提交到 Bolt，重启读取同一个协议门槛。

协议 13 的复制应用可将最新检查点保留在小型回滚日志的已同步提交标记中。对象及其目录同步完成后才写该标记。下一批首组前镜像与上一检查点一起落盘，崩溃恢复可同时还原两者。日志超过复用上限时先发布 `checkpoint.json` 再回收日志。旧协议沿用逐批发布文件的方式。旧程序会拒绝恢复带有这种回滚检查点的中断应用，先使用支持该格式的版本恢复副本。

### 2.4.3 读排空与转发修正

控制操作保留一秒读排空窗口。读处理器完成时先注销中断回调，再释放读屏障。超过窗口时，Raft 取消仍在运行的读取。如果响应尚未开始写入，服务返回完整的 JSON 错误 `503 raft_unavailable`，附带 `retryable: true` 和 `Retry-After: 1`。已经开始写入的响应最多再等待一秒，流式处理器不得延长这个期限。维护打断已开始的 NDJSON 响应时，服务中止该 HTTP 响应。客户端应丢弃未完成的流，并重新发起读取。

Follower 转发写请求时保留负载和幂等请求头，但禁止 HTTP Transport 在丢失响应后隐式重放，包括无请求体的维护操作。单独携带 `Idempotency-Key` 或 `X-Idempotency-Key` 不代表每个管理接口都有去重契约；结果未知时先查询状态，仅在接口明确支持的情况下复用业务幂等身份重试。修复与回归证据见[相邻路径复审](review-v2.4.2-adjacent-2026-10-26.zh-CN.md)。这些修正包含在 2.4.3 中，旧 v2.4.2 资产保持不变。
