## 实现范围

单进程独占本地目录，以现有租户锁处理并发写入。服务和离线 CLI 均取得目录锁，
保留 Parquet/WAL 格式、同步持久化和现有租户目录布局。云存储及 PostgreSQL 后端实现和 SDK
依赖已移除，远端存储、独立 reader/writer 和 PostgreSQL 配置明确报错。

文件发布限制每组 64 项、4 个写入工作线程，先同步数据文件，再重命名和同步目录，最后发布
manifest/catalog；这不是多文件原子事务。随机文件读取覆盖实体页、边分片、索引、快照和
备份/任务结果。进程内发布通知替代磁盘轮询，活跃读视图保护 GC、清理、清空及恢复期间的文件。

元数据缓存有容量边界，以文件写入代次失效。manifest 缓存未命中时直接读取磁盘文件，
防止发布前开始的字节缓存或共享读取在发布后返回旧 head。并发回归分别验证了发布代次变化、
延迟旧读取及元数据缓存淘汰后的行为。

## 本次性能抽查方法

执行 `scripts/local_disk_compare.sh`，由 `scripts/local_disk_benchmark.py` 驱动既有负载工具。
`scripts/local_disk_report.py` 保留原始统计，不从历史短流程挑选结果。

本次只比较 10 万实体 direct 混合读写的原本地模式和新本地实现，各执行一次。
WAL、对象存储和 1 万实体的早期短流程用于校验测试工具；它们不纳入本次结果表。
WAL 的功能与后台维护并发由最终 30 分钟持续负载覆盖。

```sh
GRAPHDB_BENCH_RUN_ID=local-disk-v2-focused-20260916 \
  scripts/local_disk_compare.sh --entities 100002 --cases main-local new-local \
  --modes direct --warmup 10 --measure 60 --maintenance-seconds 0 \
  --cold-samples 5 --repeats 1
```

| 项目 | 固定设置 |
| --- | --- |
| 两个比较组 | 基线 local、新版 local |
| 数据 | 100,002 个实体，固定生成逻辑与确定性请求序列 |
| 写入模式 | direct，同步落盘 |
| 混合负载 | 4 个写入客户端、16 个查询客户端，每批 20 个实体更新 |
| 时间 | 混合负载预热 10 秒、测量 60 秒；维护序列各执行一次预热和采样 |
| 重复 | 单轮、两场；不估计重复间波动 |
| 冷读取 | 每场 5 次进程重启后的首次查询，另记录启动到 ready 时间 |
| GraphDB 容器 | 8 CPU、8 GiB 内存；负载客户端在同一容器 |
| 存储 | 独立 Linux 命名卷，两组使用相同容器资源限制 |
| 图缓存 | 每组 reader / writer graph cache 各 512 MiB |
| 写入排队 | 所有组均 60 秒；排队时间计入写入延迟 |
| reader catch-up | 所有组均 120 秒，避免默认 2 秒截断大型冷导出 |
| HTTP 客户端超时 | 120 秒；可重试的 429 按 Retry-After 等待 |

每个实际写入批次都改变未索引的 `loadtest_revision` 字段，预热和测量使用不同确定性代次。
成功批次数必须等于 graph version 增量；背压响应单独计数，不能充当已发布吞吐。
WAL 读可见延迟包含终态确认、10 ms 轮询和一次成功的 `min_version` 读取，
因此是首次可读时间的上界。

维护序列先提交真实变更，再执行导出、compact、备份、覆盖恢复和恢复后完整导出相等检查。
恢复后遇到索引重建背压时等待，保留等待时间和重试次数。操作次数较少时，维护 p95/p99
只是顺序统计量，不能视作精确尾部估计。

记录发布吞吐、混合操作吞吐、各操作 p50/p95/p99、GraphDB 进程 CPU/RSS、磁盘读写、
fsync 次数和文件句柄峰值。RSS 使用进程高水位，覆盖预置数据、混合负载和维护阶段。
基线仅增加相同的 fsync 观察计数，业务实现仍为指定 commit。

## 结果解释与测量边界

本次是单轮抽查，不能估计重复间波动，也不能验证原方案的整体性能门槛。
报告提供实际吞吐、延迟和资源差异，不把单轮差异解释为稳定提升或回退。
完整工具仍支持三轮矩阵以及 10% 吞吐/冷读改善、5% 尾延迟回退、10% RSS 增长门槛，
但本次不运行这些完整验收项目。

- 进程冷启动与操作系统页缓存分别说明：本次不清空全局页缓存，不影响其他 OrbStack 工作负载。
- 本次两组均使用本地文件，不启动 MinIO；资源计数覆盖 GraphDB 进程。
- 当前 OrbStack 还承载用户其他工作负载；不停止这些服务，保留系统负载采样；单轮结果不能排除共享环境的干扰。
- 预热前重新创建每场数据目录；原始 Linux 卷、请求统计、日志、二进制哈希和源码归档保留。
- 早期短流程、客户端 30 秒超时的中止运行，以及缓存修复前的结果不作为最终性能证据。

## 抽查结果

两场均成功完成，写入版本增量分别为 11 和 9，与成功批次数完全相等；查询、扫描、恢复及重启校验均无错误。

| 指标 | 原本地模式 | 新本地实现 | 样本差异 |
| --- | ---: | ---: | ---: |
| 混合操作吞吐 | 393.79 次/秒 | 404.80 次/秒 | +2.8% |
| 已发布写入吞吐 | 0.161 批/秒 | 0.119 批/秒 | -25.7% |
| 写入 p95 | 47.19 秒 | 52.19 秒 | +10.6% |
| match 查询 p95 | 63.13 ms | 69.29 ms | +9.7% |
| min_version 查询 p95 | 60.64 ms | 69.81 ms | +15.1% |
| scan p95 | 106.07 ms | 94.56 ms | -10.8% |
| 进程冷读 p95（每组 5 次，等于最大值） | 154.52 ms | 366.47 ms | +137.2% |
| 混合阶段 RSS 峰值 | 3070.95 MiB | 2531.50 MiB | -17.6% |
| 全流程 RSS 高水位 | 5508.67 MiB | 5295.60 MiB | -3.9% |

冷读中位数为 143.28 → 257.33 ms。基线/新版测量阶段分别出现 29/36 次可重试背压响应，等待计入写入延迟；每场仅完成 11/9 批写入，因此写入 p95/p99 都是小样本最大值。

这些数据不支持“整体性能提升”的结论。新版在此样本中的内存使用较低，
但没有消除索引重建背压和写入排队；冷读耗时较高的具体 CPU/I/O 原因尚未剖析。
保留当前实现和证据，未继续增加对比轮次，也未将较差的样本隐藏或替换。

### 执行环境暂停

基线维护阶段出现 29769.7 秒的采样间隔（约 8 小时 16 分钟）。
容器实际运行时间没有同步增加，表明环境暂停/恢复影响了墙上时间。该阶段的资源 elapsed 和
CPU 平均值以墙上时间计算，不能用于有效工作时的性能比较；本报告不比较这部分维护资源耗时。
原始统计保留不变，并附单独的环境说明。两个混合测量阶段的最大采样间隔均小于 0.53 秒，
各自没有跨暂停；但它们位于暂停前后，且每组只运行一次，仍无法排除共享环境变化。
