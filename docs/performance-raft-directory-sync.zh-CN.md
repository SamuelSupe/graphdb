# Raft 目录同步合并与性能复测

日期：2026-10-01（Asia/Singapore）。基线 `e0f6e937`，独立 worktree `GraphDB-raft-ha`，分支 `codex/raft-ha`。

## 结论

本次减少了复制应用的重复目录同步。最终五副本 WAL 混合负载的两轮发布吞吐观察到 +24.0% / +18.7%，读取 +30.6% / +10.7%，发布 p95 下降 25.6% / 41.8%；每个发布批次的文件与目录同步次数稳定减少约 16.5%。这组结果来自短时、同机的小图测试。

三副本仍有明显回退，不能宣称整体读写性能已经稳定提升。混合直写第二轮发布吞吐 −41.0%、读取 −36.8%、发布 p99 +114.1%，同期相同基线的发布吞吐差异为 11.8%；混合 WAL 第一轮也出现 −29.4% 发布吞吐和读取尾延迟变差。不能把这些回退全部归为环境噪声，也不能用五副本的收益覆盖它们。当前保留的是减少同步操作的实现与有边界的测量证据，不构成三副本性能保证或生产容量结论。

所有最终性能窗口请求错误、观测到的同步失败均为 0，发布次数与版本增长一致，查询 `min_version` 校验通过。单机、单组 Raft、租户分片扩容与迁移继续通过运行验收。

## 实现与持久化边界

每次复制应用记录需要同步的目录：文件改名、删除，以及新建目录的父目录。重复路径合并，所有目录屏障完成后，才能持久化该应用的提交标记并推进 checkpoint。

首次修改对象前，回滚旧内容仍逐对象写入并同步到 bbolt；文件内容仍逐文件同步。中途退出时先恢复旧内容，再重放日志。新建空目录可以在回滚后留下，未提交的文件会被删除，应用位置不能提前增长。应用日志、checkpoint 与复制快照的格式保持兼容，多数派确认与 `ReadOnlySafe` 屏障继续执行。

目录记录使用独立的短临界区，避免等待其他文件的回滚日志 I/O；复制应用使用自己的目录集合，文件改名与删除不再争用单机批写的全局发布锁。恢复或迁移替换整个租户目录前，先完成此前的目录屏障，避免稍后同步已消失的旧路径。路径范围、目录类型与符号链接检查继续执行。单机、回滚和恢复暂存目录使用即时目录屏障。

## 测量方法

- OrbStack Linux aarch64、Go 1.26.7，主程序和微基准均使用 `CGO_ENABLED=0`；容器限制 8 CPU / 8 GiB，每个服务进程 `GOMAXPROCS=2`。主机仍有其他工作负载。
- 各变体使用独立的新 Linux 数据目录与真实 HTTP 通信。五副本在三个投票节点基础上加入并提升两个 learner，然后重新打开五个投票节点进行测量。
- 固定 1,002 个实体，每批 20 组 host/service，即 40 个实体和 20 条边。4 个写者；混合场景另有 16 个读者。预热 3 秒，测量 20 秒，尾部请求完成后计算实际耗时；每个场景两轮。
- 最终集群测量把优化版本夹在两个相同基线之间，第二轮反转顺序。A/A 差异定义为两个基线的绝对差除以其均值。吞吐变化与同轮两个基线的均值比较，不跨场景平均。
- 同步计数来自所有数据副本的 `graphdb_disk_sync_total`，包含 FileStore 文件、目录和本机 ingest WAL 的同步；不包含 bbolt 的 Raft 日志与回滚日志同步。HA WAL 使用 Raft，未启用独立本机 ingest WAL。计数在负载前后采样，副本尾部应用的时序会带来少量差异。
- 读取吞吐只汇总 query-match、query-min-version、query-traverse、scan；各操作的 p50/p95/p99 独立保存。CPU/操作包含所有服务进程，除以写入和这四类读取的总完成数；它受负载比例影响。
- 微基准在真实 Linux 文件存储上每次应用写入 16 个 1 KiB 对象，四个子目录，每个对象修改两次。分别复用目录、每次创建新的目录树；每个窗口三个 25 次样本，每轮两个同一基线与一个优化窗口，共 36 个最终样本。它包含本地应用日志、checkpoint 与文件同步，不包含网络复制及多数派等待。

## 最终落盘微基准

每个窗口取三个样本的中位数。耗时变化相对于两个基线窗口的中位数均值；同步次数的减少稳定，复用目录第一轮的耗时没有提升。微基准收益不代表 HTTP 或 Raft 吞吐提升相同比例。

| 路径 / 轮次 | 耗时 ms：基线1 / 基线2 → 优化 | 耗时变动 | 同步次数/应用：基线 → 优化 |
| --- | --- | --- | --- |
| 复用目录 / 1 | 163.8 / 119.2 → 147.5 | +4.2% | 68.24 → 40.12 |
| 复用目录 / 2 | 144.9 / 245.4 → 77.6 | -60.2% | 68.24 → 40.12 |
| 新建目录 / 1 | 237.0 / 103.4 → 60.2 | -64.6% | 73.08 → 42.08 |
| 新建目录 / 2 | 209.8 / 252.2 → 73.1 | -68.4% | 73.08 → 42.08 |

相同基线的微基准耗时也有较大变化：复用目录两轮差异约 31.6% / 51.5%，新建目录约 78.5% / 18.4%。因此优先确认同步次数减少约 41%–42%，耗时数据按轮保留，不能推广为稳定容量指标。

## 验证与实验记录

- 最终版本在 OrbStack 通过完整 storage、HA、config、bootstrap、CLI 包测试，以及 storage、HA、CLI 的 vet；storage 新持久化边界与文件路径/目录切换使用 race，完整 HA 使用 race，均通过。
- 聚焦回归保护：修改中途退出后的旧对象回滚、新层级目录中的文件清除；多个目录的成功对象重启后存在；目录屏障失败不能推进 checkpoint；同一应用内目录替换后恢复正确。现有崩溃测试此前只有单层目录，且没有覆盖延迟屏障失败和目录替换。
- 最终镜像 13 项运行验收全部通过：单机 direct/WAL 与 Raft 同时运行、SIGKILL 恢复、幂等发布、Leader 接管、模式目录保护；新增分片不重映射现有租户、迁移途中中断 catalog 与目标 Leader、迁回原分片、单分片失去多数派时其他组继续服务、取消迁移及分片角色保护。最后一组切主观察值为 6.908 秒，属于当次本机条件，不能作为故障切换承诺。
- 第一个目录合并候选复用了回滚日志的 I/O 锁，纯写首轮吞吐 −33.1%、混合直写 −14.7%。随后使用独立目录锁，且省去全局批写锁；只合并文件改名仍只减少约 2% 的实际纯写同步次数。最终把新建目录的父屏障一起合并。这些早期完成窗口保留在 JSON 中，没有混入最终结果。
- 初次验收镜像因动态链接无法在 Alpine 启动，改为静态构建后重新验证。五副本最初在基线启动阶段出现 `41084` 端口占用，尚未进行测量；原端口位于实际临时端口范围 `32768–60999`。脚本改用范围之外的监听端口，新容器重新完成六个五副本窗口。分片注册的地址同步修正后，另行通过三个 catalog、三个数据副本与 router 的建租户、播种、重启、WAL 混合负载及指标采集验证；这项五秒运行检查没有混入性能对比。

完整数据见 [原始结果](performance-raft-directory-sync-results.json)：24 个最终集群窗口、36 个最终微基准样本、13 项最终运行验收，以及早期完整实验窗口。CPU profile、服务日志与数据目录保存在本机 Linux 卷 `graphdb-raft-next-perf-data`。本次没有验证大图、跨主机/WAN、长期压力、物理断电或远端对象存储性能；目录集合的内存开销也需要在大规模维护负载中另行验证。
