# 多副本读写性能优化

日期：2026-10-01（Asia/Singapore）。基于 `dabaa640`，分支 `codex/raft-ha`，独立 worktree `GraphDB-raft-ha`。默认单机、单组 Raft 和租户分片部署继续共存。

## 瓶颈与改动

基线三副本只读负载的 Leader profile 中，`copyEntityPage` 累积样本约占 20%，它在实体 ID 筛选和字段投影前复制整个页。现在查询 lookup 借用已经验证、不可变的实体页，只在返回所选实体时深拷贝。租户、版本、内容与 schema 校验、远端 ETag 重验证仍然执行；结果中的嵌套字段与缓存隔离。该读取优化也适用于单机。

基线 WAL 混合负载的 Leader CPU profile 中，受理路径约占累积样本 35%，后台 `flushPending` 约占 10%；`accepted` 的记录读取与解码路径共约占 45%，这些路径存在重叠。每次受理检查容量、每次后台发布，都遍历并完整解码全部历史受理记录，包括已经完成的批次。读取与复制应用共享应用锁，因此这种扫描也影响混合负载的读取。

现在使用由应用锁保护的待发布索引，只保留活跃批次的租户、代次、位置及字节数。初次使用从持久化记录建立；受理和发布成功写入记录后维护索引。普通图提交和直接写入不改变受理队列，保留索引，避免后台刷新为重建空队列反复取得独占锁；维护命令、快照恢复和应用失败仍使索引失效。后台刷新用共享锁取得索引副本，冷重建才取得独占锁。恢复、清理和迁移仍从持久化状态重新建立索引，已完成的幂等记录与原请求继续留在磁盘。冷重建仍然遍历历史，本次没有改变历史保留策略。

复制应用日志也有额外同步：同一事务重复修改某个对象时，原来已经保存过它的 before-image，却仍然提交空的 bbolt 写事务。现在用只读事务确认已有 before-image；首次修改仍必须提交并同步 before-image，才能修改对象。新日志的对象 bucket 与首个 before-image 一起创建，省去单独初始化 bucket 的空事务。使用的 bbolt 1.4.3 在初始化数据库时已经同步其初始页，日志文件的目录同步仍然执行；恢复逻辑也继续兼容尚无对象 bucket 的情况。

多数派提交、`ReadOnlySafe` 读取屏障、本地应用等待、文件同步、应用 checkpoint 和幂等语义保持原有要求。没有调整刷新间隔、批次大小、队列预算或快照阈值。单机路径不使用这个待发布索引或复制应用日志。

## 测量方法

- OrbStack Linux aarch64、Go 1.26.7；专用容器限制 8 CPU / 8 GiB，每个服务进程 `GOMAXPROCS=2`，主机同时有其他工作负载。
- 三副本、五副本都使用真实进程、独立 Linux 数据目录及 HTTP 通信。源码与二进制只读挂载，每个变体、场景和轮次使用新目录，复用 `scripts/raft_benchmark.py` 和 `tools/loadtest`。
- 固定 1,002 个实体；每批 20 组 host/service，包含 40 个实体和 20 条边。播种后重启到独立管理端口采集 Leader profile，只读预热后更新固定 host 字段。
- 三副本：8 个读者的只读、4 写者的纯写、4 写者加 16 读者的混合直写与混合 WAL。先完成同一基线二进制的两轮 A/A，15 秒测量、3 秒预热；候选版全部四个场景每轮运行两个相同基线窗口及一个优化窗口，第二轮反转顺序。修正普通图写入的索引失效后，最终版重测受影响的混合直写，均为 20 秒测量、3 秒预热。
- 五副本：通过成员接口在三投票节点基础上加入并提升两个 learner，再测混合 WAL；每轮运行两个相同基线窗口及一个优化窗口，第二轮反转顺序。基线窗口同时作为该拓扑的 A/A，均为 20 秒测量、3 秒预热。
- CPU 和磁盘字节取所有服务进程的 `/proc` 增量，包含服务日志，排除客户端；各操作独立统计 p50/p95/p99，WAL 受理、等待可读和端到端发布分别记录。每轮核对请求错误、发布次数与版本增长、`min_version`。
- 微基准使用同一测试源分别编译基线与最终版本，内存对象存储排除复制网络和磁盘等待。实体页包含 128 个实体，每个新 lookup 读取 8 个实体，分别返回完整数据和字段投影；受理路径保留 1,000 个已完成、1 KiB 请求载荷的历史记录，循环受理新批次并标记完成、移除该临时记录。每个阶段包含两个同一基线窗口，记录耗时、字节分配量及分配次数；该测量不代表实际 Raft 发布性能。

基线二进制 SHA256：`24a1d53af6f77db1c3c66336f88acb76ca061f196d12a981c0035616f48072bf`。

最终优化二进制 SHA256：`2fb6a8f5ca16aa441a2974e3ee472a9d13722e2915e80f9f5cc1dc458eb61000`。

三副本 A/A 相邻吞吐差异：只读 +3.4% / +37.4%，纯写 −10.5% / −8.0%，混合直写 +53.8% / +1.9%，混合 WAL −8.3% / −4.9%。这些波动限制了小幅性能变化的归因，必须保留逐轮结果。

## 测量结果与判断

已确认的是热点步骤的耗时和分配量下降；端到端结果存在收益和回退，不能称为全面提速。所有性能窗口请求错误为 0，发布次数与版本增长一致，`min_version` 验证通过。

微基准取六个基线样本、三个最终版本样本的中位数，单位为每次调用。受理循环包含写入完成记录和清理临时记录，以保持 1,000 条完成历史的固定规模；首次索引重建成本仍然存在，以下耗时是循环摊销后的结果。

| 缓存页批量读取，完整实体 | 267.8 → 66.5 µs（-75.1%） | 303,130 → 64,536（-78.7%） | 1,424 → 271（-81.0%） |
| 缓存页批量读取，字段投影 | 246.6 → 62.1 µs（-74.8%） | 302,680 → 64,088（-78.8%） | 1,408 → 255（-81.9%） |

## 验证范围

性能测量是同机、小图、短时间的闭环负载，不能表示生产容量或跨机网络、故障域。五副本没有单独进行失去两个副本、长时间积压或多热点租户的故障性能验证；分片本轮验证行为，未测迁移中的性能。索引的冷重建、历史记录的空间增长和快照成本仍需在更大、长时间负载下验证。
