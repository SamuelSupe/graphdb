# Raft HA 首版验收记录

日期：2026-10-01（Asia/Singapore）。分支：`codex/raft-ha`。实现基线：GraphDB 2.1.2，`2942a175`。

## 环境与方法

- OrbStack Linux aarch64，Go 1.26.7。
- 三个独立 Linux 服务容器、三个独立持久卷、真实 HTTP Raft 通信；没有共享数据目录。
- 使用仓库 `docker-compose.raft.yml` 与 HAProxy 配置，测试覆盖文件将入口改为本机 28080；服务 API 为 18081–18083。通信端口只在私有容器网络开放。
- WAL 合批间隔 200ms，Raft tick 100ms，快照间隔 5 条，专用 RustFS S3 测试实例。
- 服务二进制来自本分支，`CGO_ENABLED=0`。SHA256：`c165df4c4190574b030eb7605e956b30d242df49f8b897576227e2ddd219c4c1`。
- 全量回归使用最多两个包并行，避免存储测试与选举测试争抢资源；HA 测试使用与运行默认值相同的 100ms tick。

## 首版限制与未验证范围

- 本记录验证单 Raft 组的三个完整副本、Share-Nothing 存储和 Leader 接管。之后新增的租户分片与多组扩容另见 [分片验收记录](sharding-validation.zh-CN.md)。
- 未运行跨宿主机/跨故障域测试，亦未验证宿主机、真实磁盘或机架整体故障。三个本机容器不能代替这些资格验证。
- 未完成生产容量、长时间持续负载、磁盘耗尽/真实 I/O 故障注入、维护长尾和大快照网络传输资格验证。
- 普通图读取已改为固定视图后释放应用锁；结构变更仍等待读取结束，维护和快照可以使新查询及新写入等待。心跳与图应用分开，并不等价于低延迟维护的性能保证。
- 自动备份调度在 HA 下明确拒绝启用；手动备份可由外部调度触发。
- 单条提案最多 32MiB，恢复还包含 JSON/base64 封装开销；没有实现较大恢复的分块持久化协议。快照预算默认 512MiB，超限保留读取并拒绝后续变更，需要提高预算后逐节点重启。
- Raft 传输使用私网 HTTP 和共享令牌，未提供原生 TLS/mTLS。成员 ID 永不复用，目录必须按整个副本保存。
- 验证的是本分支二进制与运行配置，没有发布制品、多架构镜像或跨版本混部资格。

运行配置和安全替换流程见 [Raft 运行说明](raft-ha.zh-CN.md)，设计基线见 [高可用方案](high-availability-design.zh-CN.md)。

### 混合读写性能复测

性能结果不支持“读写吞吐全面提升”的结论。长查询期间的发布和取消、应用积压内存窗口及路由探测次数改善有行为证据；混合负载则有收益、有明显回退，需要继续定位，不能把所有回退都归为环境波动。

主测量使用 OrbStack 的 Linux 本地命名卷，报告文件单独写到宿主机挂载。容器限制 8 CPU / 8GiB，每个节点 `GOMAXPROCS=2`；三个或五个完整投票副本、真实 HTTP Raft 通信。五副本先加入并提升两个 learner，再重新打开。固定 1,002 个实体，4 个写者、16 个读者，每批 20 组 host/service，预热 3 秒，测量 15 秒后等待尾部请求完成。每个场景两轮，将候选夹在两个相同基线之间，第二轮反转基线顺序。主机仍有其他工作负载。

### 仍存在的边界

- 查询列举和取消仅属于本进程；没有跨节点查询管理，也没有让 Follower 接收普通强读取。结构变更、任务和快照仍可能令新读写等待。
- 应用按 4MiB 窗口读取持久日志，单条更大的日志仍完整读取；这个上限不涵盖整个进程 RSS、提案、Raft 传输或压缩快照。
- 完整压缩快照及传输封装仍在内存，默认 512MiB 预算和超限停止变更的行为保留。终态摘要只压缩新完成记录，没有批量改写旧终态记录或实现无限历史保留容量。
- 迁移仍冻结租户，每轮重新导出完整源快照，导出/安装仍组装完整租户；没有在线增量迁移、单租户图拆分、自动热点均衡或自动排空。
- 新版能读取基线记录、日志和快照，但旧版不能解释新终态摘要。此次要求暂停流量、全组维护升级；没有证明任意混部、滚动跨版本升级或降级兼容。
- 以上服务均在一台 OrbStack 宿主机上。跨故障域、磁盘耗尽/真实 I/O 故障、长时间负载、大租户/大快照和生产容量仍未验证。

## 回滚日志合并补充验收

五副本 WAL 的 Leader 执行轨迹中，8 秒采样累计系统调用等待为 7.15 秒，其中 `journalObject` 路径为 2.41 秒。旧实现持有一个日志互斥锁，串行读取旧文件并逐个提交 bbolt 事务，使并行对象写入等待不同对象的回滚记录。该累计等待包含并发 goroutine，不代表请求延迟的独占比例，也不能与其他重叠调用路径相加。

### 局部成本与服务性能

所有测量均在 OrbStack Linux aarch64、Go 1.26.7 中进行，数据写入 Linux 本地命名卷，报告写入独立的宿主机挂载。未停止宿主机其他工作负载。候选前后各运行一次相同基线，下一轮反转基线顺序；差异相对同轮基线均值，A/A 为两个基线绝对差除以均值。

写调用取 bbolt `TxStats.GetWrite`，在最终提交标记前采样；它不是 fsync 次数，也不是整个数据库写调用数量。已有 `graphdb_disk_sync_*` 只记录 FileStore 同步，不包含 bbolt 的同步。稳定证据是 4 / 8 路并行日志写调用分别减少约 31% / 53%；串行没有稳定提速，8 路第三轮的耗时也有较大基线波动。

真实服务使用 8 CPU / 8GiB 容器、每个节点 `GOMAXPROCS=2`，三个或五个完整投票副本。五副本由 learner 加入、提升并重新打开形成。固定 1,002 个实体、4 个写者、16 个读者，每批 20 组 host/service，预热 5 秒。三副本 direct / WAL 和五副本 direct 各测两轮、每窗口 20 秒；五副本 WAL 测三轮、每窗口 30 秒，共 27 个窗口，各窗口同步采样 Leader CPU。读取汇总 match、min_version、traverse、scan；WAL ingest 延迟包含多数派受理、完成轮询和查询可读，wal-accept 单独记录受理延迟。延迟正值表示变差。
