# Raft 写入性能优化

日期：2026-10-01（Asia/Singapore）。基于 `b4d5b0f3`，分支 `codex/raft-ha`，独立 worktree `GraphDB-raft-ha`。默认单机、单组 Raft 和租户分片部署继续共存。

## 改动与持久化边界

Raft 应用每条命令都要持久化续租，以保留确定性的业务时间、身份与 fencing。原实现把本地租约文件的每次更新都当作可能的接管，清空该租户的图缓存；下一次提交因此重新解码快照并回放历史，即使所有权、fence 和图的 manifest 都没有改变。

现在仅在本地复制应用、原 owner 和 fence 均未改变时，暂存已有的不可变图；完成租约持久化和 fence 检查后，重新核对 manifest 身份，再按既有缓存容量限制恢复它。接管、恢复、租户重建和 manifest 不匹配仍然使缓存失效。单机续租和非本地存储不进入此分支。

另一个开销是每次复制应用都递归同步数据目录的所有父目录。Raft 启动的 `RequireReplicatedWrites` 已经持久化初始化它们；此后复用现有安全目录检查，继续拒绝非法路径、同步新建目录并重试失败的目录屏障，省去已有祖先目录的重复同步。未初始化复制模式的调用仍保留原先的初始化步骤。

没有改变多数派提交、对象修改前的持久化回滚日志、文件同步、应用 checkpoint、幂等响应或 `ReadOnlySafe` 读取屏障。写入 p95 以发布完成为准，WAL 的受理延迟单独列出。

## 测量方法

- OrbStack Linux aarch64，Go 1.26.7；专用容器限制 8 CPU / 8 GiB，每个数据库进程 `GOMAXPROCS=2`。本机同时有其他工作负载。
- 三个真实 Raft 服务进程、三个独立 Linux 数据目录，使用 HTTP 通信；源码和二进制只读挂载。每个场景、版本、轮次都使用新目录。
- 复用 `scripts/raft_benchmark.py` 与 `tools/loadtest`，固定 1,002 个实体、每批 20 组 host/service（60 项：40 个实体与 20 条边）。播种后重启到独立管理端口采集 profile，只读预热后更新固定 host 字段，避免图规模持续增长。
- 纯写为 4 个写者；混合直写与 WAL 为 4 个写者加 16 个读者。读者执行匹配、遍历、`min_version` 查询和扫描。
- A/A 使用同一基线二进制，2 轮、20 秒窗口、3 秒预热；版本对比使用 2 轮、30 秒窗口、5 秒预热，第二轮反转顺序。两类窗口均采集 Leader CPU profile。
- 每个窗口核对零请求错误、发布批次数等于版本增长和 `min_version`。CPU、磁盘写入为所有服务进程的 `/proc` 增量，包含服务日志，排除负载客户端。各操作保留独立 p50/p95/p99。

## 瓶颈定位

A/A 首轮基线纯写 CPU profile 中，`loadForWriteLocked` / 图加载路径约占 Leader 累积样本 16%，历史回放约占 15%，分配路径约占 35%，这些路径存在重叠。仅保留有效图缓存的诊断版本中，分配路径降至约 14%；两轮纯写每批服务 CPU 分别从 1,120 / 1,013 ms 降至 414 / 404 ms。最终版本首轮没有采样到图加载/历史回放路径，分配路径约占 18%。CPU 样本不包含全部磁盘等待时间，不能直接把样本占比当作延迟占比。

聚焦回归在基线源码上实际失败：第二次复制提交重新读取了历史；同一回归在缓存修复版本上通过，并核对续租时间仍然更新。已有崩溃与隐藏 I/O 失败测试改为走实际 Raft 初始化路径，以覆盖目录屏障优化后的回滚与 checkpoint 边界。

## 复现

使用同一 Go 工具链构建 `b4d5b0f3` 与当前源码的服务二进制，并构建 `./tools/loadtest`。将二进制目录挂载到 `/bench`，使用新的输出目录；A/A 的两个变体指向同一个基线文件。

```sh
docker --context orbstack run --rm --cpus 8 --memory 8g \
  -v "$PWD:/workspace:ro" -v /absolute/binaries:/bench:ro \
  -v graphdb-raft-write-perf-data:/runs -w /workspace golang:1.26-bookworm \
  python3 scripts/raft_benchmark.py \
  --variant before=/bench/graphdb-before --variant after=/bench/graphdb-final \
  --loadtest /bench/loadtest --output /runs/new-write-comparison \
  --cases write-direct mixed-direct mixed-wal \
  --rounds 2 --seconds 30 --warmup 5 --profile
```

此次仅测量单组性能。分片拓扑可增加 `--topology sharded`，但本轮分片验收只验证行为，没有测量扩容、迁移期间或多数据组并发的性能。

## 验证范围

性能测量使用同机通信和固定小图，未覆盖跨机网络、生产容量、长时间负载、大租户、磁盘耗尽或维护期间尾延迟。缓存超出既有容量限制时仍需加载图；目录同步的收益也取决于目录深度和存储设备。分片扩容与迁移需要运行验收，不能用单组性能窗口代替。
