# 本地磁盘版发布验证：旧索引 GC

## 发现的问题

`e24593f3` 的[30 分钟发布负载](https://github.com/SamuelSupe/graphdb/actions/runs/35315450339)
出现 4 次写入请求超时，发布步骤被阻止。索引重建后的 GC 持有租户维护锁和独占读视图，
对旧 Parquet 对象依次尝试不同类型的完整解码，再两次计算同一内容的哈希。
OrbStack 的密集维护负载与 goroutine 栈确认了这条路径，并观察到查询在读视图锁上等待。

## 改动和保护边界

- 根据既有版本化目录布局选择解码器，只完整解码一次。
- 提前排除当前及更新路径；解码后仍检查内容中的租户、版本和对象身份。
- 当前 catalog 引用的对象继续受保护，包括沿用的旧版本对象。
- 列出的孤立文件没有外部预期哈希，删除“同一字节串解码两次后比较自身哈希”的重复工作。
  从旧 catalog 获得的预期哈希校验、catalog 自身的持久化内容校验保持不变。
- 损坏、无法识别、跨租户、当前或未来版本的内容保持不动；解码使用调用方的取消上下文。

## 聚焦基准

OrbStack Linux arm64，Go 1.25.14，2 CPU / 6 GiB，`GOMAXPROCS=2`。
固定 10,000 个实体、每实体 4 个属性的 Parquet 页面，MemoryStore 隔离清理的解码与分配开销。
每次删除前重新放入同一文件，准备数据不计入时间；修复前后各运行一次、每次 3 次迭代。

| 指标 | 修复前 | 修复后 | 变化 |
| --- | ---: | ---: | ---: |
| 每页清理耗时 | 307.52 ms | 56.86 ms | -81.5% |
| 分配字节 | 872,144,856 | 225,157,304 | -74.2% |
| 分配次数 | 4,703,863 | 1,068,881 | -77.3% |

```sh
go test -mod=readonly ./internal/storage -run '^$' \
  -bench BenchmarkCleanupListedEntityPage10K -benchtime=3x -count=1
```

这是清理单个对象的聚焦样本，不能推导整体吞吐或尾延迟改善比例，也没有测量峰值 RSS。
完整发布仍要求带 compact/GC/索引重建的 30 分钟负载零错误通过；对应报告随发行包提供。

## 回归验证

OrbStack 已通过 GC/清理/索引重建相关测试及 race 检查。补充测试覆盖旧路径中包含当前版本、
未来版本、其他租户以及损坏内容时不误删；现有测试继续覆盖当前引用、空唯一索引、打包文件、
增量索引与同版本分页视图。发布流水线还必须通过全量测试、HTTP 恢复、重启和对象存储备份验证。
