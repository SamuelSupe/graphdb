# 维护负载、冷读及恢复测试的后续定位

日期：2026-10-12。本次接续[第一轮复测](maintenance-retest-2026-10-12.zh-CN.md)，基线已经包含第一轮共享文件写入预算修复；这里的“修复前”不是未经修改的 v2.3.0。改动仍在本地工作区，未提交或发布。

结论：默认冷读误用两秒追平期限及资源争用下的恢复清理测试假超时已修复；字符串编码分配成本和快照重复索引构建已优化。成熟单机写入 P99 和 stale 样本有所改善，但维护期间的秒级长尾及瞬时索引滞后仍存在。重启快照、旧版读取兼容及深度审计通过，未发现损坏证据；原历史 CI 超时的具体触发环境仍未证实。

## 已定位并修改的行为

### 默认冷读误用追平期限

成熟数据包含 51,007 个实体、85,091 条边，版本 850。基线进程冷启动第一次全量导出在 2.012 秒返回 `503 reader_not_fresh`；随后重试成功，导出内容与原快照相同。CPU 采样显示整图装载主要在解码快照分片、校验逻辑哈希和构建图。首次装载没有旧视图可以追平，却套用了默认两秒 reader catchup 期限。

默认冷读现在仍固定请求开始时已提交的 manifest 版本，首次整图装载使用已有 reader load 准入、加载期限和请求上下文。显式 `min_version` 请求、已缓存视图落后于目标的请求仍受原追平期限限制。客户端取消或期限到达继续返回请求错误。实体和边扫描的图回退也使用相同规则。

同时删除 `FromSnapshot` 中两次重复的实体索引构建：规范化后构建一次实体索引，合并边后只追加边索引。实体合并、边端点重写、类型和基数验证保留。

四条 HTTP 回归路径（全量导出、实体扫描、边扫描、实体读取）在基线均返回 503，修改后均返回 200；显式最小版本和已有落后缓存的期限测试继续通过。真实成熟数据的首轮修改版第一次导出返回 200，耗时 4.623 秒；内容与基线快照一致，深度审计 1,747 项通过。该次与普通测试共享 VM，耗时仅用于证明冷读成功，不作为速度对照。

### Parquet 字符串字典的分配成本

成熟负载 CPU 采样中，共享索引文件工作约占累计 CPU 的 42%，Parquet `WriteTable` 约占 30%；这些调用包含关系不能相加。宽行模式在每个字段行重复字符串元数据，默认字典编码有显著分配成本。

实体／边页、二级索引数据、commit／ingest 行及全量快照记录改为字符串 delta byte-array 编码，数值列保留字典，继续使用 Snappy。复用一个写入属性函数；单实体记录和其他元数据格式保持已有编码。没有改变列 schema、row group 边界、对象布局或逻辑哈希。

曾试验全部关闭字典，但成熟全量快照从 17.61 MB 增至 54.13 MB，因此未采用。也比较了字符串前缀编码及数值 delta 编码，最终选择保留数值字典以兼顾 CPU 和文件大小。

同一成熟快照、同一分片、4 核／6 GiB／Go 1.26.7，每个基准两次、每次三轮：

| 编码对象 | 基线耗时 | 修改后耗时 | 累计分配字节前／后 | 分配次数前／后 | 文件字节前／后 |
| --- | --- | --- | --- | --- | --- |
| 最大实体分片 | 27.25–29.22 ms | 21.16–21.43 ms | 57.44／47.04 MB | 627,927／165,300 | 268,402／286,089 |
| 最大边分片 | 11.81–11.83 ms | 9.08–10.52 ms | 29.02／21.05 MB | 324,777／53,740 | 171,246／150,571 |
| 全量快照记录 | 5.69–5.71 s | 5.15–5.42 s | 10.13／7.22 GB | 128,148,783／23,797,377 | 17,612,397／17,003,203 |

实体分片文件增大约 6.6%，边分片缩小约 12.1%，这份全量快照缩小约 3.5%。分配字节是编码过程的累计分配，不是峰值 RSS。结果限于这份数据；小样本编码时间不能推导请求 P99 或所有租户的收益。实体和边基准在计时前核对解码后的逻辑哈希。

### 恢复清理测试的两秒等待

在 OrbStack 中限制为 0.25 CPU，基线 `TestRestoreDrillCleanupFailureFailsTaskAndRetriesCleanup` 多次触发两秒等待上限。任务仍在 `restore_drill_restore`／审计阶段，goroutine 栈显示 Parquet 解码和对象哈希执行，没有观察到死锁。这个场景并没有两秒完成的 API 契约。

删除该文件独立的两秒轮询，复用任务测试已有的十秒等待边界，并在超时信息中记录最后任务状态和阶段。失败注入、失败状态、清理重试及目标对象清除断言保留。生产恢复期限没有调整。

相同 0.25 CPU 限制下，复用等待辅助函数后的探索版（plain 编码）race 模式连续 30 次通过，113.129 秒完成；单次经常需要 3–6 秒。最终混合编码版本又重复 30 次全部通过，75.002 秒完成，单次 2.31–2.79 秒。基线的 60 次探索运行因已取得重复失败和执行栈而主动中断，不计为完成。这里复现并修复的是资源争用触发的测试假失败；没有原历史 CI 的调度证据，不能断言它与历史偶发失败的具体环境完全相同。

## 成熟数据维护负载

两版从同一版本 850 的原生 Linux 数据卷副本开始，采用 4 核、6 GiB 硬上限、`GOMEMLIMIT=4GiB`、读写缓存各 2 GiB、WAL sync／100 ms flush。4 个写入协程、16 个读取协程、批次 20、写入间隔 5 秒，各运行 8 分钟；压缩间隔 2 分钟，GC 和索引重建间隔 4 分钟。顺序执行，期间没有本任务其他重测试；同一 VM 中用户其他项目仍运行。

| 观测值 | 基线 | 修复版 |
| --- | ---: | ---: |
| 写入 P50 / P95 / P99（秒） | 4.331 / 8.798 / 12.382 | 3.931 / 6.499 / 10.132 |
| 各查询场景 P99 范围（毫秒） | 24–128 | 23–136 |
| 写入 HTTP 200 | 192 | 204 |
| 索引 stale / 采样数 | 16 / 43 | 11 / 43 |
| unhealthy / reader unready | 0 / 0 | 0 / 0 |
| 采到的最大 catalog 版本落后 | 4 | 4 |
| 压缩 / GC / 索引重建 | 3 / 1 / 1 | 3 / 1 / 1 |
| 最终 manifest / catalog 版本 | 1043 / 1043 | 1055 / 1055 |
| 最终实体 / 边 | 62,527 / 104,291 | 63,247 / 105,491 |
| 峰值容器内存（GiB） | 4.320 | 4.314 |

两组 soak 和报告退出码均为 0，无非预期请求错误或查询 503。运行期停止写入后，立即、10 秒后、再 20 秒后三次索引健康检查均为 ready；两组各 1,747 项深度审计通过。后台日志有索引重建期间的 WAL 背压重试：基线 4 次、修复版 3 次，均为同一批四个请求的重试；对应 LSN 随后均成功提交四个逻辑事务并发布 manifest。

两版分别冷重启，完整导出快照与重启前逐字段一致。基线第一次默认导出仍返回 503（2.016 秒），修复版第一次即返回 200（5.728 秒），内容核对通过；冷装载仍需要数秒。官方 v2.3.0 二进制在修复版数据的独立副本上运行，读取新编码快照、分片和提交尾部后导出内容完全一致。该兼容性检查使用 `allow_stale=true` 绕过旧版首次装载的两秒期限，缓存初始为空，导出的是相同的最新版本 1055；这不是默认冷读可用性测试。

兼容性验证第一次用了已不支持的 `GRAPHDB_MODE=reader`，进程启动失败；失败日志和状态保留。改为独立副本上的 `all` 模式后验证通过，没有写入测试请求。该失败属于测试启动配置，未计为兼容性通过。

写入 P99 的观察差值约为 18%，但只有一轮前后对照，VM 中还有其他项目，最终数据量也因吞吐不同而不同，不能当作稳定性能承诺。延迟为工具全程累计口径；健康采样跳过首分钟。查询范围不含维护、控制和全量导出；stale 样本数不是查询错误率，也不是持续时间比例。**维护期间的秒级长尾和短暂 catalog 滞后仍存在。**

该成熟图的单图维护估算为 841,403,376 字节，前后视图合计估算约 1.68 GB，超过默认 512 MiB 维护预算，因此本地 ingest 索引更新会按现有机制同步追平。释放租户锁后有后继提交时，manifest 可以暂时领先 catalog；默认读取仍要求目标版本，通过读图回退保持一致性。没有提高维护预算或降低版本要求来改变 stale 统计。

## Raft 回归负载与恢复

最终修复版使用三节点，每节点 2 核／1.5 GiB，协议版本 3、流式快照、每 5 条日志触发快照、200 ms WAL flush。4 个写入协程、16 个读取协程、批次 1、写入间隔 5 秒，各运行 12 分钟；压缩间隔 3 分钟，GC 和索引重建间隔 6 分钟。没有与本任务其他重测试并行。同一 VM 的其他项目仍运行。

| 观测值 | 结果 |
| --- | ---: |
| 各查询场景 P99 | 0.807–1.005 秒 |
| 最大查询请求 | 6.189 秒 |
| 写入 P99 / 最大值 | 2.262 / 5.747 秒 |
| 写入 HTTP 200 / 429 | 474 / 9 |
| 索引 stale / 采样数 | 0 / 67 |
| unhealthy / reader unready | 0 / 0 |
| 压缩 / GC / 索引重建 | 3 / 1 / 1 |
| 最终 manifest / catalog 版本 | 474 / 474 |
| 最终实体 / 边 | 1,489 / 2,561 |
| 三节点峰值内存 | 约 0.39 / 0.35 / 0.35 GiB |

soak 和报告退出码均为 0，无非预期请求错误或查询 503。429 为允许的写入背压，需要与 HTTP 200 分开看。停写后的三次健康检查为 ready，1,674 项深度审计通过。关闭并重启整个集群后，完整导出快照逐字段一致，三台副本的 committed/applied 日志位置均为 845。

这次是最终版本的回归验证，数据量和维护频率与第一轮 30 分钟结果不同，不能据此推导旧版 4.65–5.18 秒长尾已经消失，也不能与批次 20 的单机结果比较部署优劣。每 5 条日志触发快照是压力设置，生产默认值为 1,000；这里没有改变该压力设置来提高成绩。

Raft 请求先经 quorum/read barrier 并等待本地应用，再固定数据视图。reader catchup 的两秒期限在后面使用，不约束前面的 Raft 屏障。运行中两次累计采样的成功 read barrier P99 分别落在 `(0.25, 0.5]` 和 `(0.5, 1]` 秒的直方图区间；全程查询执行日志 P99 约 10.792 毫秒，查询 HTTP 日志 P99 约 919.887 毫秒。调用链和分段指标支持一致性／应用等待是主要延迟来源之一；这些分布没有按请求逐一配对，不能相减推导阶段占比。维护期间仍有少数秒级请求，未宣称所有长尾已经解决。
