# 本地磁盘性能优化，第五轮

日期：2026-09-17。工作区：`GraphDB-local-disk-v2`，分支：`codex/local-disk-v2`。

## 结论

本轮减少 Parquet 编码中的重复深拷贝、临时切片扩容和时间格式化。只修改三个生产文件，保留字段规范化、内容校验、文件格式和同步落盘语义。

1 万实体快照编码的分配量减少 **6.0%**，无分析器的短基准耗时减少 **5.0%**。实际 WAL 混合负载中，服务 CPU 用时减少 **2.8%**，吞吐增加 **1.4%**。这是局部、温和的优化；单轮短测不能证明整体达到最初的 10% 性能验收目标。

全量单测、针对存储边界的 race、完整 HTTP API race、direct/WAL HTTP 流程和真实对象存储备份恢复均通过。这些检查没有发现重大回归，但不等于证明不存在所有重大 bug。

## 改动与依据

- `parquet_commit_rows.go`：实体、边的 mutation rows 不再进行外层重复深拷贝。内层 `entityPageRows`、`edgeShardRows` 仍然拷贝和规范化字段；外层只读取标量头部及字符串写入策略。
- `parquet_entity.go`、`parquet_edge.go`：根据实际字段、来源、身份信息数量预分配行切片，避免逐次扩容；没有组件时仍保留一条 metadata 行。
- 实体页、边分片的更新时间只格式化一次；实体、边自身的创建及更新时间也各格式化一次，供组件行复用。

内层拷贝不能简单删除：`graph.CopyEntity` / `CopyEdge` 会规范化嵌套的 typed-nil map 和部分空切片，直接跳过可能改变持久化内容。本轮保留该行为，没有增加共享缓存、对象池或新的并发状态。

优化前的分配分析中，`entityPageRows` 的自身分配占约 6.4%，`entityMutationRows` 占约 8.5%；复制字段和来源也有明显开销。优化后，前者在同一分析负载中的自身分配由约 286 MiB 降至 140 MiB。该 profile 包含基准初始化和多次操作，不是单次请求的内存占用。

## 测量方法

- OrbStack Linux arm64，Go 1.25.14，容器限制 4 CPU / 6 GiB。
- 数据位于 Linux 本地卷 `graphdb-local-disk-v2-validation`。
- before 为本轮开始时的完整工作区快照，after 为本轮三个文件改动后的快照；**不是 Git main 与当前分支的比较**。工具沿用 `graphdb-main` / `main-local` 名称代表 before。
- 使用现有基准和负载工具。微基准最初各运行 5 次并采集 CPU/分配 profile；因短测耗时与分配趋势不一致，追加一次无分析器、每基准 20 次操作的诊断。
- HTTP 只跑一组 before → after：相同静止数据副本，10,002 实体、5,001 边，4 写入客户端、16 查询客户端，批量 20，每客户端每 2 秒写入。预热 5 秒、测量 60 秒，WAL 同步持久化，flush interval 100 ms。
- 两版测量期间均执行了两次后台 compact 和一次 GC。写入有固定节奏，因此发布吞吐主要由输入节奏决定，不能当成最大写入能力。
- 没有清除操作系统页缓存，没有停止其他 OrbStack 工作负载。冷读仅代表进程重启后首个查询。

### 微基准

无分析器、20 次操作，原始记录为 `bench-unprofiled-before.txt` / `bench-unprofiled-after.txt`：

| 指标 | before | after | 变化 |
| --- | ---: | ---: | ---: |
| 10K 快照编码耗时 | 332.27 ms | 315.70 ms | -5.0% |
| 10K 快照编码 B/op | 577,043,016 | 542,324,521 | -6.0% |
| 10K 快照编码 allocs/op | 7,218,463 | 7,128,472 | -1.2% |
| 快照文件大小 | 442,310 B | 442,310 B | 相同 |
| 单实体索引提交耗时 | 9.622 ms | 9.579 ms | 基本持平 |
| 单实体索引提交 B/op | 14,781,240 | 14,428,000 | -2.4% |

带分析器的 5 次短测中，快照耗时是 309.16 → 320.22 ms，单实体提交是 15.93 → 16.91 ms；分配量仍分别减少约 6.0% 和 3.0%。这些记录完整保留，不把无分析器的一次更好结果当作稳定延迟保证。索引提交会随提交序列触发不同维护工作，5 次和 20 次结果不可直接横向比较。

## 正确性验证

- `go test -mod=readonly ./...`：12 个包，1,305 个顶层测试通过；两个需要外部 S3 的测试在该步骤跳过，随后在对象存储 gate 中运行。
- `go vet -mod=readonly ./...`：通过。
- 存储 race：207 个顶层测试通过，覆盖 Parquet、compact、snapshot、本地目录、读视图、恢复、WAL、GC、索引任务及索引重建；一个外部 S3 测试在此步骤跳过，随后补跑。
- 完整 `internal/httpapi` race：184 个顶层测试通过。
- `release_gate.sh` 的实际 HTTP 阶段：direct/WAL 写入、查询、来源治理、租户隔离、索引、分页、导出、compact、备份恢复与重启通过；Python SDK 12 个测试通过，Go SDK 包测试包含在全量单测中。
- 独立 MinIO `object_backup_gate.sh`：在 race 下验证 multipart 发布、禁止 manifest 重定向恢复和重新打开后的恢复；通过真实 HTTP 完成备份、在全新目录发现并 dry-run、恢复、覆盖恢复、重启后数据及元数据核对。只清理本轮创建的容器和网络。
- 编码兼容性探针：空对象、普通对象和 9,000 字段宽对象，包含来源、identity、嵌套 JSON、typed-nil、空切片和非 UTC 时间。实体页、边分片、commit、segment、snapshot 共 15 份文件与 before **逐字节相同**，输入未被修改。探针只放入隔离源码副本，保留脚本，不增加重复的永久测试。

未运行 100K 全矩阵、30 分钟持续负载、受控 OS 冷缓存测试或历史 release tag 的完整兼容脚本。本轮数据格式比较针对开始优化时的版本。
