# Raft 运维与升级

适用于单组 Raft，以及租户分片的目录组和数据组。默认单机仍使用原有 [本地磁盘部署](local-disk.md)。当前验收范围和发布缺口见 [发布准备状态](raft-release-readiness.zh-CN.md)。

## 拓扑与入口

每个 Raft 组至少三个投票副本，每份副本使用独立本地目录。三个投票副本的多数派是两个，可容忍一个副本不可用；五个投票副本保存五份数据，多数派是三个。大集群保持每组三份副本，应新增独立分片组，再按租户迁移数据。两个投票副本不属于当前支持的成员配置。

生产环境将同一组的三个副本放在三个独立故障域。单机 Compose 是启动示例和验收环境，不能证明宿主机故障下仍可用。分片模式同时保护目录组；目录组失去多数派会影响全局路由和管理。入口也应部署至少两份，通过外部负载均衡访问；示例中的单个 HAProxy/router 自身没有高可用保证。

私有 Raft 端口只允许成员和授权管理端访问，使用至少 32 字节的随机共享令牌。当前私有传输使用 HTTP，跨主机部署需要受保护的内网、加密隧道或外部 TLS 终止。不要直接暴露私有监听器。API 的 TLS、身份鉴别与租户授权由入口实施，覆盖外部传入的租户头；管理和调试端点保持私有。更换共享令牌需要维护窗口并统一更新整个组。

## 监控与处置

逐副本周期采集 `/v1/diagnostics` 和 `/metrics`，同时检查 Raft 状态采样年龄；`/v1/health` 读取实时 Raft 状态，存储阻塞时可能等待。健康接口可以返回 HTTP 200，同时携带 Raft 错误；告警必须检查内容。`raft.ready` 是本地角色/错误状态，入口可用性以 `/v1/readiness` 的新多数派确认及存储探测为准。就绪检查不等待已有维护任务应用完成，让仍有多数派的 Leader 接受等待中的请求；正常图操作仍执行完整读取屏障，未应用提交不能被跳过，超过请求期限会返回超时。Follower readiness 经当前 Leader 确认多数派；摘流节点返回 503。根据本地 health 的节点 ID 与 Leader ID 判断角色，不能从 readiness 推断角色。

| 条件 | 起始告警策略 | 处置 |
| --- | --- | --- |
| 任意 `raft.error` 或 `raft.snapshot_error` 非空 | 立即告警 | 保留日志和目录，查看错误；预算不足统一提高配置，禁止删日志 |
| `raft.status_age_seconds` 超过 10 秒或状态采样未知 | 持续 1 分钟告警 | 状态采样可能阻塞，结合 `status_sample` 并发、持久化及宿主机资源检查；旧采样不能证明多数派可用 |
| `raft.snapshot_cleanup_error` 非空 | 持续 5 分钟告警 | 旧快照清理在后台每 5 秒重试，读写继续；检查剩余空间、目录权限和异常文件，禁止删除当前快照或日志 |
| 全组没有通过 readiness 的入口 | 连续 10 秒告警 | 检查多数派、网络、令牌与磁盘；停止重试非幂等业务操作 |
| `application_lag` 持续增长 | 连续 60 秒告警 | 对比负载、维护任务、磁盘同步和剩余空间，降低输入速率 |
| `graphdb_disk_sync_failures_total` 增加 | 立即告警 | 检查磁盘/文件系统，隔离故障副本并按新 ID 替换 |
| 磁盘或内存剩余不足 | 按实际容量基线设置 | 暂停大恢复、迁移和维护，预留快照、旧图、暂存及回滚日志空间 |
| WAL 受理记录长时间未到 `committed` | 超过业务发布时延要求告警 | 检查当前 Leader、队列预算与应用滞后；按原幂等身份查询和重试 |

这些时间是初始运维建议，需按实际磁盘、网络和维护长尾调整。默认心跳间隔仍为 100ms，`GRAPHDB_RAFT_ELECTION_TICKS=30` 将随机选举等待设为约 3–6 秒；可独立调整，不必为了容忍慢盘而降低心跳频率。全组使用相同设置，并验收异常失主的恢复时间。普通 Raft 请求的内部等待预算为两分钟，客户端更短的期限仍会结束请求；读写入口以本地持久化提交位置检查应用积压，不同步等待 Raft 状态，保留 1024 条或 64MiB 的准入上限；维护仍可能造成较长等待，这不是延迟承诺。Raft 状态、应用/复制积压、持久化及控制/数据传输指标见[诊断指标](diagnostics-metrics.zh-CN.md)，需要保留逐副本采集。不要用进程存活或单次 HTTP 200 替代多数派可用性检查。

多数派失活时关联查看 `graphdb_raft_operation_seconds_bucket` 的 `persist`、`control_send` 和 `snapshot_persist` 尾部耗时，以及宿主机 CPU 抢占、swap、磁盘延迟。路径总耗时包含锁等待和调度等待，不能直接当作单次 fsync 耗时。持久化或控制消息停顿接近 `GRAPHDB_RAFT_TICK × GRAPHDB_RAFT_ELECTION_TICKS` 时可能触发重新选举；需要保障副本的 CPU、内存和磁盘资源，避免将它们与高压力负载放在同一故障域。调整选举等待会改变故障发现时间，不能替代资源保障或多数派确认。当前候选的共享 VM 失败窗口与串行复测见[可用性验证](availability-rolling-validation-2026-10-04.zh-CN.md)。

HAProxy 示例每秒检查，连续三次失败才摘流，一次成功恢复，避免单次就绪超时同步摘除全部副本。就绪接口继续报告实际探测失败，数据请求继续执行多数派和应用屏障；容错发生在入口健康策略。滚动控制器默认等待 7 秒传播摘流后再停止副本或 router，需按实际入口配置调整。

WAL 刷新遇到提交尾部或其他资源背压时，Leader 在提案前推迟刷新，已受理批次保持待发布，集群仍可读取和执行压缩。提交尾部是调度软阈值，一个刷新窗口可能越过阈值；压缩后恢复刷新。实体/边配额属于业务限制，继续由全部副本按同一复制策略检查。

## 滚动升级及维护回退

本轮支持至少三投票副本的不停机滚动升级，并为分片提供双 router 与入口摘流。首次从第四轮修复候选桥接、严格协议模式、逐节点脚本和回退边界见 [滚动升级手册](raft-rolling-upgrade.zh-CN.md)。只支持实际验收的兼容窗口；更早程序无法执行恢复分块日志或解释终态 WAL 摘要，仍执行下面的整组维护流程。

1. 核对候选二进制、镜像和 SDK；记录每个组成员、目录、预算、角色及配置。保存升级前程序和配置。旧日志没有复制队列、配额及 S3 命名空间时，统一这些设置，等待所有副本应用完成并核对数据；详见 [P0/P1 修复与升级边界](raft-p0-p1-review-2026-10-02.zh-CN.md#升级和验收边界)。
2. 暂停入口写入及外部备份/维护调度，等待已受理 WAL 全部发布，排队任务、租户迁移和恢复全部结束。不要带着未执行的新协议任务降级。
3. 通过当前组入口创建备份并完成独立恢复演练，记录快照版本、任务和结果。租户备份不包含全局分片布局，另外保存目录组状态及所有配置。
4. 关闭入口，停止整个组。备份停机后的每份完整目录，包含 `.graphdb-raft` 日志及应用 checkpoint；不要把不同时间或不同节点的目录拼接在一起。
5. 替换整个组的程序，保持成员 ID、角色、令牌、前缀和数据目录，使用相同快照预算。分片环境先完成目录组及全部数据组的程序替换，再恢复入口。
6. 启动各组并等待多数派、应用追赶和 readiness。验证代表性读写、版本、幂等重试、WAL 状态、任务和租户路由后再开放流量。

仅在升级后尚未产生新写入时，才能停机并恢复整套升级前目录/程序。产生新写入后，恢复旧目录意味着丢弃这些写入，不能当作无损回退。较旧程序不能直接打开包含新命令的现有目录；需要先明确目标版本兼容性，使用备份/导出到全新部署进行迁移，并重新验证。未经验证的组合保留为“不支持”。

## 故障恢复与替换

单副本故障时保持多数派服务，使用新的节点 ID、空目录和 `GRAPHDB_RAFT_BOOTSTRAP=false` 加入 learner。追赶完成后 promote，再移除旧节点；接口示例见 [成员替换](raft-ha.zh-CN.md#安全替换节点与滚动升级)。退役 ID 永久保留，不能复用。同一版本计划重启一次只停一个副本。

多数派丢失时先停止入口写入，保留所有残存日志、目录和配置。尝试恢复原成员及原目录；不能重新 bootstrap 残存副本来绕过多数派。全部磁盘丢失只能从已验证备份重建新组，恢复点取决于最近成功备份，不能保证保留备份之后所有确认写入。分片重建还需要恢复并核对租户归属和路由代次。

[未发布的离线恢复修复](product-p0-p1-review5-2026-10-03.zh-CN.md)保护独立 Raft/WAL 目录的占用与恢复目标路径。完整备份和恢复必须取得每个配置角色的锁；看到 `directory is in use` 或 Raft 数据库锁冲突时，先找到占用进程并正常停服，不能删除 `.lock`、`.graphdb.lock` 或 `raft.db` 来绕过。旧备份中的锁对象不会覆盖目标锁。改变根目录布局时，父角色的归档对象不能落入另一角色子目录；使用无对象交叠的空目标重试，保留原始归档和恢复日志。完整集群停机边界与恢复顺序见[灾备步骤](product-operations.zh-CN.md#完整运行状态灾备)。这些文件锁不改变协议或已验收的滚动窗口，本轮没有新增混部资格。

[后续完整性修复](product-p0-p1-review2-2026-10-03.zh-CN.md)还覆盖 manifest 丢失但图对象仍在，以及完整图冷加载的当前算法摘要不匹配。故障副本停止应用，保留原 checkpoint；恢复正确文件后重放，或按上述成员替换流程重建。不要通过同名租户创建、单副本 recover 或改写 `data_hash` 绕过保护。旧程序已经消费的错误图或任务结果需要另行核对，修复不会回溯纠正。

来源身份修复对受影响快照的解释与旧程序不同。包含来源所有者与外部 ID 来源不同、且已有显式 `sources` 的数据组，采用全组维护升级并核对身份；该候选与旧程序的混部不在不停机滚动资格内，不能直接复用旧版滚动窗口。

恢复任务用稳定任务 ID 跟踪；换主会继续复制相同输入的缺失块，部分输入尚未复制时仍需要原备份源可读。输入完整复制后可以直接完成恢复，即使备份源暂时不可用。SHA256 或块大小校验失败时不发布新图；租户清空或替换会使旧恢复失效并清理暂存。内存仍需容纳完整备份和图，暂存块计入快照预算；执行期间其他写入也会消耗预算。预算错误时先调整所有副本并重启恢复，再通过任务重试创建新任务。不要直接编辑或删除暂存文件。

2.2.2 及此前程序的 S3 恢复可能在切主或重新准备后报告 `restore input changed during transfer`。[2.2.4 的修复](product-p0-p1-review-2026-10-03.zh-CN.md)固定新传输的校验时间，但不改写旧摘要：使用包含修复的程序后，已经 failed 的任务通过 `POST /v1/tasks/{id}/retry` 创建新任务；旧程序留下的部分暂存若仍 queued，先取消，再重试。升级混部前先完成或取消这些 S3 恢复任务，窗口内暂停发起新的 S3 恢复，直到所有投票节点包含修复，避免旧 Leader 再生成不同摘要。已发布 manifest 的必需对象缺失或损坏时，故障副本应保持原 checkpoint 并停止应用；保留错误证据，恢复正确文件或用新 ID 重建，不能将其当作正常维护失败继续提供服务。修复不回溯纠正旧程序已经消费的副本分歧。

旧候选中，尚不存在目标租户的恢复任务可能一直排队。升级后先取消该旧任务，再重新发起恢复，新任务会登记到后台发现范围。当前 Raft 不支持内部自动备份策略；由[持久化外部备份 worker](backup-automation.zh-CN.md)提交集群备份任务并自动校验/隔离演练，演练提供明确的 `backup_key`；外部保留由显式配置的对象存储生命周期管理。单机自动备份不受此限制。

## 固定验收门禁

[2.2.4 的迁移/快照保护](product-p0-p1-review4-2026-10-03.zh-CN.md)把多数派确认的分块 SHA256 与总字节数持久化到归属记录。确认后的分块本地丢失或变化时，故障副本保持安装前 checkpoint 并停止应用；恢复与已确认摘要匹配的正确文件后重启重放，或用新 ID 替换该副本。不要改写摘要、归属或 checkpoint 绕过校验。健康多数派仍可服务。

旧程序的进行中迁移没有分块摘要。升级前在允许取消的阶段完成或取消迁移，混部期间暂停新的迁移，目标投票节点全部升级后重新发起。新程序对缺少分块绑定的旧 importing 状态返回 409，并保留源；已切换目录后不能取消，先按原流程完成该迁移。旧来源的完整导出格式仍可由新目标重新分块受理。本候选没有新的双版本混部资格，来源身份的维护升级限制继续适用。

新旧 Raft 快照格式都在固定源视图及解码后的临时目标上冷验证已发布图。接收到已校验字节但图损坏的旧快照时，不覆盖健康对象，也不推进应用位置；需修复源或从健康成员/已验证备份重建。流式源校验在后台构建，传输和编码格式保持兼容；完整图验证会增加构建/恢复时间和内存，不等于容量资格或全请求坏盘检测。旧程序已经安装的损坏快照不会被自动修复。

同组全部投票节点须使用相同 `GRAPHDB_PREFIX`，并在升级和重启时保持原值。新候选将它持久化到本地数据目录，旧目录先检查业务对象再建立绑定；配置不符拒绝启动，新复制命令或快照前缀不符停止应用/拒绝安装且保留 checkpoint。恢复原配置后重开并核对租户和应用位置，不能删除前缀标记或改写日志来绕过保护。若新节点首次就用错前缀并已建立本地身份，按成员替换流程用新 ID 和空目录重建。旧日志仍兼容，但旧二进制没有新增保护；本轮没有验证新的混部矩阵。已由旧程序造成的跨前缀分歧需从健康成员重建，不会自动合并。

准备支持 `!override` 的 Docker Compose 与 Python 3.11+，先构建候选镜像，然后执行：

```sh
GRAPHDB_GATE_IMAGE=graphdb:raft-candidate \
GRAPHDB_GATE_OUTPUT=/absolute/path/to/new-evidence \
scripts/raft_gate.sh

# 三十分钟持续验证；需要 Go 工具镜像及依赖缓存/网络。
GRAPHDB_GATE_IMAGE=graphdb:raft-candidate \
GRAPHDB_GATE_OUTPUT=/absolute/path/to/new-soak-evidence \
GRAPHDB_GATE_ENHANCED=true \
GRAPHDB_GATE_PROTOCOL_VERSION=3 \
GRAPHDB_GATE_SOAK=1 scripts/raft_gate.sh
```

在 macOS 设置 `DOCKER_CONTEXT=orbstack`；`PYTHON` 可指定可用的解释器路径。每次使用新的输出目录。门禁使用独立容器项目及卷，结束后删除这些测试数据，保留日志和结果。默认端口为 36081–36083、39081–39083（私有 Raft 监听器）、46080–46082、47080–47082、47101–47103、47201–47203、47301–47303。需要并行运行时，可用 `GRAPHDB_GATE_PORT_OFFSET=2000` 将全部宿主机测试端口增加 2000，并使用不同输出目录和项目名；预先确认端口无冲突。并行运行会产生资源争用，不适合性能比较。

三十分钟任务用现有 soak 工具，四个写入者、十六个查询者、每批一个应用组、每个写入者间隔五秒，执行 compact、GC 和索引重建。它验证持续正确性和维护交错，不用于声明最大吞吐或容量。报告校验持续时间与错误事件；失败保留 FAIL，不能以此前短测代替。
