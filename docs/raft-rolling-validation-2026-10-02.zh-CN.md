# Raft 滚动升级验收（2026-10-02）

本轮在独立 `codex/raft-ha` worktree 实现了兼容窗口内的逐副本滚动升级，包括安全摘流、Leader 交接、重新追赶、失败停止和双 router 入口。默认单机、单组 Raft 和按租户分片的 Raft 继续同时支持。实际两个不同二进制的升级、有限回退和严格协议模式下的协调脚本均已通过本机容器验收。

这里的“不停机”指业务入口和多数派持续运行。换主、连接关闭和健康检查传播仍可能产生请求重试；客户端必须保留写入幂等键或 WAL 批次身份。本次记录 39 次重试，最终逻辑操作失败为零，不表示每次 HTTP 尝试都成功。单机单进程升级仍需要重启，跨宿主机按现有决定保留待验收。

## 实现与关键修复

新程序使用协议 1，检查 Raft 传输、命令和快照的兼容声明；历史磁盘缺省字段继续读取，未声明协议的网络通信默认拒绝。首次升级仅针对上表已验证的来源，临时启用 legacy，逐个替换 follower、交接 Leader、替换旧 Leader，再逐节点关闭 legacy。未来补丁即使协议号不变，也需真实双版本验收。

摘流先停止新本地提案受理并等待已受理提案结束，然后多数派复制一条空操作，等待所有投票节点应用，核对全组健康和追赶，再交接 Leader。失败恢复先前摘流状态并拒绝停节点。Follower 经私有接口转发到 Leader，图操作仍执行强一致屏障；已经提交但结果不确定的写入不会由服务端自动重放。

本轮确认并修复一项安全摘流 P1：如果第三个副本的 HTTP 状态接口可访问，但 Raft 消息路径已经断开，仅比较旧提交/应用位置会允许停掉 Leader 唯一正常的复制伙伴，导致多数派不可用。原实现的回归实际失败；新增的空操作及全副本应用验证拒绝这种摘流。它证明当前复制路径，而不是依赖历史状态。

分片入口新增第二个 router 及鉴权摘流/恢复接口。两个 Compose 的 HAProxy 持续解析 Docker 服务名，修复容器替换后继续连接旧 IP 的问题；验收日志包含真实 DNS 地址更新。升级控制器逐个 drain、替换、核对目标构建并等待重新准入，失败即停止。其本机 inventory 文件锁不等于跨宿主机锁，实际部署控制器必须全组串行，并暂停成员变更和迁移。

## 失败历史与边界

原始失败日志全部保留。早期演练包含尚未追赶的交接 409、旧 Leader 入口传播 503、错误的 import fixture 格式、旧 HAProxy DNS 地址、未启动新增 gateway 和 HTTP 头大小写假设；相应脚本或实现修复后，以最终镜像重新运行。不会用早期通过结果替代最终源码验收。

最终源码的一次竞争检查与全仓测试、两个真实容器门禁同时运行时失败：慢副本在既有 10 秒期限内只追到应用 22/提交 25，另一个成员测试在 20ms tick 的 fixture 中切主后返回 503。没有 DATA RACE 报告。负载竞争是原因推测；本轮未扩大等待期限或弱化断言，停止本任务其他后端负载后，同一源码完整关键包 race 及成员场景连续 10 次通过。仍保留并行负载失败记录，不能据此宣称真实容量及慢副本长期负载已经资格验证。

本轮只资格验证指定来源到目标、该来源有限回退、目标同程序/配置滚动重启。更早程序、任意未来版本、不同协议和最终发布资产尚未资格验证。跨宿主机、真实大图/大 WAL 容量、长期压测和最终发布仍按 [发布准备](raft-release-readiness.zh-CN.md) 保留门槛。
