# Raft 快照与维护传输优化及性能验收

## 最终范围

本轮在 `codex/raft-ha` 已有可用性修复之上优化，候选为 `2.2.2-perf10`，不是 GitHub 正式版本。保留快照捕获和准备维护分块传输两项优化。强读合并的实验候选出现纯写或混合负载回退，已撤回；读确认、调用方取消、应用屏障、复制控制循环和原有诊断指标恢复优化前的实现。

- 快照捕获每个目录只做一次安全检查和目标目录创建，文件仍逐个固定 inode、核对类型、大小与预算。共享应用锁排除应用变更，同时允许读者；捕获后的完整图校验与编码在锁外执行。旧内存快照路径仍占用应用执行器，流式路径在后台构建。
- 维护捕获复用每个目录的检查和创建。首个 1MiB 块先确认多数派并应用，建立暂存清单；随后最多 4 个块并发提交，各自使用独立输入缓冲。所有已启动调用结束并成功后才发布。相邻块可复用现有最多 8 条日志的应用事务。取消、换主和重试仍校验固定摘要、已确认块内容、代际、任务 ID 和基础状态。
- 基准脚本增加协议版本、流式快照和快照间隔选项，默认保持原有协议 1 与非流式行为。启用独立管理监听的 profile 模式从管理端口获取指标。缺失的新增候选指标用未知值表示，不伪造零值。

多数派提交、ReadOnlySafe、完整图验证、回滚日志先于改写和最终文件/目录同步先于提交标记的持久化约束保持原有顺序。单机 direct/WAL 和 Raft 均继续支持。默认快照间隔仍为 1000 条日志。

## 验证方法

Linux 运行使用 OrbStack Ubuntu。本轮新增回归使用大于四块的真实维护输入，逐实体冷读校验三副本一致性，并检查任务完成和暂存分块清理。复用已有快照固定位置、发布冲突、崩溃恢复、同步失败、隔离、切主、恢复与维护并发测试。

存储与 HTTP 生产源码及测试逐文件核对后，复用本轮早些时候的完整 race 结果；最终候选重新执行复制和 HA 完整 race 测试。真实 S3 的四项测试没有配置 endpoint，保留待验收。

本轮集群测量与功能测试串行；OrbStack 内核和宿主机仍与其他运行任务共享资源，不能据此视为独占环境。基准使用独立 Linux 本地目录、真实进程、HTTP 复制和既有 loadtest，校验发布计数、最小读取版本、每个副本应用位置与同步失败计数。协议 3、流式快照、默认 1000 条日志间隔。每个场景做两轮 A1/候选/A2，第二轮反转二进制次序；A1/A2 为同一基线二进制。纯写、单读者、混合 direct 用 60 秒窗口；三/五副本并发读取和混合 WAL 用 20 秒窗口。最终基线与候选统一 Go 1.26.7、Linux arm64、CGO 关闭、trimpath 与链接参数，滚动升级仍使用先前验证的 availability3 镜像。

捕获微基准计时仅包含捕获，关闭与文件清理不计时；1000/5000 个对象分布于 32 个租户的多级目录。5000 对象保留原始 20 次迭代数据，1000 对象追加每窗口 200 次迭代对照。实现逐文件相同，原始测量与最终候选证据共同保留。

## 候选筛选

`perf4` 混合 direct 出现约 13% 写入与 23% 读取回退（A/A 约 3%）；`perf5` 单读者回退约 15.1%（A/A 0.1%）；`perf6` 60 秒反向混合 direct 回退约 11%（A/A 约 3%）。`perf7` 调整写入间歇判断后由下一候选取代。`perf8` 两轮短纯写回退约 7.5%/3.3%（A/A 1.8%/2.5%），`perf9` 增加首次写预检后，首轮 60 秒纯写仍回退约 11.3%（A/A 1.7%）。这些候选不构成最终性能验收。

CPU profile 的主要成本仍在索引更新、Parquet 编码、GC 与系统调用；不能仅据回退推断读队列是唯一原因。恢复原读路径的额外隔离轮遇到约 33% 的 A/A 波动，并观测到磁盘同步耗时上升，因此该轮只作诊断，不用于性能资格。最终方案收窄到捕获与维护传输，并统一构建方式重新测量。各候选冻结源码、二进制哈希及原始结果保留。

功能验证：最终复制与 HA 完整 race 为 PASS（86 个测试项，包含子测试，0 失败）；storage 和 HTTP 逐文件相同，复用本轮完整 race 的 PASS。四项真实 S3 测试因 endpoint 未配置跳过。Go vet、Python 编译和 diff 检查为静态 PASS。部署验收为 PASS：单机 direct/WAL 与 Raft 14 项、分片 11 项。混合版本滚动升级 29 项为 PASS：此前 availability3 与最终 perf10 混部、逐节点排空替换、追平、回退，以及协议 1 到协议 3 流式快照切换。负载成功完成 2142 次写入、2142 次强读与 267 次 WAL 接收；有 7 次可重试响应，最终请求失败为 0。三十分钟维护压力长测已完整结束：45116 次操作、4 次操作错误，验收结果为 FAIL。本轮可用性资格未通过。

长测首次启动发现夹具初始化竞态：只创建了 `prod`，而读请求立即遍历 `staging/dev`，依赖首次写入先完成。新增无写入回归在修复前稳定复现缺失实体，修复后 soaktest 完整 race 为 PASS；初始化补齐三个环境根后，从干净卷重新启动三十分钟验收，保留首次失败轮。没有修改查询错误契约或忽略错误。服务端构建闭包的 459 个生产 Go 文件逐一核对仍与已测二进制一致，聚合 SHA256 为 `846e76e3c72db00afc1ce74100aaa4c50c22fdb198b3e1131cf7947dc8795198`；修复后的 soaktest 工具单独冻结源码与哈希。当前工作树包含这项工具修复，不能用包含旧工具的冻结全量摘要代表当前工具源码。

## 维护压力长测的可用性失败

修复初始化夹具后的长测在 UTC 11:44:09–10 出现四次查询 503。节点就绪请求因原有两秒 QuorumBarrier 截止时间返回 504，HAProxy 的连续失败检查摘除了全部后端，随后自动恢复。故障窗口记录的任期均为 2，没有换主；该故障窗口没有观察到节点 OOM、CPU 限额节流或快照失败。

同期共享内核一分钟负载约 74–126，换入约每秒 7.6–17.3 万页、换出约每秒 8.0–17.2 万页；节点内存约 40–55MiB。节点及入口日志、指标和逐两秒资源记录共同保留在 `soak/outage-evidence.json`。这些数据表明环境存在明显争用，但不能证明不存在服务端缺陷，也不能抹去四次真实请求失败。没有扩大就绪截止时间、放宽多数派约束或过滤查询错误。完整运行最终累计 45116 次操作、4 次操作错误；维护成功事件为 compact_ok: 5, gc_ok: 2, index_rebuild_ok: 2。本轮可用性验收为 FAIL，不是可发布的 PASS。

整轮共享内核一分钟负载范围为 12.42–174，三个节点均无 OOM 和容器重启；后续维护阶段有少量 CPU 限额节流。写入 P99 为 24019ms，多数强读查询 P99 约为 6–8 秒。这轮存在可用性失败和显著资源争用，不作为生产延迟或容量结论。

## 剩余空间与验收边界

本轮没有实现全图维护的增量重建，也没有放宽维护发布的基础状态检查。profile 指向的索引写入、Parquet 对象布局和 journal 批次优化仍需独立设计与验证。不能把捕获阶段的改善解释为整体吞吐同比增长，也不能把共享 VM 中落在 A/A 波动内的变化解释为稳定收益。

每 5 条日志触发快照的维护压力长测与默认 1000 条日志的基准是不同场景。跨宿主机、真实 S3、24/72 小时稳定性和生产容量资格仍待验收；旧候选的三十分钟 PASS 不转移到最终候选。
