# 本地磁盘性能复查：深度索引校验

日期：2026-09-18。工作区：`GraphDB-local-disk-v2`，分支：`codex/local-disk-v2`。

## 结论与修改

本轮优化了 `internal/storage/index_health.go` 中重复的 JSON 归一化和哈希计算：

- 同一实体页归一化一次，供内容哈希和图数据比对使用；已计算的页哈希继续供实体记录校验使用。
- 同一边分片归一化一次，供内容哈希和图数据比对使用。
- 复用仅发生在单次检查内。实体记录的严格比对仍使用原始解码数据，保留 nil/空容器等细节。租户、版本、数量、元数据、内容哈希和图内容检查继续执行。

在 1 万实体的完整深度校验基准中，单次耗时约减少 **4.4%**，分配字节减少 **4.5%**，分配次数减少 **9.9%**。实际 HTTP 恢复样本约慢 1.6%，没有显示端到端恢复加速。因此本轮确认的是校验路径的重复工作减少，不宣称整体性能验收通过。

## 方法

- OrbStack Docker，Go 1.25.14 linux/arm64，4 CPU、6 GiB。源码和数据放在 Linux named volume。
- 修改前是本轮开始时的完整工作区，包含前九轮修改；不是原始 main。证据目录中的 `main-local` / `new-local` 是工具沿用的名字，分别代表本轮修改前 / 后。
- 两份源代码归档、二进制哈希和增量补丁均保留。生产代码只改一个文件；新增基准位于现有 `index_health_paging_test.go`，同一 fixture 复制到修改前后两份源码中。
- `BenchmarkIndexHealth10K`：真实 FileStore，10,000 个实体、5,000 条边，包含嵌套字段、数字字段和字段索引；先提交、compact、重建索引、预热一次，再用 `-benchtime=3x -count=1` 测量完整深度校验。`WriteEntityRecords=false` 与服务默认配置一致。
- HTTP：相同停止状态的种子目录，10,002 实体、5,001 边；WAL sync，关闭后台维护，先导出、compact、backup，再测量覆盖恢复。修改前后各一场，均采集 10 秒 CPU profile 和每 0.5 秒一次的进程资源数据。
- 不清空操作系统页缓存，不停止其他 OrbStack 工作负载。没有扩大混合负载比较矩阵。

## 深度校验基准

| 指标 | 修改前 | 修改后 | 变化 |
| --- | ---: | ---: | ---: |
| ns/op | 1,958,018,584 | 1,871,809,373 | -4.4% |
| B/op | 3,553,663,234 | 3,394,123,093 | -4.5% |
| allocs/op | 20,443,561 | 18,424,939 | -9.9% |

每次减少约 159.5 MB 分配和 201.9 万次分配。B/op 表示累计分配量，不是同时驻留的内存。耗时是本轮三个操作的均值，没有多轮统计显著性证明。

早期 fixture 未建立索引目录，在准备阶段得到 `index catalog is missing`；补齐后发现库构造器默认打开可选实体记录，与服务默认值不同，主动停止该次基准并校正配置。上述准备阶段的输出和源码保存在 `fixture-setup/`，不纳入性能比较。生产修改在这些 fixture 调整期间未变化。

两边输入导出 SHA-256 相同：`82fa529e816915cfe8efcc3881c8df30ca6b154f332c6cdc20ab168873eff39b`。恢复延迟包含客户端 100 ms 任务轮询。

本次恢复耗时增加 1.6%、CPU 增加 4.3%；采样 RSS 下降约 9.6%。这些都是单次样本，不能宣称稳定收益或把差异确定归因于页缓存。

CPU profile 中，`IndexHealthWithOptions` 的累计采样从 1.93 秒降到 1.70 秒；`runtime.gcDrain` 从 2.15 秒变为 2.24 秒。校验路径采样有所减少，整次恢复的墙钟时间没有同步改善。profile 的累计时间可能重叠，不应相加当作总耗时。

## 正确性验证

生产修改没有新增行为分支，复用已有的损坏检测、哈希兼容、记录不一致和跨租户/版本测试；新增测试代码仅用于测量完整校验行为。

最终验证及每个测试结果见 `validation-summary.json`、`unit.jsonl` 和各 `*-race.jsonl`：

- 全量 Go 单元测试：12 包、1,306 个顶层测试通过；`go vet ./...` 通过。2 个需要外部 S3 的用例在对象备份门禁中补齐。
- race：graph 136、query 141、HTTP API 184 个顶层测试通过；storage 聚焦选择的 231 个通过，覆盖深度索引校验、compact、快照、WAL、本地存储、读视图、恢复、GC、索引更新和任务。
- 实际 HTTP direct/WAL 门禁、写入后重启导出一致性通过。Python SDK 12 项通过；Go SDK 包包含在全量 Go 测试中。
- 独立 MinIO 的对象备份门禁通过，包括上传发布、恢复目标校验、重启重试、空目录发现备份、dry run、按需恢复、覆盖恢复、恢复演练和再次重启。

测试源码与当前工作区一致，`git diff --check` 通过。上述范围内未发现新的重大正确性回归。

本轮没有重跑 30 分钟持续负载、100K HTTP 矩阵、全部历史标签兼容性或受控操作系统冷缓存测量；没有测量混合吞吐的前后变化。验证通过仅适用于已执行范围，不构成不存在任何 bug 的保证。
