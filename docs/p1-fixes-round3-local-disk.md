修复第三轮审查确认的 3 项 P1，同时修复该轮缓存重新验证竞态。保留已有迁移、备份及前两轮修复；没有提交、推送或合并。

## 修复结果

| 问题 | 修复后的行为 |
| --- | --- |
| 恢复目录创建与普通写入竞争 | 两条路径共用受 `directoryMu` 保护的目录创建函数，统一处理父目录同步和失败屏障重试。 |
| 重启后旧任务一直 running | 独占本地目录时，旧实例的持久化租约不再被当作存活证明。统一任务和索引任务在宽限期后将遗留任务标记失败，允许重试；本进程已注册任务继续受到保护。 |
| WAL 启动恢复加载全部历史 | 在持有 WAL 进程锁、启动 writer 之前逐条校验和折叠记录；终态请求及时释放。保留 LSN、CRC、截断尾部、准备状态、owner 和重复身份检查，减少 CRC 和 payload 的整段复制。 |
| 缓存重新验证吞掉发布通知 | 保留读取 manifest 前的缓存代次；期间发生发布则重新读取，避免把旧 manifest 对应的缓存标记为不过期。 |

WAL 状态折叠逻辑集中到 `internal/storage/ingest_recovery.go`，与扫描和启动服务分开。存储层内部 `OpenIngestWAL` 改为接收恢复回调；完整原始记录收集仅用于测试。HTTP、SDK、Parquet/WAL 格式及 direct/WAL 写入语义不变。

### 内存边界

恢复内存取决于扫描位置仍未终结的请求、当前记录和解码临时分配，不再保留全部已完成历史。这不是 `QueueMemoryBytes` 对进程 RSS 的硬限制；如果真实未完成请求本身很大，或重启时大幅降低资源配置，仍需为真实待处理工作提供内存。本轮没有丢弃已受理请求，也没有改变日志回收条件。

### WAL 内存复现

1. **128 MiB 历史回归测试：** 相同测试在修复前源码中失败，观测到峰值堆增长 143,775,048 字节（约 137 MiB）；修复后定向运行通过，峰值增长 8,452,144 字节（约 8 MiB）。测试同时验证只重放未完成请求。
2. **原 640 MiB fixture：** 使用审查时相同的 3 个分段、640 条 accepted 和 639 条 finalized 记录的副本，在原先发生 OOM 的 512 MiB 限额下运行完整 `OpenIngestService`。恢复成功，GC 后额外保留堆 1,383,704 字节，实际 pending 1 条、1,049,067 字节。待处理请求发布为 v1，再次打开 WAL 后版本仍为 v1；容器退出 0，`OOMKilled=false`。

两项指标分别是采样峰值与 GC 后保留堆，不能混作同一种指标。它们是缺陷回归证据，不是整体吞吐或查询性能的基准结论。640 MiB 日志由生产帧编码器构造，本轮没有通过完整 HTTP 流程生成这些历史请求。
