## 1. 恢复后阻止旧导入继续写入

本地导入和死信重放任务创建时，在租户锁内读取当前代次，并把它写入持久化 checkpoint。任务开始执行、每次 Ingest 等待 WAL 前，以及取得租户写锁后，都会检查代次是否仍然匹配。最后一次检查受到读视图和写锁保护，恢复不能在检查与发布之间替换目录。

覆盖恢复或删除重建改变代次后，旧任务明确失败，不能把剩余批次写入新的租户数据。重试同样检查 checkpoint 的代次，进程重启不会绕过这个限制。没有代次信息的旧 checkpoint 只允许在初始代次重试；已发生租户替换时，需要创建新的导入任务。

沿用现有 checkpoint 字段和 Parquet 格式。多批导入仍按批发布；恢复可以替换先前已发布的批次，但旧任务不能跨过恢复继续执行并报告成功。

## 2. RecoverTenant 遵守 WAL 发布顺序

RecoverTenant 在取得排他读视图和租户维护锁之前，暂停该租户的新 WAL 受理，并排空已受理请求。已持久化的 PREPARED 先完成发布，recover 才检查和恢复孤立 commit，避免抢占 WAL 准备的版本。

HTTP recover 使用带维护名额的上下文。等待 WAL 时让出租户任务名额和全局执行名额，等待结束后重新取得；compact 因此可以运行并解除 commit-tail 背压。原请求的取消信号继续传递到等待过程。

真正的 WAL 损坏仍按原规则停止写入。本轮修复 recover 制造的版本冲突，没有新增损坏 WAL 的跨租户隔离机制。

## 3. 等待任务保留独立的内存并发名额

导入、死信重放、恢复和恢复演练，开始执行前先取得一组独立的常驻任务名额，默认共 4 个。任务让出执行名额等待 WAL 时，仍持有常驻名额；结束或取消时释放。因此队列中的其他导入不能陆续加载全部源文件并长期停留在内存中。

常驻名额在租户任务名额和执行名额之前取得，compact 不占用它，避免等待内存容量的任务阻塞解除背压所需的维护。

这是对同时保留大对象的任务数量设限，不是整个进程 heap 或 RSS 的精确字节上限。导入源仍使用现有 32 MiB 上限及批次解码方式。

## 实际验证

环境：OrbStack / Docker Engine 29.4.0，Go 1.25.14 Linux arm64；源码、数据和 WAL 使用独立 Linux 验证卷。unit/race/内存探针限制 4 CPU / 6 GiB，HTTP 门禁限制 2 CPU / 4 GiB。

| 验证 | 结果 |
| --- | --- |
| `go test -mod=readonly ./...` | 全部通过，包含 Go SDK |
| `go vet -mod=readonly ./...` | 通过 |
| storage/httpapi 定向 race | 61 个顶层测试通过，无数据竞争报告 |
| direct/WAL 真实 HTTP 门禁 | 两种模式均通过，覆盖图查询、来源治理、幂等写入、索引、任务、导出、本地备份恢复、recover、compact/GC |
| HTTP 混合请求与重启 | 4 写入、16 查询客户端，10 批 × 20 条；全部请求无错误，重启前后导出快照一致 |
| Python SDK 真实 HTTP | 12 项通过 |
| 源码一致性 | 测试后的产品源码与运行快照一致 |

新增四个聚焦回归：

- 导入三行、每批一行，在第二批之后安排覆盖恢复。恢复成功，旧导入失败；图只包含备份中的 seed。旧任务在重启前后均不能重试；没有代次的旧 checkpoint 也被拒绝，新导入可以正常完成。
- 注入直接提交的 manifest 失败和回滚删除失败，再注入 WAL 准备后的 manifest 失败。解除故障后 recover 先完成 WAL 版本 1，跳过旧孤立 commit；另一租户仍能写入，服务保持就绪。
- 12 个租户的 WAL 均受背压阻塞，启动 12 个导入。只有 4 份源文件加载；常驻名额全部占用时 compact 仍成功，取消退出后常驻、执行和队列名额全部归零。
- 全局只有一个执行名额时，持有 HTTP 同款维护上下文的 recover 等待 WAL；compact 成功解除背压，recover 和 WAL 均完成。

复跑一次原审查内存探针：12 个租户、每份源文件约 2 MiB，加载数量从修复前的 **12 份降为 4 份**。强制 Go GC 后，本次净 heap 增长为 **9,768,288 字节**，修复前为 **31,936,976 字节**。这是单次故障场景观察，不能当作进程内存上限或整体性能验收。

初次聚焦测试中，原有 `waitForTask` 辅助函数把预期的任务失败视为测试失败；改用已有的指定状态等待函数后通过。没有因此修改产品行为。
