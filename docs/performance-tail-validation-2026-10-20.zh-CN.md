# 维护窗口写入、索引追平与 30 分钟 Raft 增长负载复测（2026-10-20）

本轮比较上轮工作区候选 C3 与最终候选 C7，基础 HEAD 为 `adddc6c75cdc656e8a43309f40a4db32fe5f44f2`。实验在 2026-10-20（Asia/Singapore）的 OrbStack Linux/arm64 上执行，使用 Go 1.26.7；两边加入相同的私有 pprof 初始化。完整指标、请求指纹、源代码和二进制摘要见[机器可读记录](performance-tail-validation-2026-10-20.json)。[上轮六分钟结果](performance-tail-validation-2026-10-19.zh-CN.md)保留为历史记录。

单机写入 P99 从 **9.470 秒降至 3.948 秒**，约下降 58.3%；并发写入导致重建版本冲突的问题已修复。单机短暂 stale 的采样频率**没有下降**：131/327 → 134/327。Raft 严格对照的查询最大值从 **13.132 秒降至 5.584 秒**，仍有秒级长尾。

## 定位与保留的修改

1. **重建与 WAL 发布缺少统一顺序。** 旧实现按捕获的图构建索引，却在发布时要求图头仍等于该版本。并发 WAL 可以推进图头，使重建返回 `manifest ... changed while rebuilding indexes`。新增的直接重建回归在 C3 上稳定复现该冲突；C7 在短暂前台锁内捕获图并进入有序索引队列，保留 writer fence、读视图和 catalog CAS，允许同一代图头向前推进，随后按序追平。
2. **维护占用内存预算时，WAL 确认被索引同步回退拖住。** 本地 compact／重建期间合并有界追平需求，不保留中间图或占用前序维护所需的图构建预算。仅保存首次变更前的标量值和边端点；最多 8192 个变更引用，每项元数据的估计字节上限为 `min(维护预算 / 64, 8 MiB)`，后台工作总数仍最多 8 项。获得原有预算后才加载最新图，针对匹配的基准 catalog 增量更新；超过上限、schema 变化或基准不匹配时回退全量构建。显式 commit 仍等待自身索引工作。
3. **实际 compact 任务仍串行准备两种表示。** 可恢复任务路径现在与直接 compact 一样，在原有共享编码限额内准备分片快照和兼容全量记录；两者持久化后才发布 manifest，任务进度更新保持串行。
4. **Raft 维护屏障内有大量重复文件系统操作。** 密集堆栈观察到删除／祖先检查、目录 fsync、快照捕获接连占用应用屏障。维护发布仅在同一次应用屏障内复用祖先校验；独立目录同步有界并行，全部完成后才写提交标记。流式快照只为实际文件重建父目录，避免为 GC 留下的空版本目录逐一创建快照目录。

保留 before-image 回滚日志、文件和目录持久化要求、WAL committed 确认、Raft 读屏障及索引版本校验。没有改变持久化索引的 64 分片布局。

尝试过的 C4/C5/C6 写入 P99 分别为 2.677/2.763/2.620 秒，但 stale 为 161/155/158 次，均高于基线的 131 次，因此没有保留这些组合。最终撤销正向、反向索引同时准备的尝试，恢复主索引优先；追平元数据也不再额外解码旧实体页。保留了 compact 两种快照表示的并行准备。

Raft 使用 protocol 3、流式快照和 `snapshot_entries=5` 的频繁快照压力配置；恢复点包含原门禁中的其他租户与文件。两种部署的数据、批量和资源不同，不能横向比较。

原始增长工具会把预期 429 当作限流并丢弃该批次。原始记录轮共 1142 个尝试，其中 62 个未写入，并复现了 17.920 秒查询极值；该轮只用作诊断，**不与候选作严格性能对照**。

严格前后轮使用同一个客户端二进制和同一份记录计划，保留原查询参数、`min_version`、流式／分页／保存查询和维护顺序。429 使用相同逻辑批次、相同请求体每 5 秒重试，仍受原有 120 秒逻辑超时约束。两轮各完成 **85,570 个逻辑操作：1142 批写入、84,419 次查询操作、9 次维护**，逻辑请求和批次指纹一致。分页游标、任务轮询等控制请求由各轮服务端结果决定；物理 HTTP 数量可以因重试和轮询而不同。该对照是固定逻辑计划的延迟测试，不是最大吞吐测试。

## 单机结果

基线 `single-window-before`，候选 `single-window-after-v4`。两轮均完成 288 批写入、5760 次查询，客户端错误和索引采样错误均为 0。

| 指标 | C3 | C7 |
| --- | ---: | ---: |
| 写入 P50 | 3.116 s | 3.140 s |
| 写入 P95 | 4.178 s | 3.616 s |
| 写入 P99 | 9.470 s | 3.948 s |
| 写入最大值 | 9.472 s | 3.949 s |
| neighbors P99 | 65.745 ms | 72.795 ms |
| profile match P99 | 91.757 ms | 76.950 ms |
| range aggregate P99 | 98.136 ms | 91.994 ms |
| stale / 采样 | 131 / 327 | 134 / 327 |
| 最大索引版本差 | 8 | 8 |

基线最慢四批均在第一次 compact，候选最慢四批均在负载启动时。两边所有 stale 样本都带 `updating=true`：基线 127 次落后 4 个版本、4 次落后 8 个版本；候选分别为 128/6 次。最终负载采样已恢复 `ready`，catalog 和 manifest 均为 289，随后深度完整性审计均为 `ok`。**这修复了并发重建及维护确认阻塞，没有使异步索引始终新鲜，也没有降低本轮 stale 频率。** 当前命中分片仍需整片重写，Parquet 编码和 GC 仍有成本。

两轮写入 SHA-256、实体／边数量、schema、拓扑及边字段一致。16 个共享 cluster 的 `env/name` 字段因并发更新的合法到达顺序而不同，详细差异保存在 JSON 中；不能称两轮所有业务字段完全相同。单机客户端使用同一个二进制和固定 worker/round 查询选择，共三类查询各 1920 次；该客户端未记录逐查询 SHA。

单机服务生命周期资源包含预热、计时负载、审计和导出：CPU 为 592.024 → 604.400 CPU 秒，增加约 2.1%；cgroup 内存峰值为 4,364,832,768 → 4,642,705,408 字节，增加约 **6.4%**。进程 VmHWM 为 4,030,611,456 → 4,326,752,256 字节，增加约 7.3%。cgroup 峰值包含页缓存，不等于 RSS；此次延迟改善有内存开销。

## Raft 30 分钟严格对照

基线 `raft-strict-before`，候选 `raft-after`。两轮 1142 批均返回 200，全部逻辑请求完成，非预期操作错误为 0，61 次健康采样均为 ready。最终版本 1142，3,493 实体 / 5,901 边；业务字段、身份映射、schema、拓扑及边字段投影摘要一致。

| 指标 | C3 | C7 |
| --- | ---: | ---: |
| 所有查询中的最大值 | 13.132 s | 5.584 s |
| profile match P99 / 最大值 | 1.532 / 12.849 s | 0.909 / 3.128 s |
| min_version match P99 / 最大值 | 1.521 / 12.839 s | 0.853 / 2.958 s |
| path-filter traverse P99 / 最大值 | 1.402 / 10.634 s | 0.876 / 4.883 s |
| 逻辑写入 P99，含重试 | 7.516 s | 6.168 s |
| 逻辑写入最大值，含重试 | 50.137 s | 27.789 s |
| 429 重试次数 | 56 | 43 |
| 两次 GC 任务总耗时 | 157.992 / 150.532 s | 116.453 / 117.665 s |

查询极值下降约 57.5%，但**5.584 秒查询、27.789 秒重试后写入仍然存在**。基线全查询最大项是 `scan-entities-min-version`，候选是 `neighbors-host-out`，均在 GC 附近。GC 任务总耗时包含屏障之外的准备阶段，不能等同于查询阻塞时长。

没有只统计实际发起后的响应时间：相对原计划的起跑延迟 P99 为 14.971 → 1.576 秒；计入排队后的 profile 完成延迟 P99 为 15.009 → 1.877 秒，逻辑写入为 41.853 → 18.699 秒。所有请求完成时刻约为 1800.495 / 1801.115 秒，停止生成请求时没有取消慢操作。

基线结束后的资源采集脚本发生引号解析错误，未保存该轮 cgroup CPU/内存峰值。错误出现在已完成的负载、审计和导出之后；这些记录及请求指纹完整，三个节点均以 0 退出且没有 OOM。已核对前后 Docker 镜像和 CPU/内存限额相同。**Raft 不提供缺失资源计数的前后改善结论**，候选单侧资源保存在 JSON 中。

## 回归与恢复验证

- C3 直接重建回归在 0.483 秒内复现图头推进后的版本冲突；C7 同一回归连续三轮通过。维护阻塞用例同时覆盖极小预算的全量回退及默认预算的标量增量追平，并核对重复字段更新、边删除／重建和正反向结果。
- OrbStack 完整 `go test -json -p 2 ./...`：1827 条测试及子测试通过记录，无失败，7 条条件跳过（6 项可选对象存储集成、1 项 root 下不可表达的目录权限检查）。`go vet ./...` 通过。
- storage/ha 相关 race 两轮通过；补充 Graph 存储复制、顺序和旧视图不可变性用例的 race 两轮通过。
- 从单机候选目录克隆恢复副本，重建中确认写入版本 290；当 catalog 仍为 289 时，指定 `min_version=290` 的一次查询读到 `cpu=654321`，实测约 1.57 ms。随后在重建仍运行时 SIGKILL，退出码 137、非 OOM；重启恢复版本 290，自动修复的 ready 采样距强杀约 34.8 秒，深度审计通过。这包含默认 30 秒维护周期，不是 2 秒恢复承诺。
- 从 Raft 前后两轮的停止目录各克隆三个独立副本，分别直接通过存储层冷加载；同一轮三份完整快照均与该轮在线导出相同，不经过网关或请求转发。跨轮业务投影相同，运行时来源时钟等元数据不要求逐字节相同。

独立快照微基准在相同 1000 个有效文件和 5000 组空版本目录下，捕获中位数为 387.481 → 72.281 ms，单次分配约 75 MB → 9 MB。该测量在引入捕获优化时完成，最终候选的捕获实现未再改变；它不是全 Raft 应用屏障的耗时。

原始事件、冻结源码、私有 record/replay 工具、profiles、恢复文件和摘要在本地 `.workflow/perf-window-20261020/`；公开 JSON 保留主要数值和来源摘要。计时后仅扩展了直接重建回归测试，服务端生产 Go 文件保持与实测二进制源码一致。

本轮没有模拟物理断电、跨机网络分区或多组长期重复试验。剩余优化方向是降低索引整分片重写量，以及将大型 Raft 维护发布拆成有界、可恢复步骤；这些持久化流程改动未在本轮实施。不能把此次改善描述为消除了 stale、秒级长尾或给出了生产 SLA。
