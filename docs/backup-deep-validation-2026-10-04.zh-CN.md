# 备份自动化深度故障验证与修复

日期：2026-10-04。工作区 `GraphDB-raft-ha`，分支 `codex/raft-ha`。
本轮验证范围为外部备份 worker、单机内置 S3 备份，以及单组三投票副本的备份/恢复故障边界。没有提交、推送、发布或安装生产计划。
机器可读结果见 [JSON](backup-deep-validation-2026-10-04.json)，使用方式见[自动备份指南](backup-automation.zh-CN.md)。

## 发现与修复

在原始实现上，新增恢复回归复现四类缺陷：

| 问题 | 影响 | 修复 |
| --- | --- | --- |
| P1：多个租户共享一次轮询截止时间 | 首个租户长期排队耗尽预算，后续租户每轮都没有提交机会 | 每个租户单独取得完整预算；文档明确多租户总运行时间 |
| P1：状态读取/写入错误终止整个进程 | 一个损坏 JSON 或不能持久化的租户阻止其他租户备份，常驻进程退出 | 按租户隔离异常；损坏状态不覆盖，无法持久化时不受理新任务；其他租户继续 |
| P1：有效 JSON 中的状态字段不一致未被拒绝 | `idle` 与未确认任务并存时会丢弃旧轮次；受理结果缺少 ID 等情况可能重新提交 | 在读取时核对阶段、轮次、任务输入、受理结果/ID 和时间字段；不一致时停止该租户 |
| P2：指标发布错误阻断核心流程 | 仅指标目录不可写也会停止备份，并可能使提交前的安全标记停留在未知状态 | 状态 JSON 仍须先持久化；指标错误输出结构化日志，备份继续，提示监控指标过期 |

修复前的 Linux 和本机回归失败日志保留。修复后 11 项 Python 回归通过，包含五种有效 JSON 状态损坏、租户状态写入错误和原有六项受理/重试保护。CI 已有的备份恢复回归入口自动包含这些测试；本轮未运行 GitHub CI。

另修正文档对 RPO 的说明：`last_success` 是校验完成时间，长时间上传重试仍保留原捕获版本；数据年龄应核对任务结果或 S3 清单的捕获时间。

OrbStack Linux arm64，专属容器、网络、S3 桶/前缀和 Linux 数据卷；没有连接生产 S3 或 AWS 账号。后端复用 `graphdb:availability1-20261004`，508 份生产 Go 文件绑定到聚合 SHA256 `c0a4e33983c5730235a9897c65f11b52e5e5620781786a680557293ba310c093`。本轮没有修改 Go 后端或 Raft 协议。

最终按完整阶段汇总：单机 19 项检查，Raft 7 项检查，共 26 项。各阶段使用相同的最终 worker 源码和后端镜像；不将失败尝试整体改写为通过。

| 场景 | 结果与可观察行为 |
| --- | --- |
| S3 上传失败后重试 | PASS，源图写到版本 2后，仍上传原捕获版本 1，完成校验和演练 |
| 已完成计划的重新运行 | PASS，未到 `next_run` 时不增加备份受理 |
| 常驻运行、重启、竞争进程与权限 | PASS，进程锁排除同目录第二进程，UID 10001，状态 0600、指标 0644 |
| 备份、校验、完整演练受理后分别 SIGKILL | PASS，三阶段均认领原任务；原捕获版本保持 1，未产生重复演练 |
| 受理前 401/429 | PASS，没有服务器备份任务，退避后才重新提交；最终服务器任务仅一份 |
| 受理后的 400/409/503 | PASS，保持结果未知并认领已存在任务，备份 POST 仅一次 |
| 指标卷只读 | PASS，出现 `backup_automation_metrics_error`，状态继续持久化，备份/演练完成；指标降级明确可见 |
| 前序租户一直显示 queued | PASS，后续租户完成备份；解除阻塞后前序租户认领原任务完成 |
| 单个租户状态 JSON 截断 | PASS，原文件未改写，该租户零受理，其他租户完成；常驻模式持续报告错误并保持运行 |
| S3 payload 位翻转、payload 删除、manifest 删除 | PASS，校验失败时不记录成功、不进入完整演练；恢复原对象后从原备份重试成功 |
| 服务器 GC 删除已知任务历史 | PASS，worker 报错且不重新捕获，成功时间不更新；此场景按契约需要人工核对 |
| Raft 丢失 202并切主 | PASS，限定重试预算内认领原任务、校验和演练完成，保持版本 1与一次备份 POST |
| Raft 演练隔离与计划重开 | PASS，生产版本 2的前后实体保持可读，临时目标清理，下一周期未到时不提交 |
| Raft 丢失多数派后恢复 | PASS，期间报错并保留已知任务 ID，恢复后完成原轮次，没有新捕获 |
| Raft 分别丢失校验/完整演练响应 | PASS，两种情况均认领原任务，演练任务总数仍为两个 |

HTTP 401/429 和受理后的错误响应通过测试代理注入，测试的是实际 SDK/HTTP/持久状态边界，不代表验收了生产认证系统。queued 状态通过代理延迟可见性模拟；S3 对象删除/损坏、进程 SIGKILL、服务器任务 GC和 Raft 节点故障则实际执行。

## 失败记录与验证限制

第一轮运行检查发现“只修改空指标卷权限”未构成持续只读：容器挂载空卷时重新初始化目录权限。改成实际只读挂载后，该故障通过；原失败日志保留。

第二轮在 19 项单机检查通过后，Raft 换主恢复遇到一次 10 秒 HTTP 客户端超时。该尝试结果仍为 FAIL。后续按持久计划在 180 秒总恢复预算内重试完成，测试继续确认原任务/版本和受理次数；没有把一次就绪成功或延迟返回当作已完成备份。

第三轮的守护进程断言恰逢测试配置的 60 秒计划到期，新周期正确触发。调整该检查的计划窗口为 3600 秒，避免测试过程把正常到期调度误判为重复受理。最终分阶段复验保留单机已通过证据并补齐 Raft 故障阶段。

初次 Docker Go 检查因模块缓存不完整和容器缺少代理 CA信任，停在 setup阶段；随后使用已有受信任的 OrbStack Linux 原生 Go环境完成竞争检查和完整 S3门禁，没有关闭 TLS验证。

分片 router/迁移与 worker 组合、跨宿主机、生产 timer实际触发、真实 AWS IAM/版本控制/Object Lock/生命周期、大图容量和性能矩阵仍未验收。外部 worker 保留仍由显式 S3生命周期配置；本轮没有增加远端自动删除或生产自动恢复。

此前[可用性与滚动升级长测](availability-rolling-validation-2026-10-04.zh-CN.md)的 Raft 失败仍然有效。本报告的 PASS限定于备份故障恢复，不构成无中断或低延迟 SLO、新的混部资格、全产品验证或正式发布资格。
