# 本地磁盘版：第三轮性能优化

2026-09-17。工作区 `/Users/livesite/Documents/GraphDB-local-disk-v2`，分支 `codex/local-disk-v2`。基于包含六轮 P1 修复的当前代码开展优化，保留原工作区和全部既有改动，未提交或推送。

## 热点与改动

重新编译当前版本，在 OrbStack 中采集 20 秒 CPU profile 和混合负载前后的分配差值。诊断使用 10002 实体 / 5001 边、同步 WAL、4 写入和 16 查询客户端，每写客户端间隔 2 秒；诊断时关闭自动维护，避免把后台维护混入查询热点。

当前调用栈中，带索引的排序查询占累计 CPU 样本约 34.85%，`runtime.duffcopy` 占 14.10%。过滤、取字段、聚合和 Top-K 比较不断按值传递较大的 Request/Entity；字符串排序还对已是字符串的值反复调用 `fmt.Sprint`。这些占比有重叠，不能相加作为可获得的加速比例。

本轮采用两项直接调整：

- 内部同步、只读的过滤、字段访问、聚合和排序函数接收指针，避免候选遍历过程中反复复制整个结构。Top-K 只有保留候选时才复制实体值，堆中仍保存独立的结构值。
- 普通字符串相等比较直接比较字符串；排序复用已有 `filterText` 的字符串路径。数字继续采用原数值比较，其他类型保留原反射或格式化规则。

返回给调用者的实体仍执行原有深复制。排序后的稳定 ID 次序、投影与聚合输入、游标、成本计数和取消检查保持原逻辑。没有增加缓存、对象池、依赖或后台工作，也没有修改磁盘格式、同步落盘和 WAL 发布顺序。

18 个变更文件都在 `internal/query` 中，多数是内部函数签名的调用点调整。新增一个排序查询基准，复用已有行为测试保护上述边界。

## 聚焦基准

OrbStack，Go 1.25.14 Linux arm64，4 CPU / 6 GiB；前后各运行一次，每个基准测量 2 秒。相同的新基准文件也复制到优化前的隔离源码中；优化前产品代码保持原样。

| 场景 | 优化前 | 优化后 | 变化 |
| --- | --- | --- | --- |
| 1 万实体、字段索引后按字符串排序 | 1.128 ms/op | 0.417 ms/op | −63.1% |
| 上述场景分配字节 | 414998 B/op | 87793 B/op | −78.8% |
| 上述场景分配次数 | 20831/op | 383/op | −98.2% |
| 5 万实体、字段索引后的聚合排序 | 7.369 ms/op | 4.119 ms/op | −44.1% |

字符串基准让 ID 访问顺序与 hostname 排序方向相反，候选频繁替换 Top-K，排序比较成本较高。它能稳定复查这一热点，不代表所有线上查询都能提速 63%。其他现有查询微基准的耗时变化约为 −8.5% 至 +5.0%，分配次数不变；单轮结果不足以解释这些较小差异。

- 同一份已停止的种子库，10002 实体 / 5001 边，复制到独立 Linux 卷目录。
- 4 写入、16 查询客户端，每批 20 实体，每写客户端间隔 2 秒；每场预热 5 秒、测量 30 秒。
- direct 按前→后运行，WAL 按后→前运行；每场均启用既有自动维护配置。
- 服务与负载工具共用 4 CPU / 6 GiB，测试和构建已完成，不与测量同时运行。其他 OrbStack 工作负载保留，未清空操作系统页缓存。

## WAL 尾延迟与导出补查

只补查一对 WAL 场景，顺序改为前→后，其余资源、种子库、客户端和写入节奏相同。每场预热 5 秒、测量 60 秒；各发布 120 批，版本增加 120，所有请求无错误。随后连续导出 5 次，每次均验证实体/边数量、最新版本和快照哈希一致。

| 指标 | 优化前 | 优化后 |
| --- | --- | --- |
| 混合操作/秒 | 2726.93 | 2840.89（+4.18%） |
| 服务 CPU 时间 | 90.18 秒 | 82.20 秒（−8.85%） |
| 写入完成 p95 / p99 | 187.934 / 208.329 ms | 193.631 / 196.168 ms |
| WAL 受理 p95 / p99 | 23.297 / 29.093 ms | 26.872 / 28.851 ms |
| WAL 受理后到可读 p95 / p99 | 175.887 / 187.933 ms | 174.703 / 177.541 ms |
| 窗口峰值 RSS | 609.20 MiB | 847.58 MiB |
| 窗口 RSS 中位数 | 344.87 MiB | 352.09 MiB |
| 窗口末尾 RSS | 418.79 MiB | 441.14 MiB |
| 连续导出中位数 | 70.84 ms | 70.70 ms |

先前较大的 WAL p99 增幅未复现，但这次受理 p95 上升约 15.3%；两次主/补查的增减方向不一致，**WAL 受理尾延迟门槛仍为未定**。连续导出中位数基本持平，不据此保证所有单次维护操作的耗时。

本次 RSS 峰值增加约 39.1%，不能宣称满足峰值 RSS 增幅不超过 10% 的目标。采样与服务日志对齐后，两者的峰值都处于测量约第 55 秒、v135 自动 compact 附近，结束时已经下降；中位数增加约 2.1%、末尾增加约 5.3%。这些证据把峰值范围缩小到并发维护阶段，但没有采集该瞬间的分配栈，不能进一步断言具体分配来源，也不能仅凭末尾下降证明不存在内存问题。

本轮结论：保留经过语义和并发检查的查询热点优化。聚焦基准有明确收益，三组混合观察的服务 CPU 时间均下降约 5%–9%，吞吐小幅增加约 1%–4%。**不宣称整体性能验收通过**；RSS 峰值、WAL 受理尾延迟，以及少量维护样本仍不足以验收原定全部门槛。
