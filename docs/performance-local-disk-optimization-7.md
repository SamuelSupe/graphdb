# 本地磁盘性能优化，第七轮

日期：2026-09-17。工作区 `GraphDB-local-disk-v2`，分支 `codex/local-disk-v2`。

## 结论与实现

本轮优化有序实体查询的 Top-K 选择：在单次查询内复用堆中实体的首个排序字段，减少重复字段查找及时间字段格式化。10K 实体的现有排序基准平均耗时下降 **12.2%**，分配量基本持平。混合 HTTP 吞吐的两次观察方向不一致，WAL 受理尾延迟仍有不确定性，**本轮不宣称整体吞吐提升或全部性能验收通过**。

只修改 `internal/query/bounded_entities.go` 一个生产文件：

- 缓存随实体入堆、交换、替换和移除同步更新；最终排序也使用同一交换逻辑，避免键与实体错位。
- 只缓存首个排序字段，最多 4,096 个键。更深分页沿用按需读取字段，避免缓存量随分页窗口和排序字段数相乘。
- 保留升降序、多字段比较、缺失字段处理和 ID 平局规则。缓存仅在请求内存活；返回结果仍经过原有深复制，保持与共享图数据的隔离。

在已有 `TestBoundedResultsMatchesFullSort` 中扩展数据和用例，与独立完整排序结果比较，覆盖多次堆替换、升降序、多字段、空窗口、深分页回退、identity、labels 和时间字段。已有查询分页、聚合和返回值隔离测试继续使用。

## 热点依据与测量环境

OrbStack Linux arm64、Go 1.25.14、4 CPU / 6 GiB，独立 Linux 本地卷。before 是本轮开始的完整工作区，after 只增加本轮实现和回归测试。驱动中的 `graphdb-main` / `main-local` 指 before，**不是 Git main**。

修改前单独采集了 20 秒 CPU profile：`boundedEntities.Add` 累计占采样 CPU 的 10.47%，`entityValue` 占 7.99%；二者存在调用关系，不能相加。选择复用排序键是针对这条已观察到的调用链。

没有清除 OS 页缓存，没有停止其他 OrbStack 工作负载。性能运行与本轮测试 gate 错开；环境仍不是专用独占机器。遵循减少比较轮次的要求，采用一次 60 秒代表性比较，针对异常增加一次反向 30 秒诊断，没有扩大为完整容量矩阵。

## 性能结果

### 排序基准

现有 `BenchmarkMaterializedFieldIndexStringSort10K`，每版各运行 1,000 次。10,000 个实体，字段索引筛出 1,250 个候选，按 hostname 排序并投影，返回 20 项；数据顺序会触发较多堆替换。

| 指标 | before | after | 变化 |
| --- | ---: | ---: | ---: |
| 平均耗时 | 404,335 ns/op | 354,833 ns/op | **-12.2%** |
| 分配字节 | 87,792 B/op | 87,818 B/op | 基本持平 |
| 分配次数 | 383 allocs/op | 382 allocs/op | -1 |

这是特定排序查询的单组微基准结果，不能外推为所有查询或端到端性能提升。

### 60 秒真实 HTTP 混合负载

使用同一个停止状态的种子目录，10,002 实体 / 5,001 边；WAL sync，flush 100 ms，4 个写入客户端 / 16 个查询客户端，每个写入客户端间隔 2 秒，每批 20 项。预热 5 秒，测量 60 秒，顺序 before → after。两版各发布 120 批、版本增加 120，全部请求成功；每版在运行中完成 2 次后台 compact、1 次 GC。

| 指标 | before | after |
| --- | ---: | ---: |
| 混合吞吐 | 3,000.91 ops/s | 2,981.71 ops/s |
| 服务进程 CPU 用时 | 83.20 s | 81.32 s |
| 采样峰值 RSS | 609,796,096 B | 602,460,160 B |
| 生命周期 RSS 高水位 | 1,430,503,424 B | 1,347,063,808 B |
| 峰值文件句柄 | 32 | 34 |
| 磁盘读取量 | 6,131,712 B | 147,456 B |
| 磁盘写入量 | 415,715,328 B | 414,031,872 B |
| 文件及目录同步次数 / 失败 | 4,754 / 0 | 4,755 / 0 |
| 同步累计耗时 | 6.549 s | 6.638 s |

吞吐下降 0.6%，CPU 用时下降 2.3%，均不作为稳定的整体提升。磁盘读取量受页缓存状态影响，不用于推断实现节省了相同比例的 I/O。

### 维护及反向诊断

60 秒负载结束后，每版完成 export、compact、本地备份、覆盖恢复和重启；本版恢复后和重启后的完整导出均与本版备份前相同。

| 操作 | before | after |
| --- | ---: | ---: |
| export | 75.40 ms | 76.94 ms |
| compact | 606.87 ms | 650.70 ms |
| 本地备份，客户端等待 | 421.38 ms | 520.31 ms |
| 本地备份，持久化任务起止时间 | 416.06 ms | 426.63 ms |
| 覆盖恢复 | 4,221.99 ms | 4,352.91 ms |
| 维护采样峰值 RSS | 669,913,088 B | 731,959,296 B |
| 维护同步次数 / 失败 | 756 / 0 | 756 / 0 |

额外诊断使用相同种子、同一配置，顺序 after → before，预热 5 秒、测量 30 秒，再执行同一维护流程。各发布 60 批，全部成功，均完成 1 次后台 compact 和 1 次 GC，恢复与重启内容检查通过。

- 混合吞吐 before 2,586.95、after 2,765.38 ops/s；查询 p95/p99 比 before 更低。与首轮方向不同，因此整体收益仍未定。
- compact 为 624.77 → 603.72 ms，restore 为 4,247.15 → 4,214.39 ms，没有持续复现首轮 compact 退化。
- 备份客户端为 417.08 → 515.77 ms；任务自身为 405.22 → 432.44 ms。两轮 after 均比 before 多等待一个 100 ms 轮询周期，放大了端到端差值；实际任务差异分别为 +2.5% 和 +6.7%，不能把端到端约 +24% 全部归因于实现退化。
- WAL accept 客户端 p95 为 24.207 → 26.120 ms，p99 为 27.232 → 33.802 ms，尾延迟偏高再次出现。日志显示高值集中在少数同时受理的批次。首轮服务端受理 p95 为 15.107 → 14.667 ms，与客户端方向不同，但服务端 p99 为 16.303 → 23.031 ms；短诊断的服务端尾延迟也更高。当前证据无法区分查询调度、GC、同步 I/O 波动与改动间接影响，**WAL 受理尾延迟保持未定，不认定已满足“不回退超过 5%”**。

单次进程重启查询为 41.63 → 50.25 ms。没有控制 OS 页缓存，且每版仅一个样本，不将它作为冷读 p95 或性能验收依据。

## 正确性验证

- 全量 `go test ./...`：12 个包、1,306 个顶层测试通过。两个外部 S3 测试随后由独立对象存储 gate 补跑通过。`go vet ./...` 通过。
- race：完整 query 141 项、存储边界 208 项、完整 HTTP API 184 项顶层测试通过。存储覆盖 Parquet、目录独占、读视图、恢复、WAL、compact、GC 和索引任务；该阶段跳过的一个外部 S3 测试随后补跑通过。
- 实际 HTTP release gate：direct/WAL 写入及并发查询、图查询、分页、来源治理、租户隔离、索引更新、scan/export、compact、备份恢复和重启通过。Python SDK 12 项通过，Go SDK 包包含在全量测试中。
- 独立 MinIO gate：multipart 发布、禁止 manifest 重定向、重新打开后的校验恢复在 race 下通过；HTTP 完成对象存储备份、全新目录发现及 dry-run、恢复、覆盖恢复、恢复演练与重启校验。
- 当前生产代码和测试文件的 SHA-256 与已验证源码一致；`git diff --check` 通过。本轮创建的 MinIO 容器和网络已清理。

上述检查没有发现重大正确性回归。本轮没有执行 30 分钟 soak、100K HTTP 容量比较、受控 OS 冷缓存或完整历史 release 兼容矩阵；不以本轮结果替代这些验证，也不能据此保证不存在所有重大 bug。
