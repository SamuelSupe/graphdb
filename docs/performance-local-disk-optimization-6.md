# 本地磁盘性能优化，第六轮

日期：2026-09-17。工作区 `GraphDB-local-disk-v2`，分支 `codex/local-disk-v2`。

## 本轮改动

快照解码从“读取整个 Arrow 表，再构造图”改为每批读取 4,096 行。这样完整 Arrow 表不再与恢复出来的图同时存活。只修改 `parquet_snapshot_record.go` 一个生产文件。

复用现有 Parquet 读取接口和解码并发限制，保留逐行身份检查、字段还原、规范化和最终内容哈希校验。新增批次间取消检查及流式读取错误检查；返回前释放批次、解码名额和文件 reader。写入格式、manifest 发布顺序及同步落盘策略不变。

在已有 `parquet_decode_test.go` 中增加一项行为回归：在第二个行组触发读取错误或取消，必须返回对应错误、关闭 reader，并允许后续解码取得名额。它用于防止流式读取忽略中途错误或泄漏资源；已有跨行组完整内容回归继续使用。

## 性能结果

环境为 OrbStack Linux arm64、Go 1.25.14、4 CPU / 6 GiB，文件位于独立 Linux 本地卷。before 是本轮开始的完整工作区，after 只包含本轮实现及回归测试；工具中的 `graphdb-main` / `main-local` 代表 before，**不是 Git main**。

### 快照解码

| 指标 | before | after | 变化 |
| --- | ---: | ---: | ---: |
| 10K 实体，20 次基准平均耗时 | 87.02 ms | 86.49 ms | 基本持平 |
| 10K 实体，B/op | 215,077,694 | 202,348,620 | -5.9% |
| 10K 实体，allocs/op | 516,785 | 530,297 | +2.6% |
| 100K 实体，独立进程解码耗时 | 904.45 ms | 858.38 ms | -5.1% |
| 100K 实体，进程峰值 RSS | 1,283,846,144 B | 692,633,600 B | **-46.0%** |
| 100K 实体，累计分配字节 | 1,765,641,576 B | 1,905,681,640 B | **+7.9%** |
| 100K 实体，mallocs | 4,906,788 | 5,044,095 | +2.8% |
| 100K 实体，峰值文件句柄 | 7 | 7 | 相同 |

主要收益是大快照解码的峰值内存，由约 **1.20 GiB 降至 0.65 GiB**。分批处理增加了部分临时分配，因此不能宣称所有规模的累计分配都下降，也不能把单次解码结果当作整体吞吐提升。

100K 文件由 before 一次生成，两版读取同一个文件，并各自在全新进程中解码一次。内置内容哈希校验通过，租户版本及 100,000 个实体数量符合预期。RSS 每 10 ms 采样并读取进程 VmHWM。文件 SHA-256：`3c8dfa7bbfc856af24c69b160be638353b1946ff6b4758ad8fa0beb02af48ed0`。

没有清除 OS 页缓存，before → after 的顺序可能影响耗时；这里的稳定设计收益是避免整表与图同时存活，46% 是该负载的一次实测值。

### 真实 HTTP 维护和恢复

只运行一组 after → before，使用同一个已停止的数据库副本，10,002 实体 / 5,001 边，关闭自动维护以隔离手动操作。两版依次完成 export、compact、快照备份、覆盖恢复和重启，完整导出均保持一致。

| 指标 | before | after |
| --- | ---: | ---: |
| compact | 270.10 ms | 260.00 ms |
| 本地快照备份 | 731.93 ms | 728.45 ms |
| 覆盖恢复 | 4,204.46 ms | 4,248.82 ms |
| 维护窗口 CPU 用时 | 9.16 s | 9.24 s |
| 维护窗口采样峰值 RSS | 358,055,936 B | 358,268,928 B |
| 进程生命周期 RSS 高水位 | 428,875,776 B | 387,870,720 B |
| 文件及目录同步次数 / 失败 | 626 / 0 | 626 / 0 |

10K 完整恢复耗时增加 1.1%，维护窗口内存基本持平。恢复还包含索引重建等阶段，不能把纯解码的内存改善外推为整次恢复减少 46%。

首次 export 单样本为 61.49 → 72.55 ms。针对这个波动额外做了一次小诊断：每版重启并预热后连续导出 10 次，中位数为 68.48 → 66.02 ms，最大值为 72.14 → 75.11 ms；每次内容一致。未复现持续的导出退化，两版该窗口均无磁盘读写。全部样本保留，不择优替换首次记录。

重启首个查询单样本为 58.49 → 30.82 ms；它仅是进程冷启动检查，不能称为受控冷读 p95。本轮没有重跑混合吞吐比较矩阵。

## 验证

- 全量 `go test ./...`：12 个包、1,306 个顶层测试通过；两个外部 S3 测试在此阶段跳过，随后由对象存储 gate 补跑通过。`go vet ./...` 通过。
- 存储 race：208 个顶层测试通过，覆盖快照、读取失败、取消、compact、恢复、WAL、GC、目录独占、读视图和索引任务；一个外部 S3 测试随后补跑通过。
- 完整 HTTP API race：184 个顶层测试通过。
- 实际 HTTP release gate：direct/WAL 写入与并发查询、来源治理、租户隔离、索引、分页、export、compact、备份恢复及重启通过。Python SDK 12 个测试通过；Go SDK 包包含在全量单测中。
- 独立 MinIO gate：multipart 发布、禁止 manifest 重定向恢复、重新打开后的恢复测试在 race 下通过；HTTP 完成对象存储备份、全新目录发现及 dry-run、恢复、覆盖恢复、恢复演练和重启校验。已清理本轮创建的容器和网络。
- 两份保留的 10K 实体 / 5K 边历史快照，分别含 1 个与 5 个行组，均成功解码并通过内置内容哈希检查。既有宽实体/宽边跨行组回归及本轮失败/取消回归通过。

上述运行验证没有发现重大回归。

没有运行本轮 30 分钟 soak、100K HTTP 容量矩阵、受控 OS 冷缓存或历史 release tag 的完整兼容脚本。本轮只对已读取的旧单行组与当前多行组快照进行直接兼容性验证。测试通过不能证明不存在所有重大 bug。
