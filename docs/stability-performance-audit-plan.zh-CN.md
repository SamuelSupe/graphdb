# v2.6.5 稳定性与性能审计复核及修复计划

基线为本地 `main` 的 `5f57ca2`。编号沿用原审计。同组内有多个子项时，分别记录证据和验证结果。性能项的验收使用同一数据、负载和持久性设置，比较耗时、分配量或 I/O，并检查结果一致性。

## 顺序

1. 修复复制回滚、对象缓存和索引 GC，再处理 HA 回执和分片拓扑。验收覆盖回滚重试、缓存代次、在线索引引用、历史回执及成员替换。
2. 修复 WAL、清单恢复、Parquet、分片导入与转换、HA 维护、查询和 HTTP。验收覆盖压力上限、失败恢复、历史数据兼容及请求完成语义。
3. 修复 SDK、路由、GraphQL、图合并、维护和 CLI。验收覆盖调用方可见结果、资源关闭和错误传播。
4. 按读写放大、共识屏障、缓存与查询热点推进性能项。验收保留快照兼容、Raft 持久性和查询结果顺序，先跑定向测试，再跑受影响的包和集成测试。运行验证在 OrbStack Linux 执行。

## 运行证据

- OrbStack Linux arm64 上，包含恢复 GC 的修订通过全仓 `go test -p 1 ./... -count=1` 和 `go vet ./...`。本轮 HA、分区及 Raft 的定向 race 检查覆盖快照预算、GC 和 WAL 换主恢复。此前分区和路由包完整 race 测试通过。多轮九节点 race 回归覆盖固定读视图、提交、转换、换主、地址更新、GC 恢复和 WAL 回执。
- 加入非分片回执保留期、旧队列别名回归和 SDK 修复后，OrbStack 全仓 `go test -p 2 -timeout 15m ./... -count=1`、普通 HA 定向 race、Go SDK race 和 `go vet ./...` 均通过。
- 普通 HA 协议 13 集成回归验证了受理队列在只读一个待决对象、不扫描历史目录的情况下恢复，并在发布后持久化空队列。分片列表集成回归覆盖了 purge 之后的分页。
- 非分片 HA 三节点回归覆盖协议升级后的历史回执迁移、重复 flush、原身份重试、改包冲突、`wait=committed`、幂等别名、换主及在新卷恢复快照。回执的受理 LSN、受理时间、结束时间和结果版本保持一致。在新卷上回收一份历史控制回执后，原先超限的快照可以在同一字节预算内生成。
- 同一个三节点 WAL 集群保留同一图版本，迁移 96 条历史批次回执后，重复控制对象从 96 降至 0，未压缩快照从 1,822,720 降至 1,711,616 字节，压缩快照从 53,559 降至 46,799 字节。迁移后原状态 URL 仍可查询。
- 单独的三节点 Raft 状态机回归在超限时拒绝普通提案，允许同一内容经清理提案提交。随后生成合规快照并恢复普通写入。该场景启用 race 检测连续通过三次。
- 三节点普通 HA 与租户分片均复测了硬清除、换主、回收旧代已完成及排队回执、迟到 flush、复用批次 ID 和副本重开。原实现的普通 HA 用例在换主后仍能直接读到两条旧代控制回执。修复后原 URL 返回 404，新代回执和新图仍可读。另一个三节点测试以固定 16 KiB 应用快照预算复现普通写入被拒，明确授权的硬清除完成后自动恢复写入。
- 九节点分片回归在事务发布后暂停收尾，令一个 Raft 组触及固定 512 KiB 应用快照预算。修复前批量收尾返回快照超限，修复后原请求可重放并释放活动事务，新的普通提交仍被拒。通过 Router 启动有界 GC 后，旧图页被删除，当前实体存留，并在同一预算内生成新快照和恢复普通提交。另用协议 5 验证了逐分区收尾和 GC。WAL 回归用 16 KiB 上限覆盖接续提案降级，前一批进入终态，后一批保持待决，写入恢复并换主后仅发布一次。
- 重跑 64 MiB、8,200 入边的九节点场景时，快照超限出现在删除事务发布前。活动事务停在版本 17 的 `preparing`。检查两个数据组的持久状态时，256 个分区都已准备，home 仅记录 255 份准备回执。原键在 Router 上重试仍返回 503。固定 512 KiB 的独立故障注入进一步验证，数据分区已有持久准备结果时，重放原 `prepare` 和在 home 登记 `prepared` 都被快照上限拦截。
- 修复后，512 KiB 故障注入验证单分区与批量重放均可返回持久准备结果。混入未准备分区的批次、摘要不符的重放及缺回执的发布继续被拒。释放暂停后，原幂等请求发布一次，GC 后回到同一快照预算并恢复普通写入。以同一 64 MiB 预算重跑 8,200 入边场景，home 换主后原键经 Router 发布版本 18，重放的版本及摘要一致，边数归零。home 在发布收尾后仍报超限。之后经 GC 生成合规快照并恢复写入，从提交 GC 到下一次普通写入成功用时 12.87 秒。这是一次本地集成测量。
- 独立故障注入在数据组 prepare 落盘前拦截请求，再触发 512 KiB 快照上限。超限期间新 prepare 被拒，原事务仍活动，图 GC 启动也被拒，版本保持为 1。测试恢复原快照容量后，原幂等请求只发布版本 2。该场景定位了准备确实未齐时的恢复缺口。
- 修复后，协议 13 九节点分别用普通提交和已受理 WAL 验证了缺少准备结果的恢复。只有一个数据组触及 512 KiB 快照上限。恢复 GC 启动后切换 home Leader，活动事务和 GC 身份均保持一致。普通提交保留了健康数据组原有的准备根，WAL 回执在 GC 期间保持 `accepted`。旧页被删除，固定视图仍能读取旧行。两笔原请求分别恢复并只发布一个版本，快照预算保持不变。
- 另在九节点普通提交中，仅令 home 组触及 512 KiB 上限，时机在事务开始后、参与分区登记前。登记被拒后启动恢复 GC，切换 home Leader 并回收旧页，原幂等请求发布一次。
- 有效图页单独超出 512 KiB 预算时，恢复 GC 保留了当前页和活动事务。自动完成一轮后，观察期内没有重复启动。通过原图 GC 接口可为同一事务再运行一轮，图版本和已保留页保持一致。
- 另用普通提交验证了两条边界。待收集固定视图的普通 GC 可沿用原任务 ID 进入恢复，原提交随后成功发布。当数据组仍运行协议 12 时，自动恢复不启动，当前图版本和已准备分区的回执保持原值。
- 协议 13 非分片三节点以不同批次 ID 重复写相同实体，图版本保持为 1，终态控制回执为 0。基线未压缩快照为 57,856 字节。新增 64 条无别名权威回执后为 1,174,016 字节，再新增 64 条权威回执及其 64 条幂等别名后为 3,402,240 字节。以 3 MiB 快照上限重启后，Raft 拒绝新 WAL 受理并返回 `503 raft_unavailable`，最早的原回执仍能查询。该测试控制了图内容，使用 128 个新增批次。
- 非分片 HA 为新 WAL 批次启用终态期限后，三节点 race 回归覆盖待决别名复用、不同正文冲突、终态回执的 Leader 切换、回收后批次和别名重新受理、旧状态地址与迟到清理指令隔离，以及保留老回执和待决批次。启用前已受理的待决别名还验证了配置切换后保持原 LSN、只发布一次，修复前会生成第二条受理并在 flush 中产生存储冲突。另一组三节点 race 回归保持图版本不变，以 25 条终态回执和各自的别名触及 512 KiB 快照门禁。后台到期后回收对应的接入和租户侧记录，在原预算内生成快照并恢复新受理。

## 剩余工作的验收顺序

1. STAB-04 保持默认永久查询和幂等重试。接入可恢复的分段发布，使 Raft 确认归档后再回收热回执，并校验新旧读路径一致。独立计量历史段与活动快照的空间，快照安装须在同一检查点拿到全部引用段并校验完整性后发布。再验证中断重试、实体图转换、租户迁移、落后节点追平和空卷加入。百万批次验收使用永久保留策略，测量历史容量、活动快照预算、追平耗时和恢复后的查询与重试。
