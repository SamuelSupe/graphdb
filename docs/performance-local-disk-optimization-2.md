# 本地磁盘版：第二轮性能优化

2026-09-16。实现位于 `codex/local-disk-v2` worktree，未提交或推送。
本轮基于[上一轮热点诊断](performance-local-disk-opportunities.md)，保留同步落盘、版本及游标契约。

## 实现

- **目录哈希复用**：`GetScanCursorBinding` 仅从内部已验证目录取得版本和哈希；
  不再为每个首屏游标复制整个目录、规范化内容并计算哈希。公开可修改的 `IndexCatalog`
  仍通过 `PinScanCursor` 重新计算哈希。同版本索引重建后，新绑定使用新哈希，旧绑定保持原值。
- **HTTP 实体编码**：实体详情、实体列表和 query 响应（含 path 中的实体）复用 `Entity.JSONValue()`，
  由外层编码器直接输出字段，避免每个实体先生成 JSON、再由外层检查和压缩。
  `Entity.MarshalJSON` 和持久化编码未改动；保留 labels、来源、转义、空数组和 null 语义。
- **实体分页顺序缓存**：每个驻留只读图首次建立一次 `(shard, ID)` 顺序，后续从游标位置搜索。
  顺序与具体图实例绑定，随提交、恢复、失效或驱逐替换；不按版本号单独复用。
  建立前在 ReaderCache 的字节预算中预留空间；预算不足继续使用原来的有界堆路径。
  并发请求共用一次构建，取消不留下永久失败条目，返回实体仍是独立副本。
  HTTP 已固定到历史目录的后续页继续走原来的持久化读取路径；边分页仍使用原有选择逻辑。
- **Parquet 物理布局**：打包实体按 `(shard, ID)` 写出，让 shard 的行组 min/max 能过滤无关分片。
  仅排序临时位置数组，不修改逻辑页的实体顺序或内容哈希。旧文件继续可读，新布局随正常写入或重建产生。
- **增量索引分配**：直接借用内部不可变图中的实体字段，页只拥有自己的切片；
  准确传播 `hashCanonical`，避免对已规范化内容再次 JSON 往返。仍校验非规范化数值等输入。
  本轮没有改变 WAL 批量受理、发布、终态、目录同步或 manifest/catalog 发布顺序。

## 对比方法

运行一轮完整修改前后比较；发现 WAL 受理尾部疑点后，只补查 WAL 混合负载。
未扩展为三实现、多次轮换矩阵。

- 修改前二进制：`d59dde0b007c4eeb6c6731faa64831926f674a5f64c80acdad4ba205222ba32a`。
- 修改后二进制：`05a5bf3babad2fa0e280f212155dfb1efb5bb326334bd5300900168806512016`。
- 固定 10002 实体 / 5001 边；4 写入、16 查询客户端；每批 20 实体，每写客户端间隔 2 秒。
- 每场预热 5 秒、测量 30 秒；direct 按前→后运行，WAL 按后→前运行。
- 同一份已停止的种子数据库复制到独立 Linux 本地卷目录；包含自动维护。
- 每场随后验证导出、compact、备份、覆盖恢复、快照一致性及三次进程重启读取。
- 未清空操作系统页缓存；保留其他 OrbStack 工作负载。三次重启样本只作为进程冷启动观察，
  不代表磁盘完全冷读 p95，也不用于严格统计显著性判断。

复现入口：

```sh
python scripts/local_disk_optimization.py \
  --bin /validation/optimization2-20260916/bin \
  --output /validation/optimization2-20260916/comparison-rerun \
  --write-interval 2s
```

需在 8 CPU / 8 GiB 的 Linux 容器内运行；`--bin` 包含本轮修改前的 `graphdb-main`、
修改后的 `graphdb-new` 和同一份 `loadtest`。`graphdb-main` 是脚本的兼容名称，并非当前 Git main。
输出目录必须不存在，测量时不要同时运行构建或重负载测试。

## 主对比结果

以下均为同一轮修改前→修改后；延迟单位为 ms。吞吐来自固定 16 查询客户端的闭环负载，
服务与负载工具共用容器资源，不是服务的最大容量。

| 指标 | direct | WAL |
| --- | --- | --- |

| 测量期服务 CPU 时间 | 88.94 → 61.48 秒（−30.9%） | 84.46 → 58.13 秒（−31.2%） |
| 测量期峰值 RSS | 637.88 → 575.61 MiB（−9.8%） | 687.98 → 467.33 MiB（−32.1%） |
| scan p95 / p99 | 21.070 / 28.234 → 18.997 / 25.844 | 20.896 / 27.227 → 18.426 / 25.221 |
| match p95 / p99 | 14.152 / 20.563 → 13.397 / 18.908 | 14.016 / 19.484 → 12.953 / 18.329 |
| min_version 查询 p95 / p99 | 13.860 / 19.658 → 13.087 / 18.804 | 13.762 / 19.758 → 12.984 / 18.320 |
| traverse p95 / p99 | 9.427 / 14.431 → 8.424 / 12.717 | 9.508 / 14.746 → 8.315 / 13.109 |
| 写入完成 p95 / p99 | 421.542 / 540.568 → 403.690 / 493.519 | 193.971 / 202.670 → 197.418 / 210.599 |
| WAL 受理 p95 / p99 | — | 26.782 / 33.038 → 29.294 / 39.210 |
| WAL 受理后到可读 p95 / p99 | — | 180.129 / 189.062 → 177.590 / 194.917 |
| export | 71.27 → 71.91 | 85.43 → 74.49 |
| compact | 740.23 → 627.17 | 734.65 → 704.32 |
| 本地备份 | 2152.27 → 1452.00 | 2161.19 → 1555.61 |
| 覆盖恢复 | 6174.63 → 4551.58 | 6013.96 → 4667.99 |
| Linux write_bytes | 270139392 → 277008384 | 204562432 → 206778368 |
| fsync 次数 | 3437 → 3450 | 2459 → 2377 |
| 峰值文件句柄数 | 32 → 34 | 29 → 29 |

两种模式已发布吞吐均约 2 批/秒（由固定写入节奏限定），没有将 WAL 受理数当成发布吞吐。
fsync 失败数全部为 0。`read_bytes` 为 0–65536 字节，说明这些读数主要受页缓存服务；
`rchar/wchar` 包含响应等系统调用流量，不能当作磁盘读写量。完整计数见原始 JSON。

三次进程冷启动后的首次读取，direct 为 64.58–75.20 → 40.18–57.51 ms；
WAL 为 56.07–70.95 → 51.43–53.35 ms。样本数和页缓存控制不足以验收“冷读 p95 提升 10%”。
每种模式导出和维护操作仅各执行一次，也不将其耗时变化解释为稳定的容量增益。

### WAL 尾部补查

主对比的 WAL 受理 p95/p99 分别上升约 9.4%/18.7%，每场仅有 60 个写入样本。
为确认这是否稳定复现，增加一次仅含 WAL 的 60 秒混合负载，顺序改为前→后，
其他数据、客户端、写入节奏、维护配置和资源限制保持一致。每场实际发布 120 批，
版本增量均为 120，请求错误数为 0。

| 指标 | 修改前 | 修改后 | 变化 |
| --- | --- | --- | --- |
| WAL 受理 p95 | 28.036 ms | 29.363 ms | +4.7% |
| WAL 受理 p99 | 32.524 ms | 33.147 ms | +1.9% |
| WAL 受理后到可读 p95 / p99 | 174.074 / 179.837 ms | 172.286 / 173.965 ms | −1.0% / −3.3% |
| 混合操作/秒 | 2971.88 | 3237.81 | +8.9% |
| CPU 时间 | 171.26 秒 | 117.82 秒 | −31.2% |
| 测量期峰值 RSS | 550.88 MiB | 618.35 MiB | +12.2% |

首次较大的 WAL 受理 p99 增幅没有稳定复现，但样本仍不足以证明所有运行都满足尾延迟门槛。
两次 WAL 测量的 RSS 增减方向相反，且补查超过了原定 +10% 上限，因此**内存收益及该上限验收未定**。
现有资源采样不足以把差异归因于具体缓存或 GC 阶段，不能将首次 −32.1% 单独当作稳定内存收益。

### 实际文件的行组过滤

检查主对比 WAL 场景在 v83 写出、备份恢复后保留的五个实体 pack，读取每个文件的实际 shard 列
及行组统计。1588 个“实际分片 × 行组”组合中，修改前需保留 1587 个（99.94%），
修改后保留 183 个（11.52%）。原始记录为 `rowgroups-before.jsonl` / `rowgroups-after.jsonl`。
这是可复查的文件过滤能力改善，不等于任意查询都能减少 88% 的实际磁盘 I/O。

### 判断

本轮在三组前后观察中，CPU 时间均减少约 31%，混合吞吐提高约 9%–19%；
所有列出的查询 p95/p99 都下降，实体 pack 的行组过滤明显改善。
这些结果支持保留本轮优化。整体严格性能验收仍有未定项：RSS 波动、真实冷读、长时间负载，
以及较小尾延迟样本的稳定性。没有以短测结果宣称全部原定门槛通过。

## 范围限制

本轮没有运行 10 万实体矩阵、30 分钟持续负载或受控清空页缓存测试。
增量索引仍扫描图以找到受影响分片；边分页、写入对象字节缓存和慢网络备份对读视图的占用
仍有后续评估空间。本轮结论仅覆盖这里列出的实现与实测场景。
