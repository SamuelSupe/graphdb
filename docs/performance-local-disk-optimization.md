# 本地磁盘实现：性能定位与优化

日期：2026-09-16。工作区 `GraphDB-local-disk-v2`，分支 `codex/local-disk-v2`。
本次比较的是**增加对象快照备份后的本地实现**与本轮优化后的实现，不是 `main` 与本地版的比较。
代码尚未提交。原 GraphDB 和 GraphDB-local-disk 工作区保持原样。

## 结论

确认并修复了并发提交误触发索引重建、WAL 多版本批次无法增量更新索引、备份重复加载与
JSON 复制、目录哈希与分页堆的过量分配、实体页缓存未遵守配置预算等问题。

固定写入压力的单轮 HTTP 检查中，Direct ingest p95 从 1577 ms 降至 448 ms，查询延迟基本持平，
测量期间峰值 RSS 从 872 MiB 降至 558 MiB。WAL 受理后可读 p95 从 2381 ms 降至 178 ms，
但持续维护索引带来了额外内存和 CPU 开销。**本次不宣称整体达到原方案的全部性能验收目标。**

## 瓶颈与改动

1. **并发索引追赶被误判为冲突。** 图版本已经前进时，按顺序执行的旧版本索引工作被拒绝，
   后续提交又因目录版本落后而重建。现在保留实际 `baseVersion`，在独占本地目录、原 writer fence、
   活跃读视图和目录 CAS 共同保护下，允许索引按顺序追赶；恢复、GC 和删除不能穿过这些引用。
2. **批量 WAL 提交跨过多个版本。** 原来的 `version - 1` 假设不适用于同一批次的多个逻辑提交。
   正向、反向索引现在使用同一实际起始版本。Direct/WAL ingest 发布后异步推进索引，
   同租户相邻待执行工作合并；超过 8192 个变更引用转为重建，全进程最多 8 项后台工作。
   达到上限后在释放租户锁后同步完成。普通 `/v1/commits` 保留等待自身索引和返回警告的行为。
3. **备份重复读取、复制整图。** 本地捕获在租户维护锁下复用有效写缓存；任务结果解码后的数据
   已经 JSON 规范化，校验哈希不再进行一次额外的 JSON 编解码。持久化格式和校验没有变化。
4. **请求路径的重复分配。** 目录哈希按原编码顺序流式计算；目录行预分配；分页堆保存位置和 key，
   避免逐个复制大实体结构。实体 GET 优先使用满足版本要求的现有图缓存。
5. **缓存预算。** 解码实体页缓存遵守索引缓存配置的一半预算及既有上限，和边缓存一致；
   这不是整个进程的 RSS 限制。
6. **性能实验暴露的正确性问题。** 缩小打包预算后，增量目录遗漏页面字节估算，目录引用与实际
   文件名不一致，真实备份失败。已补齐估算，新增大字段、小预算下的提交→备份→恢复测试。
   默认仍为 32 MiB；失败的 512 KiB 实验不计入收益。

## 测量方法

- OrbStack Linux 命名卷，容器限制 8 CPU / 8 GiB，Go 1.25.14。保留其他项目工作负载。
- 相同停服种子数据：10002 实体、5001 边；4 写客户端、16 查询客户端，每批 20 个实体。
- `scripts/local_disk_optimization.py --write-interval 2s`：每写客户端间隔 2 秒，
  预热 5 秒、测量 30 秒，Direct 前→后，WAL 后→前，各一轮。
- 四场测量均发布 60 批、版本增加 60，无请求错误。预热按时间结束，前后起始版本并不完全相同；
  数据集合、测量期写入数量和操作序列相同。混合吞吐以查询为主，不能当作写入容量上限。
- 每场完成 export、compact、本地快照备份、覆盖恢复、完整导出相等校验及三次重启读取。
- CPU、RSS、FD 每 500 ms 采样；磁盘 I/O 来自 `/proc/<pid>/io`，同步次数来自 GraphDB 指标。
  RSS 是测量窗口采样峰值，不是进程生命周期最大值；完整 HWM 也保留在 JSON 中。
- 冷读仅清空进程缓存，没有驱逐 OS 页缓存；三次样本不足以估计可靠 p95。

Direct 写入 p95 下降 71.6%，RSS 下降 36.0%，混合吞吐仅增加 2.3%，应视为基本持平。
WAL 可读 p95 下降 92.5%，同时 RSS 增加 86.5%，查询 p95 增加约 7%–12%。
旧版 WAL 的索引起始版本判断错误，批次发布后目录持续落后；日志中有 stale 索引重建及
`index_rebuild_running` 背压。新版持续更新索引，因此两者的索引写入工作量不同。
这解释了部分开销差异，不能消除已经观测到的资源回退；需要低内存部署或大量租户时仍应评估。
新版 WAL 的后台 compact 也发生在本轮窗口内，单轮数字不足以分离维护调度的影响。

### 维护流程定向复核

混合负载后的单次导出、恢复有波动，随后只对维护路径复核：相同种子副本、交替顺序、各 3 次，
每次验证恢复后的完整快照一致。以下为中位数，不是 p95。

| 操作 | 优化前，ms | 优化后，ms | 变化 |
| --- | ---: | ---: | ---: |
| export | 73.05 | 74.49 | +2.0% |
| compact | 788.27 | 824.39 | +4.6% |
| 本地快照备份 | 2394.96 | 2174.42 | -9.2% |
| 覆盖恢复 | 5485.83 | 5232.69 | -4.6% |

此复核未发现超过 5% 的中位数退化，但样本较少，不能据此证明尾延迟不回退。

## 验证与证据

### 聚焦基准

相同 Linux 卷、8 CPU 限制、1 万实体，`-benchtime=4x -count=1 -benchmem`：

| 基准 | 优化前 | 优化后 | 每次分配，前→后 |
| --- | ---: | ---: | ---: |
| 四并发提交，每客户端 20 实体 | 13.345 s/轮 | 0.495 s/轮 | 6806 MB → 377 MB |
| 备份捕获 | 99.48 ms | 7.61 ms | 180 MB → 14.7 MB |
| 备份记录解码 | 112.58 ms | 60.62 ms | 155 MB → 90.4 MB |

四并发提交的索引警告从每提交 0.25 次降为 0。这个基准专门暴露“追赶失败→重建”路径，
使用 `NewTenantStore` 的逐实体记录模式；HTTP 默认关闭逐实体记录。因此 27 倍的该基准耗时差异
不能外推成整个服务吞吐提升 27 倍。捕获微基准命中写缓存，不能代替完整备份传输耗时。
原始数据在 `before-focused.log`、`verified-focused.log`，CPU/分配 profile 包含初始化阶段。

```sh

  --bin /validation/perf-bin \
  --output /validation/new-unique-run-directory \
  --entities 10002 --warmup 5 --measure 30 --write-interval 2s
```
