# 可用性与滚动升级修复验证（2026-10-04）

本轮为未发布候选，保留单机 direct/WAL、单组 Raft 和租户分片。修复两个已稳定复现的可用性问题；两套限定来源的滚动矩阵和单机长测通过，三副本维护压力长测两次失败，本候选不具备发布资格。上一轮失败记录保留在[完整测试报告](full-validation-2026-10-03.zh-CN.md)，本轮汇总见[机器可读记录](availability-rolling-validation-2026-10-04.json)。

## 修复

- **滚动检查追赶移动目标**：此前按节点 ID 采样，较早读取的 follower 会被后来读取的 Leader 提交位置判为落后。现在先固定 Leader 的提交位置，再检查全部副本。回归测试在 follower 响应后推进一次提交；旧实现误拒绝健康组，新实现通过，真正落后一条日志仍阻止升级。摘流仍要求新的多数派探测、在途提案完成、全部投票副本应用和安全交接。
- **压缩扫描持有租户写锁**：此前压缩发布阶段在锁内读取全部直接提交幂等记录，慢 I/O 可让前台写入超时。同步压缩和后台压缩任务现将扫描、结算移到发布锁前；条件更新、未知结果拒绝、当前历史校验及并发提交尾部保留不变。两个路径的阻塞回归在旧实现都因一秒写入期限失败，新实现能完成写入、冷读取两份实体并重放原幂等结果。

压缩扫描完成后，新图提交的版本高于已捕获的快照版本；并发重试通过条件更新处理。发布仍取得租户锁、重新检查写入 fence 和租户可写状态，并验证当前头来自捕获的提交历史。遇到记录读取/结算错误仍不丢弃历史。

## 失败窗口诊断

第一轮 Raft 日志在 UTC `2026-10-03 22:01:42` 记录 Leader 因多数派不活跃退出，随后两次换主，于 `22:01:51` 恢复 readiness。Leader 的持久化直方图有一次耗时落在 5–10 秒区间，其他两副本的控制消息也出现 5–10 秒耗时；本地应用及快照错误字段为空。共享 VM 的 load average 超过 100，存在约 7GiB swap 占用。该直方图记录持久化路径总耗时，包含锁等待与调度时间，不能直接等同于单次 fsync 耗时。以上支持资源停顿参与故障的判断，尚不能证明它是唯一根因；不取消 fsync、多数派或强读屏障，也不提高请求期限把 FAIL 改成 PASS。

串行复测在 UTC `2026-10-03 22:30:00` 再次记录 Leader 因多数派不活跃退出，`22:30:03` 重新选出同一节点；错误事件集中在 `22:30:00.131` 至 `22:30:03.998`。Leader 的 `persist` 路径再次有一次 5–10 秒耗时。恢复后的三个副本 Leader 和日志位置一致，无应用/快照错误，未 OOM；不能据此将失败改为通过。共享 VM 在后续观测中仍有约 26–32 的 load average 和约 6GiB swap 占用；压力来源与单次停顿的因果关系尚未被隔离验证。

请求指标错误统计 HTTP 操作失败；错误事件还包括响应内容校验和维护等待失败，二者不可直接相加。机器记录分别保存两个计数。

## 失败尝试与验收边界

本轮第一次单机启动开启独立 admin listener，但客户端仍向数据 listener 请求租户管理，因 404 未进入负载；已修正验收客户端的 admin URL。第二次将两个 2GiB 缓存配置放入 2GiB 容器，约十分钟后容器 `OOMKilled=true`、退出 137，随后请求连接失败；该运行失败，不能作为三十分钟通过证据。第三次恢复上一轮 12GiB 容器预算、保留原缓存、负载和请求期限重新验收。全部失败证据保留。

请求期限仍为 120 秒、维护期限十分钟；滚动流量按原幂等键或 WAL 身份重试，未把结果未知的非幂等操作自动重放。先前受影响来源身份、点号业务路径和进行中旧迁移的混部/回退限制继续有效，见[滚动手册](raft-rolling-upgrade.zh-CN.md)。本机矩阵不扩大到任意旧版本、数据或协议。

没有三台独立宿主机，跨宿主机故障域仍按用户决定待验收。本轮不构成生产容量、吞吐或短请求延迟承诺；未创建发行标签、未发布 GitHub 资产。
