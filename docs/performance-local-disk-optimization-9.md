# 本地磁盘性能复查：分页分配与重复压实

日期：2026-09-18。工作区：`GraphDB-local-disk-v2`，分支：`codex/local-disk-v2`。

## 结论

本轮确认并消除了两项重复工作：

- 有排序的分页路径只分配排序堆，不再同时预分配一份未使用的结果切片。深分页样例单次分配减少约 139 KB（24.7%）。
- compact 任务先检查当前版本是否已经压实，再按需构建快照。1 万实体、数据未变化时，任务执行主体耗时从 15.50 ms 降到 3.99 ms，分配减少 80.3%。

查询基准的耗时没有明确改善；实际混合吞吐为 2,830 → 2,803 ops/s（-1.0%）。本轮可以确认局部开销减少，不能据此宣称整体性能验收通过。

## 修改和正确性边界

生产修改仅涉及两个文件：

- `internal/query/match.go`：普通候选、按 ID 候选和字段索引候选三条有界分页路径按是否排序选择缓冲区。排序、过滤、聚合、游标、成本限制和结果所有权逻辑沿用原实现。
- `internal/storage/task_compact.go`：使用已加载不可变图的版本判断已压实状态；实际需要 compact 时仍构建完整快照，沿用原发布顺序和并发写入检查。

扩展现有 `TestUnifiedTaskRunsCompactAndExportSnapshot`，验证重复 compact 的任务终态、进度和数据保持一致，以及随后写入新版本后仍会生成对应的新快照。原测试只覆盖首次任务压实，不能保护任务快速返回与新版本压实之间的边界。分页修改复用已有排序、跨页、聚合、取消和返回值隔离测试，没有新增实现细节断言。

新增 `BenchmarkCompactTaskAlreadyCompacted10K` 使用真实 FileStore，包含任务进度持久化；不包含任务入队和外部轮询等待时间。测量前完成首次 compact。

## 环境与方法

- OrbStack Docker，Linux arm64，`golang:1.25-bookworm`，4 CPU、6 GiB；源码、数据和临时文件位于 Linux named volume。
- 基线是本轮修改前的完整工作区快照，包含前八轮修改，并非原始 main。工具输出的 `main-local` / `new-local` 分别表示本轮修改前 / 后。
- 两份源码归档、二进制哈希和四个代码/测试文件的增量补丁保留在证据目录。新 compact benchmark 在两份源码中使用相同 fixture，基线生产代码未改动。
- 微基准各 `-benchtime=1s -count=1`。这是单次样本，分配量和耗时分别报告。
- HTTP 使用同一停止状态的种子数据：10,002 个实体、5,001 条边；WAL sync、100 ms flush，4 个写客户端、16 个读客户端，每客户端每 2 秒写 20 条。每场预热 5 秒、测量 60 秒，修改前后各一场。
- 保留后台维护：每场实际发生 2 次 compact、1 次 GC。测量后执行 export、compact、backup、overwrite restore 和重启。
- 不清除操作系统页缓存，不停止其他 OrbStack 工作负载。冷启动测量仅重启 GraphDB 进程，只有一次样本，不能解释为操作系统冷缓存 p95。

## 验证结果

- 全量 Go 测试：12 个包、1,306 个顶层测试通过；2 个需要外部 S3 的测试在后续对象备份门禁中补齐。
- `go vet ./...` 通过。
- race：graph 136、query 141、storage 213、HTTP API 184 个顶层测试通过。storage 为聚焦选择，包含任务、compact、WAL、恢复、删除、本地存储、读视图、GC 和索引；不是全 storage race。
- 实际 HTTP direct/WAL 门禁通过，Python SDK 12 项通过，Go SDK 包包含在全量 Go 测试中。
- 独立 MinIO 对象备份门禁通过：分片上传/发布、恢复目标约束、重启重试、空数据目录发现备份、dry run、按需恢复、覆盖恢复、恢复演练、再次重启校验。
- 源码增量、最终文件哈希和 `git diff --check` 检查通过。未提交、推送或发布。

环境启动时第一次 MinIO bucket 尚未创建，外部测试得到 `NoSuchBucket`；创建专用 bucket 后重跑通过，原失败日志保留在 `environment-startup/`。恢复诊断首次将管理请求发往数据端口得到 404，修正诊断脚本使用管理端口后重新运行；没有修改服务路由。
