# GraphDB 实体与边范围分页设计

状态：设计草案。本文参数为建议初值，性能收益需要通过基准验证；不代表相关功能已经实现或通过发行验证。

采用“保留 64 个逻辑分区，分区内按 ID 范围组织有界物理页”的方案。实体、正向边和反向边共用这个原则，继续使用不可变 Parquet 对象和目录 CAS 发布。

## 1. 目标与验收边界

修复三个路径的整分区重写：

- 实体页。
- 正向边页。
- 反向边页。

旧布局完成迁移后，修改一条记录，只读取并重写它所在的物理页；发生分裂时，只处理这个页及本次新增内容。

建议初始限制：

| 参数 | 建议值 | 含义 |
| --- | ---: | --- |
| 每页最大条目数 `R` | 1024 | 实体数或边数，不是 Parquet 展开后的物理行数 |
| 每页目标文件上限 `B` | 8 MiB | 编码后超过上限，继续拆分 |
| 后台合并触发线 | 少于 `R/4` | 还须满足合并后的条数和字节限制 |
| 单条超大记录 | 独立成页 | 保留原有合法数据，不因分页规则新增终态失败 |

对已经有界的页，数据页处理量应满足：

```text
数据页读取、编码与写入量 = O(触及的不同页数 × 页容量 + 本次变更内容)
```

这个承诺不包含首次拆分旧大页，也不代表整个 commit 已经与租户规模无关。目录编码、二级索引和图内存结构的成本必须分别测量。

## 2. 保持逻辑分桶，改变物理分页

外层继续使用现有规则：

```text
实体：    hash(lower(entity.ID)) % 64
正向边：  relationType + hash(lower(edge.From)) % 64
反向边：  relationType + hash(lower(edge.To)) % 64
```

桶内按原始 ID 的字节顺序排列：

```text
实体页：entity.ID
边页：  edge.ID
```

分桶继续使用现有大小写规则；范围比较不转小写，不引入新的排序语义。

一个逻辑桶可以包含多个物理页：

```text
逻辑桶 00
  [-∞, "host:m")       → 对象 A
  ["host:m", "host:t") → 对象 B
  ["host:t", +∞)       → 对象 C
```

点读通过 ID 二分定位，顺序扫描直接从对应页继续。无需维护每桶全局深度，也不存在哈希分裂倾斜问题。

## 3. 目录和物理对象的职责

继续让 `EntityPageSpec`、`EdgeShard` 表示逻辑分区，由它们引用多个物理对象。不要把物理页 ID 塞进现有逻辑分片字段，改变所有调用者对 `Shard` 的理解。

每个物理页引用需要表达：

| 字段 | 契约 |
| --- | --- |
| 下界、排他上界 | 定位范围；首尾可以无界 |
| 对象 key | 不可变 Parquet 对象的位置 |
| 条目数 | 页内实体或边的数量 |
| 文件字节数 | 准入、诊断和基准使用 |
| 内容 hash、schema hash、codec | 校验内容与解码兼容性 |

目录还需明确分页格式：旧目录缺省为单页布局，新目录标识为范围页布局。相关字段必须进入目录序列化和校验，不能只存在于内存。

必须保证：

- 同一桶的范围有序、不重叠，边界覆盖整个 ID 空间。
- 每条记录恰好属于一个页，且实际 ID 落在声明范围内。
- 目录计数等于各页计数之和。
- 空桶有明确表示；“没有记录”和“引用的对象丢失”不能混为一谈。
- 不变页继续引用原对象，不因目录版本提升而重写。

数据内容 hash 和路由目录 hash 分开。前者校验页内容，后者覆盖范围边界、对象引用、计数和 schema。仅扩大一个页的路由范围时，可以保留原数据对象。

`EntityRecord` 保持可选。它可以提供定位提示，但目录必须能够独立完成点读；页分裂后，不能为了更新指针而重写所有未变实体的记录。

## 4. 写入、分裂与删除流程

每次增量更新按以下流程执行：

1. 固定源图版本、目录版本和租户 generation。
2. 将变更记录归到对应逻辑桶，再归到具体物理页。
3. 同一页中的多个变更合并处理，只加载一次旧页。
4. 应用修改、排序，计算新内容。
5. 未超限则生成一个新对象；超限则拆分为多个对象。
6. 复用所有未变化的对象引用。
7. 页对象持久化完成后，发布完整的新目录。

分裂应按条数和估算字节均衡分配。例如 1025 条记录应分成接近各半的两页，避免反复产生“1024 条＋1 条”的碎片页。编码后仍超过字节上限时继续拆分；单条超大记录独立处理。

删除规则：

- 页内仍有记录：只重写该页，通常保留范围边界。
- 页被删空：移除引用，扩展相邻范围，尽量只修改目录。
- 桶被删空：发布明确的空桶状态。

全量 rebuild 必须直接产生有界页。否则“新建索引后修改一条记录”的回归仍无法稳定通过。

新范围页在第一版中建议一页一个物理对象。继续打包小页时，也必须限制物理 pack 大小，并确保修改一页不会顺带重写未变化的页。

## 5. 读路径必须同时改到物理页粒度

点读流程：

```text
固定目录版本
    → 计算逻辑桶
    → 二分定位物理页
    → 加载、校验该页
    → 查找实体
```

目录的范围排序、完整性检查和 hash 校验应当每个目录版本执行一次并缓存结果，不能每次读取实体时重新校验整个目录。

批量点读按物理页分组，每页只读一次。

顺序分页必须满足：

- 保持现有“逻辑桶顺序＋桶内 ID 顺序”。
- 通过游标定位桶和页，从页内对应 ID 继续。
- 收集到一页结果后停止，不加载后续无关页。
- 游标绑定租户 generation、图版本、目录 hash、查询条件和最后一个 ID。
- 游标不依赖物理对象 key，避免分裂改变业务分页语义。

禁止先把一个桶的所有物理页合并到内存，再执行分页。这种实现功能上可能正确，却会引入新的深分页成本。

页对象缺失、损坏或校验失败时，索引应返回不可用或错误，按现有契约回退到完整图。不能把失败解释为“没有匹配记录”。

## 6. 边分页与超级节点

正向和反向目录分别按原有关系类型、端点逻辑桶组织，桶内再按 `edge.ID` 分页。

一条边移动端点或改变类型时，需要处理旧、新位置，覆盖正向和反向目录；删除实体产生的关联边删除，也必须进入受影响集合。

邻边分页应采用惰性迭代：

- 从 `startEdgeID` 所在的物理页开始。
- 按需加载后续页，应用端点和关系过滤。
- 多个关系类型之间归并有序迭代器。
- 每个迭代器只保留当前页，不能预加载全部物理页。

对拥有大量连续候选边的超级节点，这可以限制分页工作量。对同桶中候选非常稀疏的普通节点，扫描仍可能读取多个页，必须计入查询成本并支持取消；本轮不承诺所有邻边查询都是固定页成本。

## 7. 发布、取消、重试和资源释放

新页必须先持久化，再通过现有索引目录 CAS 发布。当前发布入口见 `internal/storage/index_parquet_refresh.go` 中的 `putIndexCatalogWithMetaFast` 调用。范围边界和页引用必须在同一次目录发布中生效，不能分别更新。

| 失败位置 | 处理方式 |
| --- | --- |
| 读取或构建页期间 | 保留旧目录，释放本次资源 |
| 部分页已写完、目录未发布 | 旧目录继续有效，新对象暂时无引用 |
| CAS 冲突 | 不覆盖新目录；重新检查当前版本，重算或合并任务 |
| 发布结果不确定 | 读取实际目录确认结果，不能直接删除本次对象 |
| 发布成功后取消或清理失败 | 新目录仍有效，清理独立重试 |

图版本、租户 generation 和 writer fence 必须在发布前重新检查。维护工作不能把旧目录重新发布到更新的图或已替换的租户上。

正向主目录和反向目录目前分别发布，本方案不假设两者天然原子。读取时检查各自版本；反向索引落后时回退或报告不可用，不能返回缺失邻边。

重试沿用有界、可分类的策略。退避期间释放读视图、文件句柄、内存预留和后台名额；取消后停止安排新 I/O。不得改变已经确认的 WAL/commit 结果，也不把真实持久化错误普遍降格为可忽略错误。

## 8. 旧布局迁移、混部和降级

新读路径同时支持旧单页和新范围页，允许不同桶逐步迁移。

旧大页第一次拆分仍是一次 O(旧页大小) 操作。推荐先后台重建热点、大租户的索引；小桶可以在写入时惰性迁移。迁移受维护预算限制，不能持有全局资源无限等待。

对 legacy 256 桶或没有明确布局标记的旧目录，需要验证其实际归属规则。不能仅因为当前桶和 legacy 候选桶都存在，就向两者写入同一条记录；无法可靠识别时，采用受控重建。

部署顺序为：

```text
读兼容上线 → 确认所有相关节点可读 → 启用新写格式 → 迁移旧大页
```

单次发布要允许旧二进制混部，必须通过真实二进制验证其读取、写入、GC、备份和快照路径。验证不能通过时，采用两阶段发布；不能把 `LayoutVersion` 当成已经完成能力协商。

降级流程必须显式执行：

1. 停止产生新的范围页目录。
2. 使用支持新布局的程序，将索引重建为目标旧版本能读取的布局。
3. 校验数量、hash、查询和反向邻接结果。
4. 完成目录切换与读者处理后，再降级程序。

本轮保持图快照、WAL 和 Raft 网络格式不变。共享构建函数时，必须避免索引分页改动意外改变这些格式。

## 9. GC、备份和缓存

GC 以完整引用关系判断对象是否可删除，至少覆盖：

- 当前目录。
- 被游标和读视图固定的旧目录。
- 正在构建、尚未发布的对象保护集合。
- 备份和运行态快照持有的引用。

同一图版本可能经过 rebuild 得到不同目录，因此不能仅凭图版本号判断对象是否仍被使用。

备份需要捕获确定的目录及其引用对象集合，恢复时验证范围、数量和 hash。复制“备份时刻最新的一批文件”不足以保证一致性。

缓存按租户、物理对象身份、内容 hash 和 schema 隔离；目录编译缓存按目录 hash 隔离。缓存必须有字节上限，不能因为分页增加了对象数量而放大内存占用。

## 10. 目录开销单独治理

第一版复用现有目录结构，避免同时引入新的目录树系统。但完整目录的编码与写入仍可能是 O(页数)，必须公开这个剩余成本。

基准分别记录：

- 数据页读取、编码和写入字节。
- 目录编码、hash 和写入字节。
- 对象请求数与 fsync 次数。
- CPU、峰值内存和提交延迟。

如果数据页修复后，目录已经成为主要瓶颈，再引入分层目录：根目录引用不可变子目录，更新只复制受影响路径。届时单独设计和验证，不能把它混入本轮修复后宣称整个写路径已经恒定成本。

## 11. 测试矩阵与实施顺序

必须覆盖以下行为边界：

| 类别 | 关键验收 |
| --- | --- |
| 有界写入 | 现有实体回归通过；正向、反向边加入同类回归 |
| 分裂 | 条数超限、字节超限、单条超大记录、连续插入 |
| 删除 | 删除首、中、尾页；整桶清空；删除后重新插入 |
| 读取 | 点读、批量点读、跨页扫描、深分页、旧目录读取 |
| 邻接 | 超级节点、端点移动、关系变化、自环、反向分页 |
| 故障 | 缺页、坏 hash、写入失败、CAS 冲突、发布结果不确定 |
| 生命周期 | 取消、重试资源释放、GC 与旧读视图并行 |
| 兼容 | 旧布局、真实旧二进制、滚动升级、降级、备份恢复 |

性能基准使用 `N=10⁴、10⁵、10⁶` 等规模，保持被修改页的填充率和字段大小相近，并分别测冷缓存、热缓存。除了验证写入量，还要确认深分页不会重新读取全部子页。

建议按五个阶段实施：

| 阶段 | 完成条件 |
| --- | --- |
| 读兼容 | 新旧目录可读，尚不产生新格式 |
| 实体写入 | 增量和全量构建均生成有界页，实体回归通过 |
| 边写入 | 正向、反向页及邻边惰性分页完成 |
| 迁移与恢复 | GC、备份、故障恢复、旧版本互操作通过 |
| 性能与发行验证 | OrbStack 完成专项、全量、race 和真实运行验证 |

后台低占用页合并可以后置。启用后，只合并相邻范围，合并结果仍须满足条数和字节上限，并使用同样的 CAS 发布与资源释放规则。
