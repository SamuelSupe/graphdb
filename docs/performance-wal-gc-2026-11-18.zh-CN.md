# 分片 WAL 队列恢复与跨 GC 持续写入对照

## 比较范围

基线为本地 `main` 的 `e82755e`，候选为同一提交加上本次三处改动。核对时 `github/main` 为 `5c60c44`。其中 `273cbe0` 已给协议 7 增加可选的收据保留期，启用时将受管理的终态收据移出受理目录。默认永久保留的路径仍枚举该目录。本次在协议 6 维护待处理成员索引。原始收据、别名、受理时间、LSN、结果和重试冲突判定仍由原记录提供。首次读取无索引的旧卷仍会遍历历史收据。

其他两处改动分别按已知积压量为单机 WAL 检查点预分配请求列表，以及省去分片页解码后对每行 JSON 的重复扫描。前者继续按原 LSN 顺序写入 v1 检查点，后者继续验证页散列、顺序、范围和数量。

## 持续写入

在 OrbStack Ubuntu arm64 的 Btrfs 卷上串行运行各轮，Go 1.27.3，`GOMAXPROCS=4`。每轮从新卷启动同一九副本拓扑，目录组、home 组和数据组各三个 Raft 副本，目录组和数据组协议 5，home 组协议 6，快照间隔 1,000 条。Router 直接调用标准 HTTP handler，组间使用 HTTP，磁盘同步和多数派受理配置相同。单张图，每批带固定幂等身份，新增四个不同实体。按墙钟节拍发起请求。写入期间主动触发三次图 GC，按目录记录的 `LastGCAt` 前进核对实际完成。

每轮检查全部收据均提交，每批四项成功、版本严格递增、受理时间和 LSN 与 202 返回值相同。再检查最终实体总数，并从每批抽取一个实体经 Router 读回。提交 P99 取全轮收据 `finished_at − accepted_at` 的最近秩 99 分位。202 的耗时另计。队列峰值根据全部收据的受理到完成区间重建。停写取最后一个 202 返回的时刻，收据排空取最后一个完成时间戳。高负载轮额外轮询最后一个批次的公开状态，以 25 ms 轮询间隔记录客户端看见排空的时间。

### 每秒 2 批

每轮 300 批、1,200 个实体，持续写入约 149.5 秒。相同配置的最终基线和候选各两轮，以下按运行先后排列。

| 版本 | 提交 P99 | 202 P99 | 队列峰值 / 停写时 | 收据排空 | 观测到 GC 完成的秒数 |
| --- | ---: | ---: | ---: | ---: | --- |
| 基线 1 | 1,380 ms | 13.1 ms | 4 / 1 | 245 ms | 10、60、111 |
| 候选 1 | 1,525 ms | 11.3 ms | 4 / 1 | 215 ms | 10、61、111 |
| 候选 2 | 1,475 ms | 12.5 ms | 4 / 1 | 173 ms | 9、60、110 |
| 基线 2 | 1,371 ms | 12.8 ms | 4 / 1 | 202 ms | 9、60、111 |

两轮 P99 的均值由 1,375 ms 升至 1,500 ms，增加约 9.1%。四轮最慢三个批次的序号均为 2、102、202（从 0 起算），对应三次发起 GC 后的首批。三个等长时段内，候选的时间加权平均排队批数分别为 0.54 / 0.55 / 0.54 和 0.47 / 0.50 / 0.51，基线为 0.50 / 0.48 / 0.50 和 0.38 / 0.41 / 0.41。GC 窗口出现短时积压，各轮均回落。此处 P99 与 GC 启动时间相关，这组对照未进一步分离 GC 调度、Raft 应用和磁盘同步各自的耗时。

### 每秒 6 批

每版一轮，各 630 批、2,520 个实体，持续写入 104.84 秒。两版均在写入中完成三次 GC。最初尝试的 75 秒窗口内，基线启动了三次 GC，但只完成两次，因此将两个版本的写入窗口一并延长到 105 秒。下表仅使用延长后的配对结果。

| 版本 | 提交 P99 | 202 P99 | 队列峰值 / 停写时 | 收据排空 / 客户端可见排空 | 观测到 GC 完成的秒数 |
| --- | ---: | ---: | ---: | ---: | --- |
| 基线 | 1,665 ms | 21.8 ms | 11 / 2 | 235 / 249 ms | 16.7、41.7、67.0 |
| 候选 | 1,807 ms | 41.4 ms | 13 / 1 | 150 / 174 ms | 15.0、43.3、80.7 |

三个等长时段的时间加权平均排队量，基线为 1.97 / 1.54 / 1.00 批，候选为 2.00 / 1.93 / 1.27 批。峰值增加两批，两版的积压最终均回落。候选提交 P99 增加 8.6%，停写时少剩一批，客户端观测到的排空时间缩短 75 ms。停写时的剩余工作量不同，此项不足以推断相同积压量下的排空速率。此次持续负载的峰值低于 64 批，分桶队列通过单独的恢复和回滚测试验证。

## 单项测量

| 路径和输入 | 基线 | 候选 |
| --- | ---: | ---: |
| 1,000 张终态收据、1 张待处理，重建内存队列 | 1,001 次收据读取，8.11 ms | 1 次，8.42 µs |
| 10,000 张终态收据、1 张待处理，重建内存队列 | 10,001 次收据读取，87.66 ms | 1 次，8.21 µs |
| 4,096 项单机 WAL 检查点，每次分配 / 用时 | 22.21 MiB / 44.44 ms | 17.75 MiB / 30.53 ms |
| 8,192 项单机 WAL 检查点，每次分配 / 用时 | 47.13 MiB / 69.30 ms | 35.45 MiB / 52.63 ms |
| 同一 64 行叶页的 CPU 时间 | 50.82 µs | 41.77 µs |
| 文件卷读取 128 个相邻键 | 0.351 ms，3 页 | 0.490 ms，3 页 |
| 文件卷读取 128 个分散键 | 5.41 ms，65 页 | 6.81 ms，65 页 |

队列测试先建立检查点，保留文件系统缓存，每次清空应用内的队列，取 5 次重建的中位数。读取次数仅统计收据对象，候选另外读取复制检查点。该时间只覆盖队列重建，完整进程启动还包括 FileStore 打开、Raft 恢复及选主。

单机 WAL 与文件批读各取三个独立进程结果的中位数，交替运行两个版本。WAL 每轮强制生成并重读四次检查点，4,096 和 8,192 项的检查点大小两版分别相同，均为 2,108,684 和 4,221,765 字节。8,192 项时，每次分配字节减少 24.8%。此处统计 Go 分配的字节总量，进程 RSS 峰值需单独测量。

叶页 CPU 对照在同一进程、同一 CPU 核上交替执行基线及候选加载函数。每组用相同的内存页加载 64 次，共 32 对，验证解码结果一致，候选在 31 对中耗用较少 CPU。文件批读直接调用现有的 `BenchmarkPartitionReadBatch/file`，相邻键和分散键两版分别读取 48,930 和 1,212,174 字节。尽管单页 CPU 下降约 17.8%，这三轮的完整文件批读中位耗时均上升，应分别看待两项指标。

## 恢复与验证

- 用基线与候选分别编译测试程序，依次打开同一卷。基线写入 79 张待处理收据及 1 张历史收据，候选重建并持久化分桶索引，基线再完成原队头，候选重新打开后识别剩余 78 张收据和新的队头。四次打开完成了对旧检查点、新检查点和旧程序回写的往返验证。
- 在强制回滚的写入中跨过分桶门槛，重新打开后仍只有原来的待处理项。含 65 项的真实应用快照安装到新卷后，核对了队列大小、队头及历史终态。已有九副本回归覆盖切主、全部 home 副本重启、图发布后的恢复，以及转换前的历史状态 URL、幂等重试和正文冲突。
- `internal/ha`、`internal/partition` 和 `internal/storage` 三个包的完整测试和 vet 通过。针对队列恢复、幂等、页损坏和 WAL 回滚的 race 测试通过。远端 Linux 主机在 SSH 握手阶段超时，以上结果均来自 OrbStack 的单机多副本环境。
