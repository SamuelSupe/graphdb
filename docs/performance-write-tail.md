# 写入长尾优化验证（2026-09-29）

基线为 `v2.1.1` / `39f63eabc7f468565e0867222d526ebb47ec3c96`。
最终保留 **GC 跳过被读视图保护的孤儿索引文件解码**，以及删除前保留退休代次的修复。
不改变磁盘格式、同步持久化、索引内存预算或 API。

## 原因与改动

真实 CMDB 混合负载复现了秒级写入长尾。调用栈显示，索引内存准入不足时，
WAL worker 会等待前序索引完成；同期 GC 在租户锁内完整解码旧 Parquet 文件，
直到删除阶段才发现这些文件仍被旧读视图占用。解码既争抢 CPU，也延长租户锁等待。

现在 GC 在确认文件不被当前 catalog 引用、且版本足够旧之后，先检查读视图。
仍被保护的候选只登记延迟回收，可回收时才校验内容和租户，真正删除时再次检查保护。
退休代次保留到实际文件变更，避免预检查清除代次后，新读者再次阻止同一个旧文件回收。
同版本 catalog 重新引用文件时，原有引用保护继续生效。

同时试验过增量实体页和正反向边的并行发布，但最终仅保留 GC 修复：
这一较小改动在本轮实验中的写入尾延迟、查询延迟和 RSS 更好。

## 方法

- OrbStack Linux/arm64，Go 1.26.7，专用容器限制 4 CPU / 8 GiB，容器本地磁盘。
- 相同初始目录副本：manifest 版本 313，约 1.88 万实体；每场结束版本均为 393。
- WAL 同步落盘，flush 100 ms，读写图缓存分别 2 GiB，维护内存预算默认 512 MiB。
- 4 写入客户端、16 查询客户端，复用 `tools/soaktest` 的 CMDB 数据与查询。
- 固定批次 400–479，每批 20 个 CMDB 应用组；每客户端 20 批。
  查询先运行 30 秒，随后每客户端按 5 秒计划间隔启动写入；每客户端最多一个在途请求，
  落后时顺序追赶。因此这是有限并发的固定请求序列，不是无界开放到达率测试。
- 每场总计 180 秒。显式 compact / GC / index rebuild 间隔为 60 / 90 / 120 秒，
  自动维护保持开启。查询客户端每次完成后间隔 200 ms。
- 顺序为基线 A1、试验版 B、基线 A2、最终 GC 修复版 C。服务二进制不带 profiler。
  诊断 profiler 单独运行，不混入下列数据。
- 每场重启进程并复制相同数据，**未清空 OS 页缓存**；机器仍有其他容器。
  A2 的前期还发生了一次证据目录复制，因此不作为严格隔离的性能认证。

## 查询与维护边界

以下为 30 秒预热之后、测量窗口内的服务端 HTTP P99，按路由汇总；
它们与客户端具名查询的全程分位数不是同一种统计口径。

| 路由 | 基线 A1 / A2 | 最终 C |
| --- | ---: | ---: |
| Query | 429 / 339 ms | 249 ms |
| Query stream | 435 / 420 ms | 255 ms |
| Saved query | 542 / 527 ms | 306 ms |
| Entity scan | 156 / 204 ms | 84 ms |
| Edge scan | 232 / 211 ms | 96 ms |

所有上述请求均为 HTTP 200，三个保留场次的客户端操作错误数均为 0，
结束时 index health 均为 ready，manifest/catalog 均为版本 393。

**尚不能判定所有路径都通过性能验收：**

- 显式 GC 完成耗时由 80.5–84.5 秒降至 6.0 秒。基线的 GC 阻塞了后续维护调度；
  A1 完成一次显式 compact、A2 完成两次，两者均未在窗口内完成显式 index rebuild。
  C 完成两次 compact、一次 GC、一次 index rebuild。维护完成数量与重叠时机不同。
- C 的两次显式 compact 耗时为 12.1 / 14.1 秒，基线已完成的 compact 为 8.0–10.1 秒。
  这是实测退化信号；样本少且维护重叠不同，暂无法给出稳定归因，不宣称压实性能达标。
- 启动期仅有一次导出样本：A1/A2 为 22.9/21.7 秒，B 为 28.5 秒，C 为 16.2 秒。
  它们都发生在首批写入及维护启动之前，不将这组波动归因于 GC 或并行发布改动。
- 最终仍有秒级写入尾延迟。索引内存不足时的同步追赶、完整分片重写和维护任务的内存竞争
  仍然存在；本次没有扩大预算或绕过背压来掩盖等待。
- 本轮优化测量没有重复 10 万实体矩阵、操作系统冷缓存实验或 30 分钟持续负载。
  后续 v2.1.2 发布门禁独立运行 30 分钟正确性持续负载，见[发布验证](validation-v2.1.2.md)；
  该检查不替代相对性能验收。

## 正确性验证

- 扩展既有 GC 读视图回归，验证被占用文件不被打开、释放后仍经内容校验回收，以及同版本 catalog 重新引用时的保护。新增断言在旧实现上明确失败，在最终实现上通过。
- 探索候选通过完整 `go test -mod=readonly ./...`、`go vet -mod=readonly ./...` 和索引/GC/WAL 相关存储路径的 race 检查。撤回并行编码后，重跑最终 GC 回归、相关 race 与游标/删除预算检查。
- 最终 HTTP direct/WAL gate 通过：实际写入、查询、导出、备份恢复、SDK 和重启后快照一致性。
- 最终压测目录重启后，80 个批次均为 committed、对应 80 个不同版本，manifest/catalog 均为 393。深度完整性校验检查 1,747 个对象，状态 ok、问题数 0。
- 测试使用干净 Git 源码快照叠加本轮改动，排除四个预先存在的无关未跟踪文件；原文件 SHA-256 全部保持不变。完整测试和 HTTP gate 的日志与最终针对性检查日志均保存于证据目录。

这些检查没有发现本轮修复造成的数据或并发缺陷，不代表已经证明不存在所有故障。

原始日志、profile、固定负载补丁、运行脚本和汇总位于本机
`.workflow/write-tail/`。`comparison.json` 保存各场客户端统计、资源采样汇总和预热后
服务端路由分位数；`fixed-workload.patch` 仅用于独立压测工具，不属于服务实现。
