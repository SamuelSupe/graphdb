# 单机写入、索引追平与 Raft 查询长尾对照（2026-10-19）

本记录针对 v2.3.4 之后的工作区候选，实验于 2026-10-19 至 20 日（Asia/Singapore）执行，基线提交为 `adddc6c75cdc656e8a43309f40a4db32fe5f44f2`。二进制均在 OrbStack Linux/arm64 使用 Go 1.26.7 构建，附加相同的私有 pprof 采样初始化；这不是已发布发行包的验收，也没有修改版本号。

## 定位与修改

1. **重复扫描关联分区。** 同一端点分区有多个关系类型变化时，增量索引原来逐类型重新扫描同一份邻接集合。现在每个端点分区扫描一次，再按需要更新的关系类型分配边；保留正向、反向、空分区删除和规范化内容哈希。
2. **Parquet 编码前的多余深拷贝。** entity/edge 行构造只读字段，仍先复制完整对象。移除这两处复制，保留编码格式和字段规范化；扩展现有回归覆盖混合关系类型、数值表示、哈希、持久化往返和输入不可变性。
3. **本地 compact 的两种快照串行准备。** 分片快照和兼容全量快照使用相同不可变图，现在在既有编码并发限额内同时准备。两种表示均完成持久化后才发布 manifest；对象存储路径维持原流程。阻塞分片写入的回归验证全量快照可并行准备，且 manifest 不会提前发布。
4. **WAL 调度随机拆批。** 到期队列和已缓冲的 durable admission 同时就绪时，旧调度器可能先派发部分请求，增加提交及索引更新次数。现在派发前有界收集已缓冲请求，维持确认顺序、恢复 LSN 顺序、强制 flush、取消与停机边界。新回归在旧实现上失败，候选连续五轮通过相关测试。

没有放宽 fsync、`Prefer: wait=committed`、Raft 确认、内存预算或索引版本校验，也没有把 stale 改报 ready。

## 可比负载

每种拓扑内部使用同一份停止状态的种子目录克隆、相同二进制构建方式和相同请求计划。每轮计划 6 分钟、4 个 writer、16 个 reader，完成全部 **288 批写入、5760 次查询**；慢请求允许排空，不在 6 分钟处取消。每个查询类别 1920 次。写入请求记录逐批 SHA-256；Raft 同时记录逐次查询 SHA-256。百分位使用 nearest-rank，对每次操作单独统计。

| 项目 | 单机 | 三副本 Raft |
| --- | --- | --- |
| 固定数据 | 63,247 实体 / 105,491 边 | 1,489 实体 / 2,561 边 |
| 起止图版本 | 1 → 289 | 16 → 304 |
| 每批 CMDB 组数 | 20 | 1 |
| 服务资源 | 4 CPU / 6 GiB，GOMEMLIMIT 4 GiB | 每节点 2 CPU / 1.5 GiB |
| WAL flush interval | 100 ms | 200 ms |
| 查询 | neighbors、profile match、range aggregate | profile match、min_version match、path-filter traverse |
| 索引健康采样 | 每 1.1 秒，327 个计划样本 | 每 1.1 秒，327 个计划样本 |

两种拓扑的数据量、批量和资源不同，**不能横向比较**。相同拓扑的前后轮次保持上述参数。健康采样避免与每 5 秒写入周期同相；stale 样本占比不等同于请求错误率或精确时间占比。

两边均在第 90/180 秒 compact、第 240 秒 GC、第 270 秒全量重建索引。Raft 使用 protocol 3、流式快照、`snapshot_entries=5` 压力配置。查询与写入并发，保留原有 120 秒 HTTP 超时。采样、profiling 和限额在前后相同；计时阶段串行执行，期间不运行本任务的构建或测试。

候选的约 9–10 秒写入出现在 compact 窗口，约 12 秒最大值出现在全量索引重建窗口。内部 flush 错误分别有 3/4 次，均为 `write backpressure: index_rebuild_running`，随后重试完成；不能把“客户端零错误”写成“内部没有重试”。停载后索引追平至 289，深度完整性审计均为 `ok`。

基线 stale 样本中有 134 次落后 2 个版本、59 次落后 4 个版本；候选 131 次均落后 4 个版本。拆批减少降低了更新频次和 stale 样本数，没有改善最大版本差。

结果受拆批、维护时序和轮次影响。早期相同 5 秒健康采样的一组基线/V1 对照，写入 P99 为 11.953 → 11.389 秒，部分查询 P99 反而回退；后续 V2 在 1.1 秒采样下写入 P99 为 11.576 秒，略好于最终候选的 11.975 秒。不同采样阶段不合并成一个统计总体，也不据单组结果承诺稳定的百分比改善。

## 数据与资源核对

两种拓扑分别核对前后全量导出：实体数量、边数量、实体字段、边字段、schema 和拓扑一致；写入版本无缺失，深度完整性审计均为 `ok`。仅时间、来源时钟等运行期元数据不要求两次独立运行逐字节相同。

单机整轮服务 CPU 用量为 881.045 → 625.431 CPU 秒；cgroup 内存峰值为 **4,210,147,328 → 4,323,008,512 字节（增加约 2.7%）**，限额均为 6 GiB。这里的 cgroup 峰值包含页缓存，不能称为进程 RSS。基线每 10 秒采样的进程 VmHWM 最大观察值为 3,958,910,976 字节，候选结束时 VmHWM 为 3,968,720,896 字节；采集覆盖不同，不能据此给出精确 RSS 改善比例。

Raft 三节点 CPU 用量之和为 486.495 → 364.009 CPU 秒。逐节点 cgroup 峰值分别为 297,541,632 / 287,145,984 / 328,282,112 → 256,372,736 / 258,461,696 / 247,771,136 字节；不同节点峰值不一定同时发生，不能相加后称为集群同时峰值。

单机相同的第 25–85 秒 CPU profile 窗口，总 CPU 样本为 113.92 → 84.03 秒。基线的邻接分区访问和 map 迭代显著，候选减少此处重复工作；Parquet 编码和 GC 仍占主要 CPU，不能把这次优化描述为消除了编码成本。

## 崩溃恢复与副本核对

分别从最终单机、Raft 的停止目录克隆出独立恢复数据。新建隔离探针租户，经 `Prefer: wait=committed` 返回成功后，单机 SIGKILL；Raft 则同时 SIGKILL 三个节点，然后重启。

- 两种拓扑都恢复出已确认的版本 2 探针及 `checkpoint=1234` 字段。
- 主测试租户恢复前后完整逻辑快照（含字段与来源元数据）相同，图版本保持 289/304。
- Raft 三节点健康结果均为 `applied_index=commit_index=423`。停止服务后，用存储层分别独立加载三份磁盘数据，主租户和探针租户快照都与 API 导出相同；这一步不经过请求转发。

这验证的是“确认后强杀再恢复”，没有声称覆盖本轮未实际注入的任意 fsync 中点断电。

## 解释边界与剩余问题

- **单机长尾改善，维护窗口仍有明显阻塞。** 全量索引重建期间的写入背压仍在，不能宣称长尾归零。若要取消这一等待，需要另外验证重建结果与并发提交的版本衔接，不能只移除保护条件。
- **单机 stale 仍存在。** 本轮均是异步索引落后，最大差 4 个版本，停载后追平；没有通过健康接口掩盖滞后。默认查询的回退/重试语义不变。
- **历史 Raft 约 12 秒极值尚需长时间复现。** 短轮次相同请求计划只能说明该负载下的结果，不能替代原 30 分钟增长型负载或生产验收。
- **候选组合的改善不能拆成每项修改的独立贡献。** 早期候选的部分查询 P99 也有回退；最终结论仅使用上述同采样周期、同种子、同请求计划的最终组合。

本地原始证据保存在 `.workflow/perf-tail-20261019/`，包括请求事件、CPU/阻塞/锁 profile、goroutine、资源、日志、快照及实验元数据。`single-before1` 有构建重叠，`single-before1/2` 还有造种过程遗留的非真实大提交；这两轮仅作诊断，已排除。正式种子在克隆前经正常 GC 删除该废弃提交，实体、边、schema 和起始版本保持不变。

被试验后放弃的变更包括替换字符串编码（文件大小或分配代价回退）和并行快照硬链接捕获（没有稳定收益）；它们不在候选生产代码中。
